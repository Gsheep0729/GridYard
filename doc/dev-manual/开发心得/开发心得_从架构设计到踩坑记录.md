## 1. 项目刚开始时，我们为什么要分目录

项目刚开始时，我们其实没有马上写文件传输。最先讨论的是代码放在哪里、第一版做到什么程度。需求文档里既有局域网直传，也提到了后续的账号、聊天和离线消息。如果一开始全塞进一个客户端工程，第一版可能写得快，但后面增加服务端时会很难拆。

最后我们把范围收紧：V1.0 只做局域网 P2P 文件传输，服务端只留目录，不提前实现。代码按下面几块放：

- `shared/`：协议类型、公共数据和帧编解码。以后客户端和服务端都要用。
- `client/`：当前真正运行的桌面客户端，包含 QML 界面、业务管理和网络收发。
- `server/`：给 V2.0 留位置，第一版不碰。
- `tests/`：先覆盖协议解析和不依赖界面的逻辑，后面再逐步补集成测试。

这个结构后来确实省了不少事。比如 `FrameCodec` 只负责从 TCP 字节流中拆出完整帧，不需要知道载荷是文件信息还是设备广播。文件发送逻辑出问题时，也不用去动 QML。我们后来也踩过“QML 和 C++ 各自创建了一个单例”的坑，这反过来说明分层只解决代码位置问题，对象由谁创建、谁持有仍然要单独设计。

## 2. CMake 是怎么一步步拆开的

最开始参考的是单个 Qt Quick 应用模板，所有源文件都能写进一个 `CMakeLists.txt`。项目文件变多后，这种写法很快就不好维护了：测试需要链接协议代码，但不应该把整个 QML 客户端也带上；以后服务端也需要协议代码，但同样不需要 Qt Quick。

所以我们把构建文件拆成三层：

- 顶层 `src/CMakeLists.txt` 负责统一查找 Qt、设置编译标准和挂载子目录。
- `shared/CMakeLists.txt` 生成静态库 `gy_shared`。
- `client/CMakeLists.txt` 注册 QML 模块并链接 `gy_shared`。

这里最实用的一点是 `target_include_directories(gy_shared PUBLIC .)`。一开始我们在客户端里写过 `../shared/protocol.h` 这种相对路径，目录一调整就会报错。改成由 target 传递包含路径后，客户端和测试都可以直接写 `#include "protocol.h"`。这让我们意识到，CMake 不只是“把代码编出来”的脚本，它也在描述模块之间的依赖关系。

## 3. 踩坑记录：C++23 模块与中文路径

**日期**：2026-04-10

### 问题现象
在环境搭建完成后，第一次编译遇到了诡异的错误。CMake 配置通过了，但在编译生成依赖阶段，连最基本的 `#include "frame_codec.h"` 都报了解析错误：
```text
error: 无法确定 .../frame_codec.h 的 ‘#include’ 转换：
malformed string 'ERROR 'unrecognized \'INCLUDE-TRANSLATE \'/.../frame_codec.h\'\'''
```

### 排查过程

一开始我们以为是头文件路径写错了，检查了 `target_include_directories`，也反复删掉 `build/` 重新配置，错误完全没变。高扬后来把同一份代码复制到纯英文路径后，编译突然正常，才把范围缩小到“实验性模块扫描 + 中文路径”这个组合。

最终确认是 GCC 16 的模块依赖扫描在处理中文路径时出了问题。项目开启了 C++23 模块实验支持，`g++-mapper-server` 在解析带中文字符的路径时生成了损坏的内部指令。

此外，也发现了一些配置上的小疏忽：
1. `main.cpp` 用了 `QQuickStyle`，但 CMake 里忘了链接 `QuickControls2`。
2. 自动生成的 C++ 注册代码找不到 `app_controller.h`，需要把 `core/` 目录加入包含路径。

### 解决办法
为了兼顾中文路径下的开发体验，当时是这么改的：
1.  关闭扫描：在 `src/CMakeLists.txt` 中设置 `set(CMAKE_CXX_SCAN_FOR_MODULES OFF)`，绕过编译器 Bug。
2.  补全配置：在 CMake 中显式引入 `QuickControls2` 组件，并将 `client/core` 加入包含路径。

### 这次留下的经验

这次花时间最多的不是改代码，而是不断排除“是不是自己 CMake 写错了”。以后遇到构建工具报出和源码内容对不上的错误，我们会先做一个最小验证：换英文路径、关掉实验特性、只保留一个源文件。这样比盯着完整工程反复改配置更快。

## 4. 从单体模板拆成三层构建

**最后更新**：2026-04-12

这一章记录的是实际拆 CMake 时的考虑。它和第二章有一点重复，但更偏向当时为什么没有继续沿用 Qt Quick 单体模板。

### 4.1 单体模板里混在一起的内容
在一个标准的 Qt Quick 单体工程中，CMake 文件主要集成了以下四大职责板块：
1. **全局编译器环境定义**（第 19-21 行）：声明最低 CMake 版本，并启用实验性 C++23 模块。
2. **Qt 环境发现与基础工程化配置**（第 25-26 行）：通过 `find_package` 拉取所需的 Qt 二进制包，并调用 `qt_standard_project_setup` 规范化资源加载路径。
3. **QML 模块注册与源文件声明**（第 28-38 行）：采用 `qt_add_qml_module` 将 C++ 源码与 QML 界面资产进行一站式注册与资源编译。
4. **依赖注入与部署发布**（第 39-48 行）：声明 `cxx_std_23` 标准，链接 Qt 组件库，并注入 `/opt/${PROJECT_NAME}` 的标准安装目录。

### 4.2 拆分时真正遇到的问题

如果协议代码留在客户端 target 里，测试 `FrameCodec` 时也得链接客户端依赖，未来服务端还会被迫依赖 Qt Quick。我们不希望跑一个纯字节流测试还要启动或加载界面相关模块，所以先把 `shared` 独立成静态库。

最后的分工很简单：顶层只放全局配置；`shared` 只放可复用逻辑；`client` 负责 QML 和应用入口。拆分后新增测试时，只需要链接 `gy_shared` 和测试真正使用的 Qt 模块。

### 4.3 拆完后最有用的两点

1. `shared` 不依赖 QML，协议和编解码测试可以单独运行。
2. 公共包含路径跟着 target 传递，不再到处写相对路径：

   ```cmake
   target_include_directories(gy_shared PUBLIC .)
   ```

   客户端和测试链接 `gy_shared` 后可以直接写：

   ```cpp
   #include "protocol.h"
   ```

我们也没有继续往下拆更多库。当前项目规模不大，拆得太细会让 CMake 文件和 target 数量增加，反而不方便找代码。

## 5. `.gitignore` 把源码目录一起忽略了

**日期**：2026-04-13

### 5.1 问题现象

Stage 0 时，本机一直可以编译，队友拉取后却提示缺少 `src/client/core/app_controller.h` 和 `.cpp`。更麻烦的是，本机执行 `git status` 还是干净的，所以一开始我们以为是队友没有拉完整。

### 5.2 真正的原因
后来执行 `git check-ignore -v src/client/core/app_controller.cpp`，才发现文件被 `.gitignore` 忽略了。
原本的 `.gitignore` 规则中写入了：
```text
core
core.*
```
本意是为了全局忽略在项目开发和调试过程中由系统（Linux）生成的各种核心转储文件（core dump 文件，如 `core` 或 `core.<pid>` 格式）。

然而，由于没有加前缀路径符号 `/`，这两条规则被 Git 视作**全局模式**，不仅会忽略根目录下的匹配文件，还会默默地忽略**任何子目录下名为 `core` 的整个文件夹**！

巧合的是，根据我们的“四层架构设计”，客户端的核心控制器业务逻辑刚好存放在 `src/client/core/` 目录中。因为文件夹名字恰好为 `core`，它里面的所有 C++ 源文件在创建之初就被 Git 默不作声地忽略了，根本没有被加入版本跟踪，自然也就没能推送到远程仓库，导致别人拉取下来后编译直接报错。

### 5.3 解决办法
之前有同学通过把 `.gitignore` 的规则改写为 `/core` 和 `/core.*` 来临时规避，但这留下了新的隐患——核心转储文件不再能被全局忽略，在子目录下运行程序崩溃时产生的文件会继续污染 `git status` 工作区。

最后保留 core dump 的全局忽略规则，同时明确放行名为 `core` 的目录：
```text
core
core.*
!**/core/
```
这次以后，我们提交新目录时会多看一眼 `git status --ignored`，遇到“本机有、仓库没有”的情况先用 `git check-ignore -v`，不再只检查构建配置。

## 6. Stage 1 心得：TLV 帧编解码器与粘包状态机

**日期**：2026-04-20

### 6.0 什么是"粘包状态机"？

**粘包**（TCP Sticky Packet）是 TCP 网络编程中的经典问题。TCP 是**流式协议**，它不保证每次 `send()` 的数据会被对方以相同的次数 `recv()` 收到。发送端连续发送两个数据包，在接收端可能：
- 两次分别收到（正常）
- 合并成一次收到（粘包）
- 第一个包收到一半，剩下部分和第二个包合并到达（半包 + 粘包）

**状态机**是一种编程模式：程序处于某个"状态"，收到新数据后根据当前状态决定如何处理，然后转移到下一个状态。

**粘包状态机**就是用状态机模式来解决 TCP 粘包/半包问题的方案。在我们的实现中，程序在两个状态之间循环：
1. **WaitingHeader**：等待凑齐 8 字节帧头（Type + Length）
2. **WaitingPayload**：等待凑齐 Length 字节载荷

每当新数据到达，状态机就尝试推进：如果当前状态所需的数据够了，就解析、转移状态；如果不够，就继续等待下一次数据到达。这样无论数据怎么"粘"、怎么"拆"，都能正确还原出完整的帧。

### 6.1 最难的部分：粘包状态机

Stage 1 的核心任务是实现 `FrameCodec`——TLV 帧的编解码器。其中最难的部分是 **`feed()` 方法的粘包/半包状态机**。这块代码主要是高扬在写，他第一次实现完跑测试就栽在粘包上，下面记录的就是当时遇到的问题。

#### 为什么需要状态机？

TCP 是流式协议，没有消息边界。发送端调用两次 `socket.write()`，接收端可能收到：
- **粘包**：两次发送的数据合并成一次到达
- **半包**：一次发送的数据分多次到达

如果直接在 `readyRead` 信号里解析字节流，代码会变成一团乱麻。所以我们用一个两状态的状态机来处理：

```
WaitingHeader (等待帧头)
    ↓ 收到 8 字节
WaitingPayload (等待载荷)
    ↓ 收到 length 字节
    ↓ emit frameReady
WaitingHeader (循环)
```

#### 实现细节与踩坑

1. **大端序处理**：网络协议统一使用大端序（Big-Endian），但 x86 机器是小端序。必须用 `QDataStream::setByteOrder(QDataStream::BigEndian)` 显式设置，否则解析出的 Type 和 Length 会是乱码。

2. **循环处理粘包**：一次 `feed()` 调用可能包含多个完整帧，所以必须用 `while(true)` 循环，直到数据不足才退出。初版实现漏掉了这个循环，导致粘包时只解析第一个帧，后续帧被丢弃。

3. **状态重置**：每解析完一个完整帧，必须重置状态为 `WaitingHeader`，并清零 `_pendingType` 和 `_pendingLength`。忘记重置会导致下一个帧的帧头被当作载荷读取。

4. **边界条件**：空 payload（如 `kTypeTransferDone`）的帧，Length 为 0，状态机应直接从 `WaitingHeader` 跳到 `emit frameReady`，不进入 `WaitingPayload` 等待。

### 6.2 单测的价值

写单测时发现了一个隐藏 bug：测试"半包"用例时，先喂 4 字节（半个帧头），再喂剩余部分。初版实现在 `WaitingHeader` 状态下没有检查缓冲区大小，直接用 `QDataStream` 读取，导致读取越界。

修复后，5 个测试用例全部通过：
- 单帧编解码
- 粘包（多个帧合并）
- 半包（帧分多次到达）
- 空 payload
- 超大 payload（1MB）

### 6.3 设计决策记录

当时纠结过：为什么用 `enum class State` 而不是 `bool`？

初版用 `bool _waitingHeader` 来表示状态。但考虑到未来可能扩展（如增加"等待校验和"状态），改用 `enum class State` 更具可扩展性，也更符合 SOLID 的开闭原则。

当时纠结过：为什么 `encode()` 是静态方法？

编码过程无状态，只需要输入 type + payload，输出字节流。静态方法避免了不必要的实例化，也方便在没有 FrameCodec 实例的地方直接调用（如 `FrameCodec::encode(kTypeHello, json)`）。

### 6.4 这一阶段留下的经验

这一阶段让我们第一次真正理解了 TCP 只提供字节流，不会帮应用保留消息边界。开始时总觉得“发送一帧就会收到一帧”，直到半包测试稳定复现错误才改掉这个想法。状态机并不复杂，难的是把每次数据不足时该保留什么状态想清楚。这里的五个单测后来也成了修改协议代码时最基本的保护。

## 7. Stage 2 心得：UDP 广播与设备发现

**日期**：2026-04-30

### 7.1 最难的部分：多网卡广播

Stage 2 的核心是实现 `DiscoveryService`——局域网设备发现服务。冯春霖当时写了第一版直接用 `QHostAddress::Broadcast`，结果在自己电脑（同时接着有线和 WiFi）上测试，发现另一台机器怎么也收不到广播。其中最难的部分是 **多网卡环境下的 UDP 广播精确发送**。

#### 为什么需要多网卡处理？

在同时连接有线局域网和 WiFi 的主机上，如果直接使用 `QHostAddress::Broadcast`，Qt 底层可能仅向默认网卡发送，导致其他网段的设备收不到广播。

最后改成：遍历所有激活的网络接口，向每个网卡的广播地址单独发送：

```cpp
const auto interfaces = QNetworkInterface::allInterfaces();
for (const QNetworkInterface &iface : interfaces) {
    // 过滤：必须是激活中的、非回环的、支持广播的物理网卡
    if (!(iface.flags() & QNetworkInterface::IsUp))       continue;
    if (!(iface.flags() & QNetworkInterface::CanBroadcast)) continue;
    if (  iface.flags() & QNetworkInterface::IsLoopBack)  continue;

    for (const QNetworkAddressEntry &entry : iface.addressEntries()) {
        if (entry.ip().protocol() != QAbstractSocket::IPv4Protocol) continue;
        _socket->writeDatagram(data, entry.broadcast(), kDiscoveryPort);
    }
}
```

几个考虑：为什么不直接用 `QHostAddress::Broadcast`？

因为 Qt 的广播行为依赖系统路由表，在双网卡场景下可能只向一个网卡发包。精确遍历网卡虽然代码复杂，但能确保所有网段的设备都能收到广播。

### 7.2 节点表维护：UDP 的"连接"语义

UDP 是无连接协议，没有"断开连接"的通知。所以我们必须自己维护在线状态：

1. **心跳机制**：每 5 秒广播一次 Hello 包，包含设备 ID、名称、IP、端口
2. **超时剔除**：每 3 秒扫描节点表，超过 15 秒未更新的标记为离线
3. **本机过滤**：忽略自己发出的广播（用 device_id 去重）

几个考虑：为什么用 `QHash<QString, PeerInfo>` 而不是 `QList<PeerInfo>`？

- 查找效率：O(1) vs O(n)
- 更新方便：直接用 device_id 作为 key 插入/更新
- 去重简单：同一设备多次广播只保留最新状态

### 7.3 ConfigManager 的单例模式

配置管理器使用 `QML_SINGLETON` 模式，确保全局唯一实例。这样：
- 任何组件都能通过 `ConfigManager.deviceName` 访问配置
- 配置变更自动通知所有监听者（通过信号）
- 配置持久化到 `QSettings`，重启后自动恢复

几个考虑：为什么不用静态方法？

虽然配置管理可以用静态方法实现，但单例模式更符合 Qt 的信号槽机制，也更方便 QML 绑定。

### 7.4 QML 组件设计：required property

`DeviceCard.qml` 使用 `required property` 声明所有属性：

```qml
required property string deviceId
required property string deviceName
required property string ipAddress
required property bool   isOnline
```

当时纠结过：为什么用 required property？

当组件作为 ListView 的 delegate 使用时，QML 引擎会根据名字自动从 model 项里填值。这样就不需要手动写 `model.deviceId` 绑定，代码更简洁，也更不容易出错。

### 7.5 这一阶段留下的经验

设备发现表面上只是发广播，实际麻烦主要来自运行环境：多网卡、回环地址、多个实例共用配置都会影响结果。我们后来把设备 ID、广播目标地址和端口都加入日志，排查效率比只看界面高很多。

这一阶段我们还把 `ConfigManager` 标记成了 `QML_SINGLETON`。当时认为这样就能保证全局唯一，后来才发现它只能保证 QML 引擎里的使用方式，C++ 仍可能创建第二个实例。这个问题直到第二十章才真正解决。

## 8. Stage 3 心得：P2P 文件传输

文件传输这一阶段，冯春霖主要在写 Worker 那一摊事，杜若贤在搞接收确认弹窗和任务卡片，高扬盯着协议帧不要被改坏。下面这些坑基本是协作过程中一起踩出来的。

### 8.1 Worker-Object 模式与跨线程信号

文件收发涉及大量磁盘 I/O 和网络传输，不能阻塞主线程。采用 Worker-Object 模式（继承 QObject + `moveToThread`）而非继承 QThread 重写 `run()`，原因：

- Worker-Object 的事件循环天然支持信号槽连接
- `moveToThread` 后，该对象的槽函数自动在目标线程执行，不需要手动管理线程同步
- 更容易与主线程通信：跨线程信号自动走队列连接

有个坑：`TransferSessionManager` 管理多个 Worker 的生命周期，构造函数中 UDP socket 初始化和信号连接的顺序很重要——先绑定 socket 再连接信号，否则早期数据报会丢失。

### 8.2 本机回环测试：双实例调试

P2P 传输需要至少两个设备，开发阶段没有多台机器，解决办法是同一台机器启动两个实例，通过命令行参数隔离：

```bash
./appGridYard --port 35100 --name "接收端" &
./appGridYard --port 35101 --name "发送端" &
```

`--port` 不仅指定 TCP 监听端口，还自动让 `QSettings` 使用不同的配置文件（通过 `GRIDYARD_CONFIG` 环境变量），避免两个实例共享同一个 deviceId。

### 8.3 QML_ANONYMOUS 与类型注册

`DiscoveryService` 作为 `QML_ANONYMOUS` 注册而非 `QML_ELEMENT`，原因是它不作为独立 QML 类型实例化，而是通过 `AppController.discovery` 属性暴露给 QML。如果用 `QML_ELEMENT`，QML 引擎会尝试独立创建实例，导致与 C++ 端持有的实例不一致。

约定下来：被其他对象持有的子对象（不独立使用），用 `QML_ANONYMOUS`；需要在 QML 中直接创建的类型，用 `QML_ELEMENT`。

### 8.4 Dialog contentItem 与布局冲突

`SettingsDialog` 使用 `Dialog` + `standardButtons` 时，如果把 `ScrollView` 赋值给 `contentItem`，会替换 Dialog 的整个内容区域，导致标题栏和按钮栏的布局计算失效，ScrollView 无法正确获取可用高度，内容溢出且滚动条不出现。

最后的做法：不要用 `contentItem:` 前缀，让 ScrollView 作为 Dialog 的普通子项，由 Dialog 内部布局统一管理标题、内容和按钮区域。

### 8.5 这一阶段留下的经验

文件传输开始后，很多问题已经不能只靠单元测试发现。例如两个实例是否真的使用不同配置、Worker 是否在正确线程执行、QML 拿到的是不是已经初始化的对象，都需要实际启动程序观察。Worker-Object 模式本身没有解决所有并发问题，但至少把耗时收发和主界面分开了，信号槽也让进度更新比较容易接回 UI。

## 9. Stage 3 进阶心得：连接体验与传输完善

### 9.1 QML Dialog 的 contentItem 陷阱

`Dialog` 的 `contentItem` 属性会**替换**整个内容区域，而非向其中添加子项。当 `standardButtons` 存在时，Dialog 内部有自己的布局管理器（标题栏 + 内容区 + 按钮栏）。如果把 `ScrollView` 赋值给 `contentItem`，Dialog 的布局管理器不再控制该区域，导致：

- ScrollView 无法获取正确的 `availableHeight`
- 内容溢出但滚动条不出现
- 标题栏和按钮栏的布局也被破坏

最后的做法：去掉 `contentItem:` 前缀，让 ScrollView 作为 Dialog 的普通子项，由 Dialog 内部布局统一管理。

约定下来：Dialog 中需要滚动内容时，永远不要用 `contentItem:` 包裹 ScrollView。

### 9.2 接收路径的传递链路

文件接收路径的配置涉及多个组件，需要理清传递链路：

```
ConfigManager (QSettings 持久化)
    ↓ _config->receivePath()
TransferSessionManager (init 时持有 _config)
    ↓ worker->setReceivePath(path)
FileReceiverWorker (acceptTransfer 时使用 _receivePath)
    ↓ _file.setFileName(_receivePath + "/" + _fileName)
```

有个坑：最初 `FileReceiverWorker::acceptTransfer()` 硬编码了 `QDir::homePath() + "/GridYard"`，没有使用 `ConfigManager` 的配置。原因是 Worker 在独立线程运行，不能直接访问 ConfigManager。解决办法是通过 `setReceivePath()` 方法在创建会话时由 `TransferSessionManager` 注入路径。

### 9.3 传输完成信号的接收端处理

发送端的 `transferFinished` 信号在 `createSendSession` 中已连接，但接收端的 `transferFinished` 信号最初没有连接。原因是接收会话的 Worker 由 `P2pServer` 创建，通过 `onTransferRequestReceived` 回调传入 `TransferSessionManager`，需要在该回调中连接信号。

当时的做法：接收完成后发射 `transferCompleted(sessionId, fileName, filePath)` 信号，QML 端弹出对话框询问是否打开文件夹。通过 `QDesktopServices::openUrl()` 打开系统文件管理器。

### 9.4 本机 IP 获取与刷新

`QNetworkInterface::allAddresses()` 返回所有网络接口地址，包括回环地址和 IPv6 地址。获取本机 IPv4 地址需要过滤：

```cpp
for (const QHostAddress &addr : QNetworkInterface::allAddresses()) {
    if (addr.protocol() == QAbstractSocket::IPv4Protocol
        && !addr.isLoopback()) {
        return addr.toString();
    }
}
```

要留意：多网卡环境下可能返回不同的 IP，`refreshLocalIp()` 方法允许在运行时重新获取。

### 9.5 这一阶段留下的经验

这一轮修改看起来都是小功能，但暴露出一个共同问题：数据经过的对象一多，很容易只改链路的一半。接收路径从设置页传到接收 Worker，完成信号从 Worker 回到 QML，少接一个环节都不会在编译时报错。后来再改类似功能时，我们会先画出“配置从哪里来、由谁保存、最后在哪里使用”的简单链路，再开始改代码。

## 10. Stage 4 心得：多文件传输与 SHA-256 校验

**日期**：2026-05-26

### 10.1 DirSerializer 设计决策

`DirSerializer` 是一个纯静态工具类，不继承 QObject，不需要暴露给 QML。设计为 `gy` 命名空间下的独立类：

- 当时纠结过：为什么用结构体 `FileItem` 而不是已有的 `FileEntry`？

  `FileEntry` 是 Q_GADGET，设计用于 QML 属性反射，带 Q_OBJECT 开销。`FileItem` 是纯 C++ 结构体，仅在 C++ 层使用，不需要元对象系统。遵循 YAGNI 原则，不为不需要的功能增加复杂度。

- **SHA-256 计算时机**

  在 `serialize()` 遍历目录时同步计算。虽然大文件会阻塞，但 `DirSerializer` 在 Worker 线程中调用，不会卡 UI。如果未来需要异步计算，可以单独抽成后台任务。

### 10.2 多文件传输的协议复用

Stage 3 的 chunk 元数据格式（20 字节：fileIndex + chunkOffset + chunkSize + isLastChunk）已经预留了 `fileIndex` 字段。Stage 4 只需：

1. 发送端：按 `_fileList` 顺序逐个文件发送，每个文件的 chunk 用相同的 `fileIndex`
2. 接收端：收到 `isLastChunk=1` 后，发送 `kTypeChunkAck` 并切换到下一个文件
3. 发送端：收到 `kTypeChunkAck` 后，校验通过则打开下一个文件继续发送

关键的点：`kTypeTransferDone` 帧（0x0302）在 Stage 1 已定义但未使用，Stage 4 用它标记所有文件传输完成。

### 10.3 目录结构还原

接收端按 `relative_path` 中的路径分隔符创建子目录：

```cpp
QString dirPath = _receivePath + "/" + QFileInfo(relativePath).path();
QDir().mkpath(dirPath);
```

有个坑：`QFileInfo("subdir/file.txt").path()` 返回 `"subdir"`，但 `QFileInfo("file.txt").path()` 返回 `"."`。需要先检查 `relativePath` 是否包含目录分隔符。

### 10.4 SHA-256 校验流程

1. **发送端**：`DirSerializer::computeSha256()` 在序列化时计算，结果存入 `FileItem.sha256`
2. **握手请求**：`kTypeTransferReq` 的 JSON 中每个文件携带 `sha256` 字段
3. **接收端**：文件写入完成后，用 `QCryptographicHash::Sha256` 重新计算，与发送方的 hash 对比
4. **确认帧**：`kTypeChunkAck` 携带 `verified` 字段，校验失败时携带 `error_msg`

要留意：SHA-256 计算必须在文件关闭前完成，否则读取不完整。

### 10.5 这一阶段留下的经验

Stage 3 里提前保留的 `fileIndex` 在这里派上了用场，避免重新设计 chunk 帧。但这也提醒我们，预留字段只有和后续需求对应时才有价值，不能为了“以后可能有用”无限加字段。`DirSerializer` 没有继承 `QObject`，也是因为它只做遍历和哈希计算；不是所有类都需要信号槽和 QML 暴露。

## 11. Stage 4.4 心得：异常断网处理

**日期**：2026-05-31

### 11.1 难点分析

难点 1：如何检测对端崩溃？

TCP 的 `disconnected` 信号只能检测到正常断开（调用 `disconnectFromHost()`）。如果对端进程崩溃（`kill -9`），TCP 连接不会立即断开，而是保持半开状态（Half-Open）。此时：
- 发送数据不会报错（数据在内核缓冲区）
- 不会触发 `disconnected` 信号
- 只有等到 TCP keepalive 超时（默认 2 小时）才会断开

最后改成：应用层超时检测。每次收到数据时重置定时器，如果 30 秒没有收到任何数据，认为连接已死。

难点 2：不完整文件的清理

传输中断时，接收端可能已经写入了部分文件数据。如果不清理，下次传输同名文件会出现：
- 文件大小不一致
- SHA-256 校验失败
- 用户困惑

最后改成：在 `cleanup()` 方法中，关闭文件后立即删除不完整文件。

### 11.2 设计决策

当时纠结过：为什么用 QTimer 而不是 TCP keepalive？

1. **TCP keepalive 默认超时太长**（2 小时），需要修改系统参数
2. **应用层超时更灵活**：可以根据业务需求调整超时时间
3. **QTimer 跨平台**：不需要关心不同操作系统的 TCP keepalive 实现

当时纠结过：为什么超时时间选择 30 秒？

1. **太短（< 10s）**：网络抖动会误判
2. **太长（> 60s）**：用户体验差，长时间无响应
3. **30 秒**：平衡了可靠性和用户体验，符合验收标准"30s 内检测到"

当时纠结过：为什么在 cleanup() 中删除文件而不是保留？

1. **不完整文件没有价值**：SHA-256 校验会失败，无法使用
2. **避免磁盘空间浪费**：大文件传输中断会留下 GB 级垃圾
3. **用户期望**：要么完整接收，要么不要留下半成品

### 11.3 实现细节

**超时定时器的生命周期**：
```
构造 -> acceptTransfer() 启动 -> 每次 onReadyRead() 重置 -> 超时/完成/取消 时停止
```

**资源清理的时机**：
1. 超时触发 -> cleanup() -> emit transferFinished(false, "传输超时")
2. 连接断开 -> cleanup() -> emit transferFinished(false, "连接断开")
3. 用户取消 -> rejectTransfer() -> _socket->disconnectFromHost() -> 触发 onDisconnected() -> cleanup()

### 11.4 这一阶段留下的经验

最开始我们只处理正常完成和用户取消，直到手动结束其中一个进程，才发现另一端会长时间停在传输中。增加超时并不难，真正容易出错的是清理路径：断开、超时、取消和析构都可能调用清理函数。因此 `cleanup()` 必须允许重复调用，并统一关闭文件、停止定时器和处理未完成文件。

## 12. Stage 4.5 心得：大文件吞吐量优化

**日期**：2026-06-02

### 12.1 难点分析

难点 1：如何找到性能瓶颈？

大文件传输涉及多个环节：
- 发送端：文件读取 -> 内存缓冲 -> TCP 发送
- 接收端：TCP 接收 -> 内存缓冲 -> 文件写入
- 中间：TLV 编解码、信号槽、UI 更新

**瓶颈可能在**：
1. 磁盘 I/O（读写速度）
2. 网络带宽（千兆 = 125 MB/s）
3. CPU（编解码、SHA-256 计算）
4. Qt 事件循环（信号槽开销）

难点 2：chunk 大小的选择

- **太小（< 1MB）**：信号槽开销大，TCP 包头占比高
- **太大（> 16MB）**：内存占用高，单次写入可能阻塞
- **8MB**：平衡了内存占用和吞吐量

### 12.2 设计决策

当时纠结过：为什么调整 chunk 大小为 8MB？

1. **减少系统调用次数**：8MB chunk 意味着 5GB 文件只需 640 次 read/write
2. **匹配 TCP 窗口**：现代 TCP 窗口大小通常 4-16MB，8MB 是合理选择
3. **内存占用可控**：每个 Worker 最多占用 8MB 缓冲区，不会 OOM

当时纠结过：为什么调大 socket buffer 到 4MB？

1. **减少 TCP 窗口收缩**：默认 buffer（通常 128KB）在高带宽下会成为瓶颈
2. **匹配 chunk 大小**：4MB buffer 可以缓冲半个 chunk，减少等待
3. **操作系统限制**：Linux 默认最大 buffer 通常 208KB，需要显式调大

当时纠结过：为什么减少进度信号发射频率？

1. **信号槽有开销**：每次发射需要 Qt 事件循环处理
2. **UI 更新不需要太频繁**：每 32MB 更新一次（约 0.25 秒）足够
3. **减少 CPU 占用**：5GB 文件从 640 次信号减少到 160 次

### 12.3 实现细节

**chunk 大小的定义位置**：
```cpp
// file_sender_worker.h
static constexpr qint64 kChunkSize = 8 * 1024 * 1024;  // 8MB
```

**socket buffer 设置时机**：
```cpp
// 连接成功后设置
_socket->setSocketOption(QAbstractSocket::SendBufferSizeSocketOption, 4 * 1024 * 1024);
_socket->setSocketOption(QAbstractSocket::ReceiveBufferSizeSocketOption, 4 * 1024 * 1024);
```

**进度信号发射逻辑**：
```cpp
// 每 4 个 chunk 发射一次（约 32MB）
static int chunkCount = 0;
if (++chunkCount % 4 == 0 || isLastChunk == 1) {
    emit progressChanged(_bytesSent, _totalBytes);
}
```

### 12.4 性能预期

| 文件大小 | chunk 数量 | 信号发射次数 | 预期耗时（千兆） |
|----------|-----------|-------------|-----------------|
| 100 MB   | 13        | 4           | ~1 秒           |
| 1 GB     | 128       | 33          | ~8 秒           |
| 5 GB     | 640       | 161         | ~40 秒          |

**理论吞吐量**：千兆网络 125 MB/s，实际受限于磁盘 I/O 和 CPU，预期 80-100 MB/s。

### 12.5 这一阶段留下的经验

这次优化主要靠减少无意义的频繁操作，而不是换复杂算法。调大 chunk 后系统调用次数下降，减少进度信号后 UI 线程也轻了一些。不过表格里的速度只是目标值，实际结果仍会受到磁盘、网卡和系统缓存影响。以后做性能优化时，应该保留测试环境和实测数据，不能只根据理论带宽判断。

## 13. AppImage 打包踩坑记录

**日期**：2026-06-05

Stage 4 完成后，高扬负责把 GridYard 打成 Linux AppImage，方便在没有装 Qt 的机器上跑。他前后踩了五六个坑才把第一个能跑的包做出来，下面是完整记录。

### 13.1 背景

Stage 4 完成后，尝试将 GridYard 打包为 Linux AppImage 格式，实现单文件分发、免安装运行。

### 13.2 难点分析

难点 1：linuxdeploy strip 报错

现象：linuxdeploy 在收集依赖库时，调用 strip 命令失败：
```
ERROR: Strip call failed: unknown type [0x13] section '.relr.dyn'
```

原因：linuxdeploy 内置的 strip 工具版本过旧，无法识别新版 glibc（2.38+）引入的 `.relr.dyn` 段。这是 GNU binutils 的一个已知兼容性问题。

影响：strip 失败不影响库的功能，只影响符号表大小。可以安全忽略。

最后的做法：忽略 strip 错误，继续打包流程。最终 AppImage 可以正常运行。

难点 2：Qt6 插件和 QML 模块缺失

现象：AppImage 打包成功，但启动时崩溃（核心转储）。

原因：linuxdeploy 只收集共享库（`.so` 文件），不会自动收集 Qt6 插件和 QML 模块。GridYard 使用 QML 架构，需要：
- `/usr/lib/qt6/plugins/platforms/` — 平台插件（xcb/wayland）
- `/usr/lib/qt6/plugins/imageformats/` — 图片格式插件
- `/usr/lib/qt6/qml/QtQuick/` — QML 运行时模块
- `/usr/lib/qt6/qml/QtQuick.Controls/` — QML 控件库

最后的做法：手动复制整个 `/usr/lib/qt6/plugins` 和 `/usr/lib/qt6/qml` 目录到 AppDir。

难点 3：appimagetool 的 desktop 文件位置要求

现象：`Desktop file not found, aborting`

原因：appimagetool 要求 desktop 文件在 AppDir 根目录，而不是 `usr/share/applications/`。

最后的做法：将 desktop 文件复制到 AppDir 根目录（保留 `usr/share/applications/` 中的副本）。

难点 4：appimagetool 架构检测失败

现象：`More than one architectures were found`

原因：appimagetool 无法自动检测目标架构，可能因为 AppDir 中混合了不同架构的库。

最后的做法：显式设置环境变量 `ARCH=x86_64`。

难点 5：图标文件查找路径

现象：`gridyard{.png,.svg,.xpm} defined in desktop file but not found`

原因：appimagetool 在 AppDir 根目录查找 desktop 文件中定义的图标，而不是 `usr/share/icons/`。

最后的做法：将图标文件复制到 AppDir 根目录。

### 13.3 最终打包方案

经过多次尝试，确定了以下打包流程：

1. **构建项目**：Release 模式编译
2. **准备 AppDir**：创建目录结构，复制可执行文件和资源
3. **linuxdeploy 收集依赖**：自动收集系统共享库（忽略 strip 错误）
4. **手动补充 Qt6 组件**：复制 plugins 和 qml 目录
5. **创建 AppRun 脚本**：设置环境变量，启动应用
6. **appimagetool 打包**：生成最终 AppImage

**最终产物**：`GridYard-x86_64.AppImage`（92MB）

### 13.4 AppRun 脚本设计

AppRun 是 AppImage 的入口脚本，负责设置运行时环境：

```bash
#!/bin/bash
SELF=$(readlink -f "$0")
HERE=${SELF%/*}
export PATH="${HERE}/usr/bin/:${PATH:+:$PATH}"
export LD_LIBRARY_PATH="${HERE}/usr/lib/:${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export QT_PLUGIN_PATH="${HERE}/usr/lib/qt6/plugins/${QT_PLUGIN_PATH:+:$QT_PLUGIN_PATH}"
export QML2_IMPORT_PATH="${HERE}/usr/lib/qt6/qml/${QML2_IMPORT_PATH:+:$QML2_IMPORT_PATH}"
exec "${HERE}/usr/bin/appGridYard" "$@"
```

**关键环境变量**：
- `LD_LIBRARY_PATH`：让应用优先加载 AppDir 内的共享库
- `QT_PLUGIN_PATH`：告诉 Qt 去哪里找平台插件
- `QML2_IMPORT_PATH`：告诉 QML 引擎去哪里找 QML 模块

### 13.5 打包后才明白的事

第一次看到 AppImage 文件生成成功时，我们以为打包已经结束，实际运行才发现缺 QML 模块、平台插件和图标。打包工具显示成功，只能说明产物被生成，不能说明产物能在目标环境运行。之后每次调整打包内容，都必须重新启动产物检查，而不是只看命令退出码。

目前手动复制整个 Qt 插件和 QML 目录虽然能运行，但会让包体积达到 92MB，也可能带入不需要的组件。这是当前为了先完成可运行版本做的取舍，后续应该按实际依赖精简。

## 14. 单机多实例测试与设备发现 Bug 修复

**日期**：2026-06-07

### 14.1 问题背景

GridYard 是局域网 P2P 传输软件，测试时至少需要两台设备。但开发阶段手边只有一台电脑，所以我们通过命令行参数启动两个实例来模拟：

```bash
./build-ninja/client/appGridYard --port 35100 --name "接收端" &
./build-ninja/client/appGridYard --port 35101 --name "发送端" &
```

### 14.2 踩坑过程

两个实例都能启动，但界面一直卡在"正在搜索设备..."，互相看不到对方。

一开始以为是 UDP 广播的问题，检查了防火墙、网卡配置，都没问题。后来加了调试日志才发现真相——两个实例的 deviceId 竟然一模一样！

```
DiscoveryService: 发送广播，deviceId: "0f5bb927-..." name: "接收端"
DiscoveryService: 发送广播，deviceId: "0f5bb927-..." name: "发送端"
DiscoveryService: 忽略自己的广播，deviceId: "0f5bb927-..."
```

### 14.3 原因分析

追查下去，问题出在 `ConfigManager` 的 `QSettings` 初始化上。

`main.cpp` 里已经做了处理：指定 `--port` 时会设置 `GRIDYARD_CONFIG` 环境变量，指向不同的配置文件。但 `ConfigManager` 构造函数里写的是：

```cpp
QSettings settings(configPath.isEmpty() ? QSettings::IniFormat : QSettings::IniFormat,
                   configPath.isEmpty() ? QSettings::UserScope : QSettings::SystemScope,
                   configPath.isEmpty() ? QString() : configPath);
```

看起来没问题对吧？但 `QSettings::SystemScope` + 自定义路径这个组合，Qt 的行为是去系统级配置目录找文件，而不是直接用我们指定的路径。结果两个实例读的是同一个配置文件，生成了相同的 deviceId。

### 14.4 解决办法

最简单的办法：当有自定义路径时，直接用文件路径构造 QSettings，别用什么 Scope：

```cpp
QString configPath = qEnvironmentVariable("GRIDYARD_CONFIG");
QSettings settings(configPath.isEmpty() ? QSettings() : QSettings(configPath, QSettings::IniFormat));
```

同时在 `ConfigManager` 里所有用到 `QSettings` 的地方都统一改成这种写法（`setDeviceName`、`setReceivePath`、`setTcpPort`、`ensureDeviceId`）。

另外还顺手优化了 UDP 绑定逻辑——如果默认端口 45678 被占用，就绑定到随机端口，然后广播时同时向两个端口发，确保绑到备用端口的实例也能收到。

### 14.5 这次排查为什么绕了很久

界面表现是“发现不到设备”，所以我们一开始一直查 UDP 和防火墙。真正的问题却发生在更前面的配置读取：两个实例拿到了同一个设备 ID，然后都把对方当成自己忽略了。这个经历让我们后面排查网络问题时，不再只盯着 socket，而是先核对协议里实际发出的设备 ID、IP 和端口。

## 15. 拖拽文件直接崩溃——QML_SINGLETON 的坑

**日期**：2026-06-07

### 15.1 问题现象

设备发现修好后，测试拖拽文件功能，程序直接段错误退出：

```
[TransferSession] 创建发送会话
[TransferSession] 目标设备ID: "da6de09d-..."
segmentation fault (core dumped)
```

### 15.2 原因分析

这个问题的根源在于 `TransferSessionManager` 被声明成了 `QML_SINGLETON`。

我们原本的设计是：`AppController` 在构造函数里创建 `TransferSessionManager` 并调用 `init()` 注入依赖。但 `QML_SINGLETON` 会让 QML 引擎自动创建一个新实例——这个实例从来没调用过 `init()`，所以 `_discovery`、`_config`、`_p2pServer` 全是空指针。

QML 里调用 `TransferSessionManager.createSendSession()` 时，用的就是这个没初始化的实例，一访问空指针就崩了。

### 15.3 解决办法

既然 `TransferSessionManager` 需要初始化才能用，就不应该让 QML 引擎自动创建。所以：

1. 去掉 `TransferSessionManager` 的 `QML_ELEMENT` 和 `QML_SINGLETON`
2. 在 `AppController` 里加一个 `transfer` 属性，把已经初始化好的实例暴露给 QML
3. QML 里全部改成 `AppController.transfer.xxx`

### 15.4 后来的取舍

这次之后，我们把 `AppController` 作为 QML 访问业务对象的主要入口。需要依赖注入的对象由 C++ 创建和初始化，再通过属性暴露给 QML，而不是让 QML 引擎自行创建。这样多写了一层 `AppController.transfer`，但对象生命周期和依赖关系更明确。

重构后又出现了部分 QML 文件仍引用旧类型的问题，说明这类修改不能只靠编译验证。QML 引用很多是在运行时解析的，改名后必须全局搜索并实际启动界面。

## 16. TCP 连接失败——代理惹的祸

**日期**：2026-06-08

### 16.1 问题现象

拖拽文件不崩了，但传输一直卡住。看日志：

```
[FileSender] 正在连接到 "10.243.8.49" : 35100
[FileSender] 连接失败: "对于这个操作代理类型是无效的"
```

### 16.2 原因

电脑上配了系统代理，QTcpSocket 默认会走代理。局域网内的 TCP 直连被代理拦截，直接报错。

### 16.3 解决办法

在 `FileSenderWorker` 构造函数里加一行禁用代理：

```cpp
QNetworkProxy noProxy;
noProxy.setType(QNetworkProxy::NoProxy);
_socket->setProxy(noProxy);
```

### 16.4 为什么这个问题容易漏掉

开发机器平时开着系统代理，但我们一开始只在浏览器场景里考虑代理，没有想到 `QTcpSocket` 也会读取系统代理配置。UDP 发现能正常工作又让我们误以为网络链路没有问题。后来在 P2P 的 TCP socket 上明确设置 `NoProxy`，避免局域网直连受用户代理设置影响。

## 18. ListView 绑定与 Dialog 按钮踩坑

**日期**：2026-06-08

这一组坑主要是杜若贤在调，冯春霖帮忙看 Qt6 文档。前两个是 ListView delegate 的绑定问题，第三个是文件选择器在 KDE 下不像原生样式。

### 18.1 TransferPanel 的 modelData 问题

传输任务面板显示不出内容，日志一直报 `modelData is not defined`。

原来 Qt6 里 ListView delegate 绑定 QVariantList 的方式变了。Qt5 用 `modelData.xxx`，Qt6 要改成 `model.xxx`。这个变化很隐蔽，编译不报错，运行时才出问题。

**修复**：把 `modelData.sessionId` 改成 `model.sessionId`，其他字段同理。

### 18.2 Dialog 按钮事件处理

接收完成弹窗有两个按钮（"打开"和"确定"），但不管点哪个都会打开文件夹。

原因是 Qt 里 `Dialog.Open | Dialog.Ok` 两个按钮都会触发 `accepted` 信号。`Dialog.Open` 点了是 accepted，`Dialog.Ok` 点了也是 accepted，没法区分。

试了 `onButtonClicked` 信号，发现 Qt6 的 Dialog 没有这个信号。最后改成 `onAccepted` + `onRejected` 的组合：`Dialog.Open` 触发 accepted，`Dialog.Ok` 触发 rejected。

### 18.3 系统原生文件选择器

第一版直接使用 Qt 的 `FileDialog`。为了让窗口在 KDE 和 GNOME 下更像系统样式，我们后来尝试在 C++ 端启动外部选择器：KDE 调 `kdialog`，其他环境调 `zenity`。

这个方案当时能解决测试机器上的样式问题，但留下了依赖外部命令、同步等待进程、取消后可能再次弹窗等问题。到第二十一章重新排查后，我们删除了这套实现，改为让 Qt 通过桌面门户调用系统选择器。

这段经历比较典型：为了尽快解决界面问题先做了一个能运行的方案，后面在更多环境测试时才发现设计不够稳。记录旧方案仍然有价值，但最终实现应以第二十一章为准。

## 19. 设备名称更新不及时——信号连接的遗漏

**日期**：2026-06-09

### 19.1 问题

用户修改设备名称后，其他设备仍然显示旧名称，需要等待最多 5 秒（广播周期）才能更新。点击刷新按钮也没有效果。

### 19.2 原因分析

设备发现流程是这样的：

1. `DiscoveryService` 每 5 秒发送一次 UDP 广播（Hello 包）
2. Hello 包包含 `device_id`、`device_name`、`tcp_port` 等信息
3. 其他设备收到 Hello 包后更新节点表

问题在于：当用户在 UI 中修改设备名称时，`ConfigManager` 会发出 `deviceNameChanged` 信号，但 `DiscoveryService` **没有监听这个信号**。所以名称变化后，`DiscoveryService` 仍然使用旧的 `_config->deviceName()` 构建 Hello 包，直到下一个广播周期才会发送新名称。

### 19.3 解决方案

在 `DiscoveryService` 构造函数中添加信号连接：

```cpp
// 设备名称变化时立即广播，让其他设备尽快更新
connect(_config, &ConfigManager::deviceNameChanged,
        this,    &DiscoveryService::sendHelloPacket);
```

这样当设备名称变化时，`DiscoveryService` 会立即发送一次广播，其他设备可以马上更新显示。

### 19.4 当时还没有找到的根因

加上信号连接后，名称更新问题仍然没有完全解决。日志里能看到 QML 修改了名称，却看不到 `DiscoveryService` 立即广播。继续排查后才发现，QML 和 `DiscoveryService` 使用的并不是同一个 `ConfigManager` 实例。也就是说，这一章的修改方向没有错，但只修到了表面问题，真正的根因记录在下一章。

## 20. QML 和 C++ 各自拿到了一个 ConfigManager

**日期**：2026-06-09

### 20.1 问题

设备名称更新的问题修了几次仍然存在：用户在界面上修改名称后，其他设备收不到更新，发送文件时显示的还是旧名称。信号连接代码看起来没有问题，所以一开始很容易怀疑是 QML 没有触发 setter，或者 UDP 广播没有发出去。

当时的信号连接是：
```cpp
connect(_config, &ConfigManager::deviceNameChanged,
        this,    &DiscoveryService::sendHelloPacket);
```

### 20.2 排查过程

我们先在几个关键位置加日志：
- `ConfigManager::setDeviceName()` — 确认是否被调用
- `DiscoveryService::sendHelloPacket()` — 确认是否发送广播
- `handleHelloPacket()` — 确认收到的设备名称
- `updatePeer()` — 确认是否更新设备信息

日志显示：
```
ConfigManager::setDeviceName() 被调用，新名称: "设备3" 当前名称: "设备A"
ConfigManager: deviceNameChanged 信号已发射
```

但是没有看到 `sendHelloPacket()` 被调用。继续把对象地址也打印出来后，才发现 setter 发信号的对象和 `DiscoveryService` 保存的 `_config` 地址不同。顺着创建路径检查，最终找到下面两处：

```cpp
// AppController 构造函数
AppController::AppController(QObject *parent)
    : _config{ConfigManager::create(nullptr, nullptr)}  // 创建实例 A
    , _discovery{new DiscoveryService{_config, this}}   // 使用实例 A
```

```cpp
// ConfigManager 头文件
QML_SINGLETON  // QML 会创建实例 B
```

`ConfigManager` 被标记为 `QML_SINGLETON`，QML 引擎会创建一个实例；`AppController` 又通过 `ConfigManager::create()` 获取实例。如果工厂函数每次都创建新对象，两边就不会指向同一个配置管理器。

当 QML 中修改 `ConfigManager.deviceName` 时，访问的是实例 B。但 `DiscoveryService` 中的 `_config` 指针指向的是实例 A，信号连接自然失效。

### 20.3 解决方案

我们修改 `ConfigManager::create()`，用静态指针保证所有入口返回同一个实例：

```cpp
// 静态成员变量定义
QPointer<ConfigManager> ConfigManager::s_instance;

ConfigManager *ConfigManager::create(QQmlEngine *engine, QJSEngine *)
{
    Q_UNUSED(engine);
    // 使用静态变量确保全局只有一个实例
    if (!s_instance) {
        s_instance = new ConfigManager{};
        qDebug() << "ConfigManager: 创建全局实例";
    }
    return s_instance;
}
```

同时在析构函数中清除静态指针，避免悬空指针：

```cpp
ConfigManager::~ConfigManager()
{
    if (s_instance == this) {
        s_instance = nullptr;
        qDebug() << "ConfigManager: 全局实例已销毁";
    }
}
```

### 20.4 测试代码的适配

单例模式引入后，测试代码遇到了问题。`test_discovery` 需要创建多个独立的 `ConfigManager` 实例来测试配置隔离，但单例模式阻止了这一点。

最后使用 `friend class` 允许测试代码访问私有构造函数：

```cpp
class ConfigManager : public QObject {
    // ...
private:
    explicit ConfigManager(QObject *parent = nullptr);
    
    // 允许测试代码访问私有构造函数
    friend class TestDiscovery;
    friend class TestIntegration;
};
```

测试代码直接创建实例，不使用 `create()` 方法：

```cpp
// 测试代码
qputenv("GRIDYARD_CONFIG", config1Path.toUtf8());
_config1 = new ConfigManager{};  // 直接创建，绕过单例

qputenv("GRIDYARD_CONFIG", config2Path.toUtf8());
_config2 = new ConfigManager{};  // 创建独立实例
```

### 20.5 本机回环测试的注意事项

在单机上测试两个实例时，必须指定不同的端口：

```bash
# 正确的启动方式
./build-ninja/client/appGridYard --port 35100 --name "设备A" &
./build-ninja/client/appGridYard --port 35101 --name "设备B" &
```

指定不同端口后，程序会自动使用不同的配置文件：
- 端口 35100 → `/tmp/gridyard_config_35100.ini`
- 端口 35101 → `/tmp/gridyard_config_35101.ini`

这样每个实例会有不同的 `deviceId`，可以互相发现。

### 20.6 这次真正有用的排查方法

这次最有效的不是继续检查 `connect()` 写法，而是打印信号发送对象和接收模块持有对象的地址。两个地址不同后，问题一下从“信号为什么失效”变成了“对象在哪里被重复创建”。

另外，单例修复也给测试带来了新问题：部分测试需要两个独立配置实例。最后通过 `friend class` 让测试直接调用私有构造函数，这是为了保留生产代码的创建约束，同时满足测试隔离，不是所有类都需要照搬这种写法。

## 21. KDE 原生文件选择器与桌面门户

**日期**：2026-06-09

### 21.1 问题

系统默认文件管理器是 Dolphin，但点击设备选择发送文件时，程序显示的是 Qt 默认文件选择窗口，界面风格和 KDE 不一致。

我们一开始把“默认文件管理器”和“文件选择窗口”当成了同一个东西，以为系统默认是 Dolphin，应用就应该自动显示 Dolphin 风格。实际查资料和系统组件后才明白，Dolphin 负责浏览和管理文件，应用里的文件选择窗口由 Qt 平台主题或桌面门户提供。

### 21.2 原因分析

按照第十八章的临时方案，程序会根据桌面环境直接启动 `kdialog` 或 `zenity`，再读取命令输出的文件路径。实际检查开发机时发现，Dolphin 已安装，但 `kdialog` 并没有安装，所以旧方案只能退回 Qt 默认窗口。

继续检查后还发现这套实现有几个问题：

1. 系统可能安装了 Dolphin，但没有安装 `kdialog`
2. 外部进程同步等待会阻塞程序界面
3. 用户取消选择和系统选择器不可用都返回空列表，程序无法区分，可能再次弹出 Qt 对话框

开发机已经安装 `xdg-desktop-portal-kde` 和 Qt 的 `xdgdesktopportal` 平台主题插件，因此可以直接让 Qt 走桌面门户，不需要额外启动命令。

### 21.3 解决方案

程序在创建 `QGuiApplication` 前检查桌面环境。检测到 KDE 且用户没有显式设置 `QT_QPA_PLATFORMTHEME` 时，启用 `xdgdesktopportal`：

```cpp
const QString desktop = qEnvironmentVariable("XDG_CURRENT_DESKTOP");
if (qEnvironmentVariableIsEmpty("QT_QPA_PLATFORMTHEME")
    && desktop.contains("KDE", Qt::CaseInsensitive)) {
    qputenv("QT_QPA_PLATFORMTHEME", "xdgdesktopportal");
}
```

QML 继续使用标准 `FileDialog`，Qt 会通过桌面门户调用 KDE 原生文件选择窗口。原来的 `openNativeFileDialog()`、`kdialog` 和 `zenity` 调用全部删除。

### 21.4 为什么最后选桌面门户

调用 `kdialog` 的方案代码直观，但把桌面环境判断、外部命令是否安装、进程输出解析都留给了应用。桌面门户本来就是用来处理这类桌面集成的，由系统选择 KDE 对应的后端更合适。

实现时还有两个细节：平台主题必须在创建 `QGuiApplication` 前设置；如果用户已经设置 `QT_QPA_PLATFORMTHEME`，程序不能覆盖。最终代码只在 KDE 且变量为空时补默认值，其他环境继续使用原有配置。

## 22. 设备列表改名了，传输弹窗还是主机名

**日期**：2026-06-10

### 22.1 问题

修改设备别名后，其他设备的在线列表会马上显示新名称，但发送文件时，接收确认弹窗里显示的发送方仍然是系统主机名。

一开始我们以为名称广播还有遗漏，但对比两条数据链后发现，设备发现和文件传输根本没有使用同一个名称来源：

- UDP 发现广播使用 `ConfigManager::deviceName()`
- TCP 传输请求使用 `QHostInfo::localHostName()`

所以设备列表更新是正常的，只有传输请求一直绕过用户设置。

### 22.2 修改方式

创建发送会话时，`TransferSessionManager` 从 `ConfigManager` 读取当前设备别名，再把它作为参数传给工作线程中的 `FileSenderWorker`。Worker 构建传输请求时直接使用这个值。

这里没有让 Worker 自己访问 `ConfigManager`，因为 Worker 已经移动到后台线程。由会话管理器在启动线程前读取配置并传入，线程边界和依赖关系更清楚。

### 22.3 测试补充

原来的文件传输测试只确认程序不崩溃，没有检查握手请求里的发送方名称。这次让测试接收端实际读取传输请求，并断言发送方是测试设置的别名。以后如果又改回主机名，测试会直接失败。

## 23. 从"点击就发送"改成设备会话页

**日期**：2026-06-10

### 23.1 原来的操作为什么不顺手

原界面左侧是在线设备，右侧是全部传输任务。点击设备会立刻弹出文件选择器，这条路径虽然短，但点击动作同时承担了“选择设备”和“开始发送”两个意思。用户只是想查看设备时也会被要求选文件，而且多个设备的任务全部混在右侧，很难看出文件到底发给了谁。

### 23.2 这次采用的结构

我们保留左侧设备列表，把右侧改成当前设备的传输会话页。点击设备只负责切换当前会话，真正发送文件由右侧按钮或拖拽触发。会话页顶部显示设备别名、IP 和在线状态，中间只显示该设备相关任务，底部提供发送文件和发送文件夹入口。

第一版没有给每台设备创建独立系统窗口。独立窗口需要额外处理窗口生命周期、重复打开和状态同步，目前先把单主窗口内的会话切换做稳定。

### 23.3 为什么先改协议数据再改界面

发送任务本来保存了目标设备 ID，但接收任务只有发送方名称。同名设备出现时，仅靠名称无法把接收任务归到正确会话。因此传输请求增加了 `sender_device_id`，收发任务统一记录对端设备 ID，再由 QML 按 ID 筛选。

这次改版再次说明，界面想展示清楚，底层数据必须先能表达清楚。直接在 QML 中按名称猜测归属，短期能显示，后面一定会遇到同名和改名问题。

### 24.1 原来的类图已经跟不上代码

发现问题后没有立刻新建一堆目录和接口。现在文件传输链路已经能运行，如果只为了让目录看起来符合四层就拆 Worker，很容易把线程、信号和资源释放弄乱。

## 25. 传输记录不显示——QML 属性绑定的坑

**日期**：2026-06-11

### 25.1 问题

设备会话页实现了按设备筛选传输记录，但实际运行时，右侧会话区一直显示"还没有传输记录"，即使已经有传输任务完成。

检查 `TransferSessionManager` 的 `sessions` 属性，数据确实存在；检查 `sessionsForCurrentDevice()` 函数逻辑，筛选条件也没有问题。但界面就是不更新。

### 25.2 原因分析

问题出在 QML 的 model 绑定方式上。原来的代码是：

```qml
model: tw_deviceSessionView.sessionsForCurrentDevice()
```

这是一次函数调用。QML 在组件初始化时执行一次，拿到返回值作为 model。之后即使 `AppController.transfer.sessions` 变化，这个函数也不会重新执行——因为 QML 不知道函数内部依赖了哪些属性。

QML 的属性绑定是响应式的，但函数调用不是。函数内部读取了 `AppController.transfer.sessions`，QML 的绑定追踪机制无法穿透函数边界，所以 sessions 变化时，model 不会更新。

### 25.3 解决方案

把函数改成响应式属性：

```qml
property var filteredSessions: {
    const result = []
    const sessions = AppController.transfer.sessions
    for (let i = 0; i < sessions.length; i++) {
        if (sessions[i].deviceId === tw_deviceSessionView.deviceId) {
            result.push(sessions[i])
        }
    }
    return result
}

model: tw_deviceSessionView.filteredSessions
```

属性定义中直接读取 `AppController.transfer.sessions`，QML 的绑定追踪可以识别这个依赖。当 sessions 变化时，`filteredSessions` 会自动重新计算，ListView 也随之更新。

### 25.4 为什么一开始用函数

最初写 `sessionsForCurrentDevice()` 是因为逻辑看起来更清晰——一个专门的函数负责筛选。但 QML 的响应式系统和命令式编程的习惯不同：在命令式代码里，函数每次调用都会重新执行；在 QML 里，只有属性绑定才能自动追踪依赖。

这次之后，凡是需要响应外部状态变化的列表筛选，都改用属性而不是函数。函数只用于不依赖外部状态的纯计算，或者用户交互触发的命令式操作。

### 25.5 顺手做的改进

修复绑定问题的同时，也对照设计文档补充了几个显示改进：

1. **时间信息**：会话记录增加 `createdAt` 字段，QML 卡片显示创建时间
2. **方向标识**：发送（蓝色圆形↑）和接收（紫色圆形↓）用颜色和图标区分
3. **设备名称**：卡片显示"发送给 XXX"或"来自 XXX"
4. **移除记录**：`TransferSessionManager` 新增 `removeSession()` 方法，允许清理已完成/失败的任务

这些改进参照了 `device-session-ui-plan.local.md` 中的设计。第一版先做了显示和清理，后续再考虑速度统计和失败重试。

## 26. modelData 在 Qt6 中不可用

**日期**：2026-06-12

### 26.1 问题

修复传输记录显示后，日志一直报 `ReferenceError: modelData is not defined`，界面上的设备名称、时间、文件大小等信息全部显示为空。

### 26.2 原因

Qt5 中 ListView delegate 绑定 QVariantList 时，用 `modelData.xxx` 访问元素属性。Qt6 改了规则：当 model 是 JavaScript 数组（如 QML 函数返回的数组）时，应该用 `model.xxx`。

这次的 `filteredSessions` 是 QML 属性中用 JavaScript 构建的数组，不是 C++ 直接提供的 QVariantList，所以 Qt6 要求用 `model` 而不是 `modelData`。

### 26.3 修复

把 delegate 中所有 `modelData.xxx` 改成 `model.xxx`：

```qml
delegate: TransferTaskCard {
    sessionId: model.sessionId || ""
    taskType: model.type || ""
    peerDeviceName: model.peerDeviceName || ""
    // ...
}
```

这个坑之前在 TransferPanel.qml 中遇到过一次（第十八章），当时也是同样的修改。说明 Qt6 的这个变化是系统性的，后续所有 ListView delegate 都要注意。

## 27. 传输完成弹窗的按钮角色问题

**日期**：2026-06-12

### 27.1 问题

传输完成弹窗有两个按钮："打开"和"确定"。用户期望"打开"打开文件所在目录，"确定"只关闭弹窗。但实际上两个按钮都会打开目录。

### 27.2 原因

Qt 的 `Dialog.standardButtons` 中，`Dialog.Open` 和 `Dialog.Ok` 都触发 `accepted` 信号，无法区分。`onAccepted` 里调用 `ConfigManager.openFolder()`，所以不管点哪个都会执行。

之前尝试用 `onAccepted` + `onRejected` 组合来区分，但这种写法不够直观，而且"确定"按钮变成 reject 角色，语义上不合理。

### 27.3 修复

改用自定义 footer 按钮，明确指定每个按钮的角色：

```qml
footer: DialogButtonBox {
    Button {
        text: qsTr("确定")
        DialogButtonBox.buttonRole: DialogButtonBox.RejectRole
    }
    Button {
        text: qsTr("打开文件所在位置")
        DialogButtonBox.buttonRole: DialogButtonBox.AcceptRole
    }
}
```

这样"确定"触发 `onRejected`（只关闭弹窗），"打开文件所在位置"触发 `onAccepted`（打开目录）。按钮文字也更清楚地说明了操作。

## 28. JavaScript 数组作为 ListView model 的绑定问题

**日期**：2026-06-13

### 28.1 问题

上一章把 `modelData` 改成 `model` 后，错误变成了 `model is not defined`。两种写法都不工作。

### 28.2 原因分析

Qt6 中 ListView 的 delegate 绑定方式取决于 model 的来源：

- **C++ 直接提供**的 QVariantList（如 `AppController.transfer.sessions`）：用 `model.xxx`
- **QML JavaScript 构建**的数组（如函数返回的数组）：绑定方式不一致，容易出问题

之前用 `filteredSessions` 属性返回 JavaScript 数组作为 model，Qt6 的 delegate 无法正确识别数组元素的属性访问方式。

### 28.3 最终方案

放弃 JavaScript 数组过滤，直接使用原始 `AppController.transfer.sessions` 作为 model，在 delegate 中用 `visible` 属性控制显示：

```qml
ListView {
    model: AppController.transfer.sessions

    delegate: TransferTaskCard {
        visible: modelData.deviceId === tw_deviceSessionView.deviceId
        height: visible ? implicitHeight : 0
        sessionId: modelData.sessionId || ""
        // ...
    }
}
```

这样 model 来源是 C++，`modelData.xxx` 可以正常工作。不匹配当前设备的项通过 `visible: false` 和 `height: 0` 隐藏。

### 28.4 代价与取舍

这个方案的缺点是 ListView 会为所有会话创建 delegate，包括不属于当前设备的。对于传输记录数量不多的场景（几十到几百条），性能影响可以忽略。

如果后续记录数量很大，应该改用 `DelegateModel`（`DelegateModel`）的 `filterOnGroup` 功能，或者在 C++ 端提供按设备过滤的 model。

**日期**：2026-06-13

### 29.1 问题

改用 `visible` 过滤后，`tw_sessionList.count === 0` 的空列表提示失效了。因为 `count` 统计的是 model 中的所有项，包括 `visible: false` 的项。

property int filteredCount: {

然后用 `filteredCount === 0` 判断是否显示空列表提示。

这个属性虽然也是 JavaScript 计算，但只用于判断是否显示提示文字，不作为 model，所以不会有绑定问题。

## 30. 文件夹传输不能只把目录项当文件发送

**日期**：2026-06-13

### 30.1 问题

原来的目录序列化结果同时包含普通文件和以 `/` 结尾的空目录项，但发送端把所有条目都按文件打开。结果是空目录无法发送；同时请求只携带相对路径，接收端会把文件直接散落到接收目录，丢失用户选择的顶层文件夹。

### 30.2 修复

发送端把目录结构拆成三部分：顶层目录名、普通文件列表和空目录列表。接收端先校验所有相对路径，再创建唯一的目标根目录，并在写文件前恢复空目录。完全空的文件夹没有数据块，因此通过 `TransferDone` 明确结束传输。

接收端还为重名文件和文件夹生成 `名称 (1)`、`名称 (2)` 等目标路径，避免静默覆盖已有内容。

### 30.3 自动接收的边界

“自动保存”不能等同于默认无条件接受网络输入。本次将它实现为默认关闭、由用户显式开启的“自动接收并保存”配置。开启后 `TransferSessionManager` 跳过确认弹窗，但仍复用接收端的路径校验、重名避让和完整性校验。

### 30.4 这一阶段留下的经验

1. 目录元数据和文件数据是两类不同信息，协议中应分别表达。
2. 空文件夹没有数据块，必须设计独立的完成语义。
3. 接收路径必须在落盘前校验，不能信任发送方提供的相对路径。
4. 自动化策略应放在会话编排层，底层 Worker 仍保持相同的校验和保存流程。
5. 目录功能必须做发送端到接收端的端到端测试，仅测试序列化不足以发现落盘结构问题。

## 31. QML 动画与共享 JavaScript 的边界

**日期**：2026-06-14

## 32. 文件夹与大型文件传输的边界控制

**日期**：2026-06-14

文件夹传输原来用任务累计字节数判断当前文件是否发送完成。当前文件最后一块发送后，只要整个文件夹还有剩余字节，发送端就会再次读取已经到达末尾的文件，从而报告读取失败。任务总进度只能用于展示，文件切换必须依据当前文件的已发送字节数，并等待接收端校验确认后再打开下一个文件。

大型文件还暴露了两个时序问题。发送端连续调用 `QTcpSocket::write()` 会让未发送数据长期堆积在内存中，因此需要根据 `bytesToWrite()` 限制写队列，并在 `bytesWritten` 后继续发送。超时计时也不能只依赖接收数据；持续写出数据同样表示连接仍然活跃。

最后一个文件接收完成后，接收端不能发送 ACK 后立即销毁连接。否则 ACK 可能尚未写入网络，发送端会把连接断开误判为失败。最终流程应为：接收端校验并发送 ACK，发送端收到 ACK 后发送 `TransferDone`，接收端收到 `TransferDone` 后再结束会话。

本次测试同时断言发送端和接收端结果，并覆盖多文件夹、零字节文件、空文件夹、自动保存和 40 MB 文件。只断言接收文件存在，会漏掉发送端已经报告失败的协议问题。

## 33. 文件类型图标与文件夹记录展开

**日期**：2026-06-15

传输记录最初使用 emoji 区分文件和文件夹。emoji 的颜色、尺寸和基线由系统字体决定，不同桌面环境显示差异明显，也无法表达图片、视频、音频、压缩包和代码等常见类型。本次改为项目内置 SVG 图标，并由 `FileTypeIcon.qml` 根据扩展名选择图标。这样图标随应用资源打包，不依赖宿主机图标主题。

文件夹展开功能还要求发送端和接收端会话都提供相同的 `fileList` 模型角色。只在发送端序列化目录列表，会导致接收端卡片无法展开；非文件夹会话如果完全缺少该字段，也可能让 QML 的 `required property` 在运行时失败。因此，会话模型应始终提供稳定角色，文件夹接收端再从已经校验过的相对路径元数据填充列表。

任务卡片不能使用固定高度容纳动态内容。进度栏、完成操作和展开列表会随状态变化，固定高度会裁切底部按钮。本次让卡片高度跟随布局隐式高度，并限制展开列表的最大高度，由列表内部滚动处理超出内容。

接收确认弹窗也不能把文件夹当成“第一个文件 + 多文件统计”展示。文件夹请求中的单项大小实际是第一个子文件大小，与总大小同时出现会让用户误以为文件夹存在两个不同大小。文件夹确认信息应只展示顶层文件夹名、递归文件总数、总大小和根目录预览；根级文件夹以 `/` 结尾，文件继续按类型显示图标。单文件请求才展示“文件名 + 大小”。

传输任务模型目前通过 `QVariantList` 整体暴露给 QML。每个数据块都发送 `sessionsChanged()` 时，`ListView` 可能重建任务委托；如果委托带有入场透明度动画，就会在文件夹或大型文件传输期间反复闪烁，卡片内部的展开状态也会丢失。当前处理方式是仅在状态、总大小或整数进度变化时通知界面，移除会被重复触发的入场动画，并由列表页面按 `sessionId` 保存展开状态。后续若传输记录继续扩展，应将会话列表升级为 `QAbstractListModel`，使用角色级 `dataChanged()` 更新单条记录。

## 35. QML 运行时错误与标准属性约束

**日期**：2026-06-15

### 35.1 问题现象

在优化传输任务卡片的 UI 风格时，为了让对话框页眉实现“仅顶部圆角”的效果，我们在 `TransferTaskCard.qml` 和 `TransferPanel.qml` 的 `Rectangle` 中使用了 `corners` 属性。

代码在编译阶段完全正常（因为 QML 文件是作为资源打包的，编译器不校验属性存在性），但运行时程序直接崩溃并报错：
```text
[WARNING] qrc:/qt/qml/cqnu/gridyard/client/ui/TransferTaskCard.qml:367:17: Cannot assign to non-existent property "corners"
[1]  + 303103 exit 255   ./build-ninja/client/appGridYard
```

### 35.2 原因分析

这个问题的根源在于对 Qt 原生组件属性的误解。

1.  **非标准属性**：Qt Quick 标准库中的 `Rectangle` 组件只提供 `radius` 属性（控制四个角相同的圆角）。它并不提供类似 CSS 那样的 `border-top-left-radius` 或者某些第三方库中的 `corners` 属性。
2.  **静默失效与运行时崩溃**：由于项目使用了 `qt_add_qml_module` 将界面文件打包进二进制，CMake 构建时并不会扫描 QML 内部的属性合法性。只有当 QML 引擎在运行时尝试解析该组件时，才会因为找不到属性而抛出致命异常，导致整个引擎加载失败。

### 35.3 解决办法

为了在不引入第三方库的情况下实现“部分圆角”，我们采用了“矩形遮盖法”这一经典技巧：

```qml
background: Rectangle {
    color: "#F5F7FA"
    radius: 10
    // 仅顶部圆角：用一个同色的直角矩形遮盖底部圆角区域
    Rectangle {
        anchors.bottom: parent.bottom
        width: parent.width
        height: parent.radius
        color: parent.color
    }
}
```

此外，我们还重新梳理了构建流程：修改 QML 后必须确保执行了 `cmake --build .`，否则运行的仍是旧版二进制中嵌入的旧 QML 资源，这在排查“改了代码没生效”或“报错依然存在”时非常关键。

### 35.4 这一阶段留下的经验

1.  **不要信任编译器的“沉默”**：QML 的灵活性代价是属性校验滞后。引入新属性前，应查阅 Qt 官方文档确认其属于当前使用的 Qt 版本。
2.  **技巧重于黑科技**：像“遮盖法”这种组合基础组件实现复杂效果的方式，虽然看起来不够优雅，但它不依赖插件、兼容性最强，是局域网这类需要跨环境部署应用的首先。
3.  **运行是唯一的检验标准**：UI 修改不能只看预览，必须实际启动二进制程序，确保在目标环境中没有加载异常。

## 37. 接收侧后台化：QThread 线程归属踩坑全记录

**日期**：2026-06-16

**涉及文件**：`p2p_server.h/cpp`、`file_receiver_worker.h/cpp`、`transfer_session_manager.cpp`

这一章是 Stage 4 收尾阶段最折腾的一块，主要由冯春霖顶上。前后试了三种方案才把接收侧的文件写盘和 SHA-256 校验移出 UI 主线程，下面按时间顺序记录完整过程。

### 37.1 背景

Stage 4 收尾目标之一是将接收侧的文件写盘和 SHA-256 校验移出 UI 主线程。发送侧早已用 `QThread + moveToThread` 实现了后台化（见 `transfer_session_manager.cpp` 中 `createSendSession` 的实现），但接收侧的 `FileReceiverWorker` 由 `P2pServer::onNewConnection` 直接创建在主线程，写盘和哈希计算全部在主线程执行，违反 NF-102 界面响应性要求。

### 37.2 第一次尝试：直接 moveToThread（失败）

最初的做法很直观——在 `onNewConnection` 中创建 `QThread`，将 worker 移过去：

```cpp
auto *thread = new QThread{this};
auto *worker = new FileReceiverWorker{socket};
worker->moveToThread(thread);
thread->start();
```

**结果**：QTimer 报错 `QObject::startTimer: Timers cannot be started from another thread`，socket 报错 `QSocketNotifier: Socket notifiers cannot be enabled or disabled from another thread`。

原因：`FileReceiverWorker` 的构造函数在主线程中执行，`QTimer` 和 `FrameCodec` 都在构造函数中创建并连接信号。`moveToThread` 只移动了 worker 本身，但 QTimer 和 FrameCodec 的线程归属仍然是主线程。Qt 的定时器和 socket notifier 绑定到创建它们的线程，跨线程操作会直接报错。

### 37.3 第二次尝试：initialize() 延迟初始化（部分成功）

最后改成：将 QTimer 和 FrameCodec 的创建从构造函数移到新的 `initialize()` 槽函数，由 `QThread::started` 信号触发：

```cpp
// 构造函数中只保存 socket，不创建 QTimer/FrameCodec
FileReceiverWorker::FileReceiverWorker(QTcpSocket *socket, QObject *parent)
    : QObject{parent}, _socket{socket}
{
    _socket->setParent(nullptr);
}

// initialize() 在后台线程中执行
void FileReceiverWorker::initialize()
{
    _socket->moveToThread(QThread::currentThread());  // ← 无效，见下文
    _codec = new FrameCodec{this};
    _timeoutTimer = new QTimer{this};
    // 连接信号...
}
```

**新问题**：`_socket->moveToThread(QThread::currentThread())` 报错 `Cannot move to target thread`。因为 socket 在主线程中由 `QTcpServer::nextPendingConnection()` 创建，其线程归属是主线程的 `QTcpServer` 所在线程，不能从 worker 线程移动它。

### 37.4 最终方案：socket 设为 worker 的子对象

**正确做法**：在构造函数中将 socket 的父对象设为 worker 自身。当 worker 被 `moveToThread` 时，Qt 会自动递归移动所有子对象，包括 socket：

```cpp
FileReceiverWorker::FileReceiverWorker(QTcpSocket *socket, QObject *parent)
    : QObject{parent}, _socket{socket}
{
    _socket->setParent(this);  // 关键：socket 跟随 worker 一起移动
}
```

**完整的线程初始化流程**（`p2p_server.cpp`）：

```cpp
auto *thread = new QThread{this};
auto *worker = new FileReceiverWorker{socket};
worker->moveToThread(thread);  // worker + socket + 子对象一起移

// 线程启动时初始化（在后台线程中创建 QTimer/FrameCodec）
connect(thread, &QThread::started, worker, &FileReceiverWorker::initialize);

// 转发信号跨线程
connect(worker, &FileReceiverWorker::transferRequestReceived,
        this, [this, worker](...) {
    emit transferRequestReceived(worker, ...);
});

// 传输完成 → 退出线程
connect(worker, &FileReceiverWorker::transferFinished,
        this, [thread](...) {
    QMetaObject::invokeMethod(thread, [thread]() {
        thread->quit();
    }, Qt::QueuedConnection);
});

// 线程结束 → 安全删除
connect(thread, &QThread::finished, worker, &QObject::deleteLater);
connect(thread, &QThread::finished, thread, &QObject::deleteLater);

thread->start();
```

### 37.5 附带问题：跨线程调用 worker 方法

测试中发现，从主线程直接调用 `worker->acceptTransfer()` 会崩溃。因为 worker 在后台线程中，跨线程直接调用非线程安全。

最后改成：所有从主线程调用 worker 方法的地方，统一用 `QMetaObject::invokeMethod` + `Qt::QueuedConnection`：

```cpp
// 错误：直接调用（跨线程不安全）
worker->acceptTransfer();

// 正确：通过事件队列投递
QMetaObject::invokeMethod(worker, [worker]() {
    worker->acceptTransfer();
}, Qt::QueuedConnection);
```

需要修改的地方包括：
- `TransferSessionManager::acceptReceiveSession()`
- `TransferSessionManager::rejectReceiveSession()`
- `TransferSessionManager::cancelSession()` 中的接收方分支
- `TransferSessionManager::onTransferRequestReceived()` 中的 `setReceivePath()`
- 测试代码中所有对 worker 方法的调用

### 37.6 附带问题：P2pServer 析构时线程未退出

测试中反复出现 `QThread: Destroyed while thread is still running` 崩溃。原因是 `P2pServer` 的析构函数是 `default`，Qt 的对象树机制在 `~QObject()` 中按逆序删除子对象时，QThread 可能还在运行。

最后改成：自定义析构函数，在删除子对象前先停止所有线程：

```cpp
P2pServer::~P2pServer()
{
    if (_server->isListening()) {
        _server->close();
    }
    // 遍历子对象中的 QThread，先 quit 再 wait
    const auto kids = children();
    for (QObject *child : kids) {
        if (auto *thread = qobject_cast<QThread*>(child)) {
            if (thread->isRunning()) {
                thread->quit();
                thread->wait(1000);
            }
        }
    }
}
```

要留意：不能用 `QList<QThread*> _threads` 成员保存线程指针——析构时子对象可能已被 Qt 的对象树释放，访问野指针会 SegFault。改用 `children()` 动态获取才是安全的。

### 37.7 总结

Qt 的线程模型核心规则：

1. **QTimer/QSocketNotifier 绑定到创建线程**——必须在 worker 所在线程中创建，不能在主线程创建后移到后台线程。
2. **moveToThread 会递归移动子对象**——将 socket 设为 worker 的子对象（`setParent(this)`），moveToThread 时 socket 会自动跟随。
3. **跨线程调用必须用 Queued Connection**——直接调用 worker 方法会崩溃，统一用 `QMetaObject::invokeMethod`。
4. **QThread 也是 QObject，析构时要先 quit**——在自定义析构函数中遍历 `children()` 获取 QThread 并停止，不要依赖 `default` 析构。
5. **不要在析构中缓存子对象指针**——Qt 的对象树会按逆序删除子对象，缓存的指针可能已失效。

## 38. testConnectionLost 端口占用问题

### 38.1 现象

Stage 4 接收侧后台化改完后，`test_file_transfer` 中只剩 `testConnectionLost()` 失败：

```text
FAIL!  : TestFileTransfer::testConnectionLost()
  'server.listen(QHostAddress::AnyIPv4, _testPort)' returned FALSE.
```

失败点在 `testConnectionLost()` 内部的原始 `QTcpServer`：

```cpp
QTcpServer server;
QVERIFY(server.listen(QHostAddress::AnyIPv4, _testPort));
```

也就是模拟断网用的测试服务器没有成功绑定端口。

### 38.2 排查过程

一开始怀疑是 `testCancelTransfer()` 没有把 `P2pServer` 关干净。这个用例在函数栈上创建了：

```cpp
P2pServer server(_config);
QVERIFY(server.start());
```

函数结束时 `P2pServer::~P2pServer()` 会调用 `_server->close()`，并停止接收线程。从对象生命周期看，监听 socket 已经关闭，不是普通的对象泄漏。

继续看端口分配逻辑，测试类有一个成员 `_testPort`，初始化为：

```cpp
_testPort = 35100 + (QDateTime::currentMSecsSinceEpoch() % 1000);
```

多个端到端测试会在开头执行：

```cpp
_config->setTcpPort(++_testPort);
```

理论上每个用例使用递增端口。但 `testConnectionLost()` 紧跟在 `testCancelTransfer()` 后面，前一个用例刚刚建立过 TCP 连接并主动取消，内核层连接关闭后仍可能短时间处于 `TIME_WAIT`。测试马上绑定相邻或冲突端口时，就会出现偶发的 `listen()` 失败。

这里的关键点是：`_server->close()` 只能关闭 Qt 对象持有的监听 socket，不能控制内核 TCP 状态立即完全释放。单元测试连续跑得太快时，固定端口段很容易和系统状态产生耦合。

### 38.3 修复方案

这个测试并不需要验证固定端口，它只需要一个可连接的本地 TCP server 来模拟“连接建立后断开”。所以最稳的做法是让系统分配临时端口：

```cpp
QTcpServer server;
QVERIFY(server.listen(QHostAddress::AnyIPv4, 0));
const quint16 serverPort = server.serverPort();
QVERIFY(serverPort != 0);
```

然后发送端使用真实端口：

```cpp
QMetaObject::invokeMethod(&sender, "startTransfer", Qt::QueuedConnection,
                          Q_ARG(QString, "127.0.0.1"),
                          Q_ARG(quint16, serverPort),
                          Q_ARG(QString, sendPath),
                          Q_ARG(QString, "connlost-sender-id"),
                          Q_ARG(QString, "ConnLostSender"));
```

这样 `testConnectionLost()` 不再依赖 `_testPort`，也不受上一个测试留下的 TCP 状态影响。

### 38.4 顺手补上的线程清理

单独跑 `testConnectionLost()` 时，功能断言已经通过，但测试进程一开始退出码异常。原因是模拟接收端也创建了后台线程，测试结束前没有明确等待线程退出。

修复时增加了三个验证点：

```cpp
bool receiverFinished = false;
bool receiverSuccess = true;
bool receiverThreadFinished = false;
```

`transferFinished` 到达时退出线程：

```cpp
connect(worker, &FileReceiverWorker::transferFinished, this,
        [&receiverFinished, &receiverSuccess, thread](bool success, gy::protocol::ErrorCode, const QString &) {
    receiverFinished = true;
    receiverSuccess = success;
    thread->quit();
});
```

线程真正结束后再标记：

```cpp
connect(thread, &QThread::finished, this, [&receiverThreadFinished]() {
    receiverThreadFinished = true;
});
```

用例结尾等待接收端失败并确认线程退出：

```cpp
QTRY_VERIFY_WITH_TIMEOUT(receiverFinished, 5000);
QVERIFY(!receiverSuccess);
QTRY_VERIFY_WITH_TIMEOUT(receiverThreadFinished, 5000);
```

同时把接收路径也放回 worker 所在线程里设置：

```cpp
QMetaObject::invokeMethod(worker, [worker, this]() {
    worker->setReceivePath(_recvDir->path());
    worker->acceptTransfer();
}, Qt::QueuedConnection);
```

这样既修复了端口占用，也避免测试结束时后台线程还没收尾。

### 38.5 结果

验证命令：

```bash
cmake --build build-ninja --target test_file_transfer
./build-ninja/tests/test_file_transfer testConnectionLost
./build-ninja/tests/test_file_transfer
```

结果：

```text
testConnectionLost: passed
test_file_transfer: 17 passed, 0 failed
```

### 38.6 经验总结

1. 测试如果不关心具体端口，优先使用 `listen(..., 0)` 让系统分配端口，再用 `serverPort()` 传给客户端。
2. TCP 端口关闭不等于内核状态立即消失，连续集成测试不要依赖固定端口刚用完就可再次绑定。
3. `SO_REUSEADDR` 可以缓解端口复用问题，但这个用例不需要固定端口，随机临时端口更简单。
4. 涉及后台线程的测试，不能只等业务信号，还要等线程退出，否则容易出现“断言通过但进程退出异常”的问题。
5. 测试代码也要遵守生产代码的线程边界，worker 已经移到后台线程后，主线程继续用 `QMetaObject::invokeMethod` 投递调用。

## 39. 封装性改进：对象协作约定

### 39.1 背景

参考项目 `doc/sims/` 展示了一种"Tell, Don't Ask"的封装设计思想：用 `hasId(id)` 替代 `getId()`，用 `info()` 替代 `getName()`，让对象自己负责回答"是不是"而不是暴露内部状态。这个思路启发我们重新审视 GridYard 的跨类访问方式。

### 39.2 发现的问题

扫描代码后发现，GridYard 存在大量跨类 getter 调用：

- `DiscoveryService` 直接调用 `_config->deviceId()`、`_config->deviceName()` 构建 Hello 包
- `TransferSessionManager` 直接调用 `_config->deviceId()`、`_config->deviceName()` 获取发送方信息
- `TransferSessionManager` 直接调用 `worker->sessionId()`、`- `TransferSessionManager` 直接调用 `worker->sessionId()`、`worker->fileName()` 等获取接收会话信息

这些调用破坏了封装性：调用者需要知道被调用对象的内部结构，而不是告诉对象"做什么"。

### 39.3 改进方案

**ConfigManager 新增语义化方法**：

```cpp
bool isMyDevice(const QString &deviceId) const;
void fillHelloPayload(QJsonObject &json) const;
void fillSenderInfo(QVariantMap &session) const;
```

**DiscoveryService 新增语义化查询方法**：

```cpp
bool isPeerOnline(const QString &deviceId) const;
QString peerIpAddress(const QString &deviceId) const;
quint16 peerTcpPort(const QString &deviceId) const;
QString peerName(const QString &deviceId) const;
```

**FileReceiverWorker 新增委托方法**：

```cpp
void fillReceiveSession(QVariantMap &session) const;
QStringList rootPreviewPaths() const;
```

### 39.4 踩坑记录

**坑 1：lambda 捕获变量未定义**

修改 `createSendSession()` 时，我移除了 `senderDeviceId` 和 `senderName` 变量的定义，但 lambda 中仍然在使用它们。编译时报错：

```
error: 'senderDeviceId'在此作用域中尚未声明
```

**解决方案**：从 session 中获取这些值，因为 session 已经通过 `fillSenderInfo()` 填充了发送方信息。

**坑 2：`buildRootPreview()` 函数作用域问题**

在 `fillReceiveSession()` 中调用 `buildRootPreview()` 时，编译报错：

```
error: 'buildRootPreview'在此作用域中尚未声明
```

原因是 `buildRootPreview()` 是 `transfer_session_manager.cpp` 中的匿名命名空间函数，不是 `FileReceiverWorker` 的方法。

**解决方案**：在 `fillReceiveSession()` 中直接实现根目录预览逻辑，而不是调用外部函数。

**坑 3：`fileList` 字段始终为空**

第一次修改 `fillReceiveSession()` 时，我错误地将 `session["fileList"]` 总是设置为空的 `QVariantList{}`，而没有调用 `rootPreviewPaths()` 方法来获取文件列表。

**解决方案**：在 `fillReceiveSession()` 中正确处理目录情况，构建根目录预览。

### 39.5 测试验证

修改完成后，运行测试发现 `testReceiveFolderPreview` 失败：

```
FAIL!  : TestFileTransfer::testReceiveFolderPreview() Compared values are not the same
```

原因是测试期望 `preview` 列表包含 `"root.txt"` 和 `"nested/"`，但我们的实现没有正确构建根目录预览。

**解决方案**：在 `fillReceiveSession()` 中实现根目录预览逻辑，只显示顶层文件和目录：

```cpp
if (_isDirectory) {
    QVariantList preview;
    QSet<QString> seen;
    for (const auto &item : _fileList) {
        const QString cleanPath = item.relativePath.endsWith('/') ? item.relativePath.chopped(1) : item.relativePath;
        const QStringList parts = cleanPath.split('/', Qt::SkipEmptyParts);
        if (parts.isEmpty()) continue;

        const bool isRootDirectory = parts.size() > 1 || item.relativePath.endsWith('/');
        const QString rootEntry = parts.first() + (isRootDirectory ? "/" : "");
        if (!seen.contains(rootEntry)) {
            seen.insert(rootEntry);
            preview.append(rootEntry);
        }
    }
    session["fileList"] = preview;
}
```

### 39.6 经验总结

1. **Tell, Don't Ask 原则**：让对象自己负责回答"是不是"或"填充什么"，而不是暴露内部状态让调用者自己判断。
2. **lambda 捕获变量**：修改代码时要特别注意 lambda 捕获的变量是否仍然有效。
3. **函数作用域**：匿名命名空间中的函数不能在其他文件中调用，需要将逻辑内联或提取为公共方法。
4. **测试驱动开发**：修改代码后必须运行测试，测试失败时要仔细分析失败原因，而不是简单地修改测试。
5. **渐进式改进**：Q_PROPERTY READ 函数必须保留（Qt/QML 集成要求），值类型（Q_GADGET）直接访问成员是合理的。

## 40. 传输会话的职责边界与跨线程值传递

**日期**：2026-06-21

文件接收链路里，`FileReceiverWorker` 运行在独立线程，`P2pServer` 负责连接和转发，`TransferSessionManager` 负责会话记录、确认弹窗和 QML 状态。三个对象都需要同一份传输信息，但不应该共享 Worker 的内部状态。

### 40.1 请求阶段：交付一份完整快照

Worker 解析完 `TransferReq` 后，构建 `QVariantMap` 请求快照并通过信号发出。快照包含会话编号、发送方信息、展示名称、文件总数、总大小、目录标记、顶层预览和完整相对路径列表。

```cpp
void transferRequestReceived(const QVariantMap &request);
```

`P2pServer` 只把快照和用于后续确认操作的 Worker 指针继续转发；`TransferSessionManager` 直接用快照建立会话。这样会话管理器只处理已经确定的请求结果，不需要知道 Worker 用哪些成员保存解析状态。

目录传输有两种不同用途的数据：界面确认弹窗只需要顶层预览，而测试和传输记录有时需要完整相对路径列表。快照中分别保存这两份数据，避免为了测试或展示去读取 Worker 的文件列表。

### 40.2 完成阶段：把结果随事件一起交付

同名避让后，实际写入路径只能由接收端确定。该路径作为完成事件的一部分传递：

```cpp
void transferFinished(bool success,
                      gy::protocol::ErrorCode errorCode,
                      const QString &errorMsg,
                      const QString &savedPath);
```

`TransferSessionManager` 根据 `savedPath` 更新 `localPath` 和可删除标记。这样“传输是否成功”和“最终保存在哪里”属于同一次完成结果，清理记录时也能准确删除接收文件而不会误碰发送源文件。

### 40.3 跨线程边界的处理

Worker 被 `moveToThread()` 后，主线程不直接读取或修改它的状态。接收路径设置、接受和拒绝操作仍通过 `QMetaObject::invokeMethod(..., Qt::QueuedConnection)` 投递到 Worker 所在线程；请求和完成信息则由 Qt 信号以值类型复制到主线程。

这个边界有两个实际好处：

1. 线程归属清楚。网络收包、写盘和哈希计算只在 Worker 线程进行，QML 会话模型只在主线程更新。
2. 会话记录不依赖 Worker 生命周期。Worker 在传输结束后可以正常退出和释放，会话列表保留的是自己的值数据。

### 40.4 设备发现的发送端点

发送文件时需要设备名、IP 和 TCP 端口。发现服务提供 `transferEndpoint(deviceId)`，一次返回可发送目标的值快照；设备不存在或离线时返回空结果。调用方不需要连续查询同一设备的多个字段，也不会把节点表的存储方式带到传输会话层。

### 40.5 Qt 属性与普通协作接口的区别

QML 的 `Q_PROPERTY READ` 访问器仍然保留。例如配置、在线设备列表和传输会话列表都需要通过属性绑定发布给界面，并由 `NOTIFY` 信号驱动刷新。它们返回的是受控只读数据或副本，不直接公开内部容器。

对象之间的业务协作则优先使用带有明确含义的方法、请求快照和完成结果信号。区分这两类接口后，QML 绑定需求和后台业务边界不会互相混在一起。

### 40.6 验证

这部分调整后重点运行了目录传输、取消、断连和接收会话相关测试，确认目录预览、完整路径、实际保存路径和线程退出流程仍然正确。全量 `ctest --test-dir build-ninja --output-on-failure` 的 8 个测试均通过。

## 42. 在线聊天协议：把 JSON 收口到值类型编解码器

**日期**：2026-06-23

Stage 5 需要在既有 TLV 帧上增加 `ChatText` 和 `ChatAck`。最开始看起来只需在发送端构造 JSON、接收端逐个读取字段，但这种做法很容易让字段名、长度限制和校验规则分散到多个网络类中，后续增加回执或消息模型时会出现不一致。

### 42.1 设计选择

新增 `ChatMessage` 值类型承载 `messageId`、发送方设备 ID、发送方名称、文本内容和发送时间；新增 `ChatMessageCodec` 作为唯一 JSON 出入口。协议字段名和业务上限集中在 `protocol.h`：控制帧仍受 1 MB 通用限制，聊天业务额外限制为 64 KiB Payload、4,000 个字符。

```cpp
gy::ChatMessage message;
QByteArray payload;
gy::ChatMessageCodec::encode(message, &payload);
```

接收端通过同一接口解码，不让 `P2pServer`、后续 `ChatManager` 或 QML 重复解析 JSON。

### 42.2 校验边界

编码与解码均校验 UUID、ISO 8601 时间、必填字符串、空白内容和长度上限。发送端失败归类为 `InvalidInput`，入站 Payload 的缺字段、字段类型错误、无效 UUID 或时间统一归类为 `InvalidPayload`。`PeerOffline`、`ConnectionFailed`、`WriteFailed` 和 `ConnectionLost` 也提前定义为稳定分类，留给连接管理层使用。

`kTypeChatAck` 在阶段 A 只保留协议码，不实现送达语义。这样后续增加回执不会重新分配 Type，也不会让未完成的功能伪装成可用状态。

### 42.3 测试经验

聊天协议测试覆盖中文、多行文本、半包、粘包、超长 Payload、缺字段、字段类型错误、空白内容、无效 UUID 和无效时间。协议测试不依赖 socket，定位问题时能先排除网络层干扰。

## 43. 同端口分流：首帧判断不能吞掉首帧

**日期**：2026-06-23

文件传输和在线聊天共用 `P2pServer` 的 TCP 端口。旧实现一有入站连接就创建 `FileReceiverWorker`，聊天帧会被错误送入文件传输状态机。直接在服务器中 `readAll()` 后用 `FrameCodec` 判断 Type 虽能分流，却会吞掉首帧；交给 Worker 后它会一直等待已经读走的 `TransferReq`。

### 43.1 最终方案：peek + FrameCodec 副本校验

路由层先查看 8 字节 TLV 帧头，确认 Payload 长度没有超过对应 Type 的上限；只有 socket 缓冲区已经包含整个首帧时才继续。随后用 `peek()` 取得完整帧副本并交给临时 `FrameCodec` 校验，原始 socket 字节始终不被消费。

```cpp
const QByteArray firstFrame = socket->peek(frameBytes);
FrameCodec codec;
codec.feed(firstFrame);
```

校验后：`TransferReq` 交给 `FileReceiverWorker`，`ChatText` 通过 `chatConnectionReceived(QTcpSocket *)` 交接，`ChatAck` 首帧、未知 Type、超限帧和无效聊天 JSON 一律关闭连接。

这个方案的重点不是“手工重写 FrameCodec”，而是在路由阶段只判断用途，保留真正的解码职责给最终处理者。它还能保留同一批 TCP 数据中紧跟首帧到达的后续字节。

### 43.2 为什么要等待完整首帧

只收到 TLV 头就立即交接会让无效或不完整 Payload 绕过路由校验；直接读取完整首帧又会破坏后续状态机。等待完整帧、对副本校验、对原 socket 交接同时满足了协议防护和首帧保留两个要求。

## 44. socket 交接的线程归属与缓冲数据

**日期**：2026-06-24

首帧路由引入了一个新的生命周期问题：`P2pServer` 在主线程等待数据，文件接收 Worker 在后台线程运行。路由完成后，如果 socket 还保留着服务器的信号连接，或者 Worker 只等待新的 `readyRead` 信号，都会造成重复读取、跨线程访问或首帧滞留。

### 44.1 文件传输路径

路由前 socket 归 `P2pServer` 管理；确认 `TransferReq` 后先断开路由阶段的 `readyRead` 和 `disconnected` 连接，再将 socket 设为 `FileReceiverWorker` 的子对象。Worker 随后和 socket 一起 `moveToThread()`，延续既有后台接收模型。

因为首帧已在 socket 缓冲区中，Worker 初始化完成并连接信号后主动检查 `bytesAvailable()`，有数据就调用自身的读取流程。不能假设“晚连接 `readyRead` 后 Qt 会再发一次旧事件”。

### 44.2 聊天连接路径

`chatConnectionReceived(QTcpSocket *)` 的接收者必须在当前线程同步接管 socket 的对象归属。阶段 B 还没有 `ChatManager`，因此没有接收者时服务器主动关闭连接，避免悬空 socket。阶段 C 接入聊天管理器时必须先明确这一所有权契约，再把 socket 移交给聊天连接对象。

### 44.3 经验总结

1. socket 路由与 socket 读取是两件事，路由层不应替业务处理者消费数据。
2. `moveToThread()` 前必须让 socket 成为将要移动对象的子对象。
3. 交接时先断开旧连接；新处理者初始化后主动处理已缓冲数据。
4. 信号传递裸 socket 指针时，必须在接口注释中写清谁接管对象归属。

## 46. ChatManager：连接复用、去重与失败状态不能混在一起

**日期**：2026-06-24

聊天功能最容易被低估的部分不是一次 `write()`，而是连接和消息状态在异步信号下如何收口。发送端需要先根据 `DiscoveryService` 找到在线设备，再复用可用连接或创建连接；接收端则在真正读到第一条合法消息后，才知道这条 socket 属于哪个设备。

### 46.1 按设备维护连接，而不是按 socket 堆积

`ChatManager` 用 `deviceId -> ChatConnection` 维护活动连接。出站连接创建后立即登记；入站连接在解析出 `fromDeviceId` 后调用 `registerConnection()` 登记。若同一设备已经有一条可用连接，新的重复连接关闭；旧连接不可用时才替换。

这样做避免了两个问题：同一设备反复点击发送时创建多个 TCP 连接，以及双方同时发起连接时两条 socket 并存导致消息顺序和断线处理不确定。

### 46.2 发送状态必须先进入 Pending

`sendText()` 在编码成功后先把消息写入内存模型，状态为 `Pending`；`ChatConnection::messageWritten` 再更新为 `Sent`；写入失败则更新为 `Failed` 并发出 `sendFailed`。不能把“已经调用发送函数”直接当作已送达，也不能在 socket 尚未连接时丢掉用户刚输入的内容。

当前 Stage 5 只表示本地写入结果，`ChatAck` 尚未实现送达确认。因此 `Sent` 的语义是“本端成功写入连接”，不是“对端已阅读”。把这个边界写清楚，比提前伪造已读状态更重要。

### 46.3 去重键要和会话键分开

会话按 `deviceId` 分组，去重按每个会话内的 `messageId` 完成。`_messageIds[deviceId]` 阻止重连、重复帧或异常重发把同一条消息多次插入模型。清空会话时也必须同时清理对应的去重集合，否则同一 `messageId` 会在界面已清空后继续被错误过滤。

## 47. QAbstractListModel 是 QML 聊天列表的稳定边界

**日期**：2026-06-24

开始时可以把 `QVariantList` 直接暴露给 QML，但消息状态会从 Pending 变成 Sent 或 Failed，单纯替换整个列表容易造成 ListView 重建、滚动位置跳动，也让 QML 依赖内部 `QVariantMap` 字段名。

### 47.1 每个设备一份模型

`ChatManager::messageModelForDevice()` 返回按设备缓存的 `ChatMessageModel`。模型角色固定为 `messageId`、`deviceId`、`senderName`、`content`、`sentAt`、`isOutgoing` 和 `status`，会话页只消费这些角色，不直接访问连接对象。

这使得“切换设备会话”只是更换模型引用；新增消息调用 `beginInsertRows()`，状态变化调用对应行的 `dataChanged()`。后续 Stage 6 接入数据库时，也可以在不改变 QML 委托结构的前提下，把模型的数据源由纯内存扩展为历史消息。

### 47.2 视图层只负责输入和呈现

`DeviceSessionView` 将输入文本长度限制在协议定义的 4,000 字符，并在 Enter 时发送、Shift+Enter 时换行。离线设备禁用输入框；发送失败显示错误状态，但不会让 QML 自己构造协议帧或修改消息状态。

这一层次让 UI 与 `ChatConnection` 的 socket 生命周期解耦。排查显示问题时先检查模型角色和信号，再检查 QML 委托，不必从网络层一路跟到界面。

## 48. QML 标准属性不能凭经验套用

**日期**：2026-06-24

聊天会话页首次加载时出现过 `Cannot assign to non-existent property "maximumLength"`。这类错误的危险在于 C++ 编译完全正常，应用却会因为 QML 组件无法实例化而启动失败。

### 48.1 排查与修复

先根据报错的 QML 文件和行号定位实际对象类型，再查 Qt 版本对应的 QML API。不能因为 `TextInput`、`TextField` 或某个控件版本存在类似属性，就假定当前 `TextArea` 也支持同名属性。最终将长度控制放在 `onTextChanged`：超过 4,000 字符立即截断，与协议层的业务上限保持一致。

```qml
onTextChanged: {
    if (text.length > 4000)
        text = text.slice(0, 4000)
}
```

### 48.2 留下的约束

QML 组件属性属于运行时 API，新增属性前应查当前 Qt 版本文档，并至少启动一次实际 QML 场景。业务长度限制仍必须由 C++ 编解码器校验；界面的截断只改善输入体验，不能作为网络边界的唯一防线。

## 49. Stage 6 阶段 D：传输历史持久化的边界与测试稳定性

**日期**：2026-06-25

阶段 D 为已结束的传输补上 SQLite 历史记录：应用启动后恢复最近记录，传输完成、失败、取消或拒绝时写入，删除历史时只删除数据库记录，不删除原始文件。这个功能表面上是“多一张表、一次查询”，实际难点在于把异步传输状态、存储线程、重启恢复和测试数据库的生命周期接起来，同时不能让存储失败阻塞文件传输。

### 49.1 架构取舍：业务状态与持久化记录分开

`TransferSessionManager` 仍负责传输中的会话、进度和用户操作；`SqliteTransferHistoryProxy` 只实现 `ITransferHistoryRepository`，负责 `transfer_history` 表的新增、查询和删除；`AppController` 负责把两者接入存储执行器。这样做避免了传输 Worker 直接访问数据库，也避免 QML 依赖 SQLite 查询结果。

传输结束时，`TransferSessionManager` 先将内存会话收敛为完成、失败、取消或拒绝等最终状态，再发出待持久化的 `TransferRecord`。`AppController` 在存储工作线程中先更新设备活动时间，再调用历史仓储写入。数据库不可用或写入失败只记录错误并向用户提示，不能反过来改变已经完成的文件传输结果。

为保证重复回调、重试或应用重启后的记录不产生重复项，历史写入以 `session_id` 为唯一键，使用 SQLite 的 `INSERT ... ON CONFLICT(session_id) DO UPDATE` 实现幂等更新。查询支持设备、状态、开始时间过滤，按 `started_at DESC, record_id DESC` 排序；删除单条、清空已完成记录和过期清理都只操作 `transfer_history`，绝不删除源文件或接收文件。

启动恢复也保持单向依赖：`AppController` 在存储线程查询最近 100 条记录，再切回主线程调用 `restoreFinishedTransfers()` 填充会话模型。恢复数据只作为历史展示，不会重新启动发送或接收任务。

### 49.2 Bug：在非 void 辅助函数中误用 QtTest 断言宏

**文件**：`src/tests/test_storage_transfer_history.cpp`，`transferRowCount()`

#### 现象

构建测试目标时，GCC 对同一类问题报出 4 个错误：

```text
error: 在返回'int'的函数中，返回语句不带返回值 [-fpermissive]
```

#### 根因与排查

`transferRowCount()` 的返回类型是 `int`，用于给调用方返回历史表的行数。初版在函数内使用了 `QVERIFY2` 和 `QVERIFY` 检查数据库连接、SQL 执行和查询结果。

QtTest 的这些断言宏适用于测试槽函数等 `void` 返回的上下文；断言失败时宏会展开为无返回值的 `return`。因此编译器看到 `int` 函数可能执行 `return;`，即使测试路径通常不会失败，也必须拒绝编译。

这里不能靠强制转换或忽略编译警告解决。测试辅助函数应把“报告失败”和“返回错误值”分开：断言由外层测试槽函数承担，辅助函数只返回明确结果。

#### 修复

将三个断言替换为普通条件判断，失败统一返回 `-1`：

```cpp
QSqlDatabase connection = database.connectionForWorkerThread(&error);
if (!connection.isValid())
    return -1;

QSqlQuery query(connection);
if (!query.exec("SELECT COUNT(*) FROM transfer_history"))
    return -1;
if (!query.next())
    return -1;
return query.value(0).toInt();
```

调用侧再使用 `QCOMPARE(transferRowCount(...), expected)` 或 `QVERIFY(value >= 0)`，这样失败信息仍由 QtTest 输出，而辅助函数的 C++ 返回契约保持正确。

#### 经验

QtTest 宏不是普通布尔函数，使用前必须检查它们是否会从当前函数直接返回。凡是返回值不是 `void` 的辅助函数，优先返回 `std::optional`、结果对象或约定的错误值；不要把 `QVERIFY`、`QFAIL` 一类控制流宏放进去。

### 49.3 Bug：WAL 模式下重开同一测试数据库偶发读不到数据

**文件**：`src/tests/test_storage_transfer_history.cpp`，`testReopenDatabase()`

#### 现象

`testReopenDatabase()` 在全量或批量运行时偶发失败：`loaded.size() == 1` 为假。单独重跑通常通过，连续执行约 20 次会出现约 1 次失败。这种“单测正常、批量偶发”的特征说明问题更可能在外部资源生命周期，而非查询条件或断言本身。

#### 根因与排查

仓储使用 SQLite WAL 模式。写入可能先保留在 `.sqlite-wal` 文件中，而不是立即合并到主 `.sqlite` 文件。第一个 `SqliteDatabaseProxy` 离开作用域时虽然会关闭其连接，但 Qt 的连接池仍可能保留当前线程的底层数据库句柄。

紧接着使用相同文件名重新 `openDatabase("reopen.sqlite")` 时，新连接在特定时序下只读到主库，未看到仍由旧句柄关联的 WAL 内容，于是查询结果为空。因为计时和连接销毁顺序会随批量测试而变化，问题表现为偶发而不是稳定复现。

排查中先确认写入接口返回成功，再将问题缩小到“写入后立即重新打开同一路径”的边界；重复运行测试后，才确认这不是查询排序、过滤条件或数据构造错误，而是 WAL 与 Qt 连接生命周期没有显式收口。

#### 修复

在旧代理仍存活时取得当前线程连接，执行 checkpoint 强制合并 WAL，再显式关闭连接：

```cpp
QSqlDatabase conn = database->connectionForWorkerThread(&error);
QSqlQuery q(conn);
q.exec("PRAGMA wal_checkpoint(TRUNCATE)");
conn.close();
```

旧代理和 `QSqlDatabase` 局部句柄都离开作用域后，遍历并移除当前线程残留的 Qt 连接：

```cpp
for (const QString &name : QSqlDatabase::connectionNames())
    QSqlDatabase::removeDatabase(name);
```

最后才重新打开同一数据库文件并查询。顺序不能颠倒：`removeDatabase()` 前不能保留同名连接的 `QSqlDatabase` 或 `QSqlQuery` 对象，否则 Qt 会报警告，连接也不会被可靠释放。

#### 经验

SQLite 的“关闭数据库”不等于“测试进程中的所有 Qt 连接对象都已释放”。涉及同一文件的关闭、重开、临时目录清理或数据库迁移测试时，需要同时处理三层状态：事务和 WAL 是否落盘、连接是否关闭、Qt 连接注册表是否已清理。

对生产代码不应为了测试方便而全局删除所有连接；这里的清理仅限独立的单线程测试上下文。生产环境应按连接名和所属线程管理连接，并在不再持有 `QSqlDatabase`、`QSqlQuery` 后再调用 `removeDatabase()`。

### 49.4 本阶段的验收重点

这次问题也补足了传输历史的验收范围：除了验证写入、按条件查询、幂等更新、重启恢复和“删除历史不删除文件”，还必须编译所有测试目标，并多次或批量执行数据库重开用例。编译期错误通常暴露的是接口或宏的控制流契约；偶发失败则应优先检查共享文件、线程、连接池、端口和临时目录等生命周期资源，而不是先怀疑业务判断。

## 50. Stage 6 阶段 E：历史视图、保留清理与异步边界

**日期**：2026-06-25

阶段 E 的目标不是把 SQL 调到 QML，而是把阶段 C、D 已经稳定的仓储能力变成可管理的桌面功能：聊天记录可向上分页、传输历史可筛选、用户可删除或清空本地记录，并可设置自动保留期限。核心约束仍然不变：页面只能表达用户意图，应用层编排异步任务，SQLite 只在 storage 层出现。

### 50.1 HistoryController 是历史功能的唯一应用层入口

新增 `HistoryController` 后，QML 通过 `AppController.history` 访问受控操作，而不是拿到 Repository 或数据库对象。控制器持有 `IMessageRepository`、`ITransferHistoryRepository`、`ChatManager`、`TransferSessionManager` 和 `ConfigManager` 的抽象协作关系；查询、删除和清理均提交给已有的 `DatabaseWorker` 串行执行，结果通过值类型回投主线程更新模型。

这条边界解决了两个问题：一是 UI 不会因查询历史或批量清理而阻塞；二是核心层不需要知道 SQLite 的表结构或 `QSqlQuery`。验收时专门检索 QML、`Main.qml` 与 `HistoryController`，确认不存在 `QSqlDatabase`、`QSqlQuery`、SQL 文本或数据库路径泄露。

### 50.2 聊天翻页不能直接“再 append 一页”

消息仓储按 `sent_at DESC, message_id DESC` 返回最近一页；聊天界面却按时间正序显示。向上翻页时，如果直接把查询结果追加到模型尾部，历史消息会出现在最新消息之后，时间线立刻错乱。

最终流程是：从当前模型第一条消息取得 `sentAt + messageId` 作为 `MessageCursor`，在存储线程查询更早一页；回到主线程后按正序转换并通过 `prependHistoryMessages()` 插入模型顶部。模型层使用精确的 `beginInsertRows()` 通知，消息 ID 集合继续承担去重职责。这样可同时保证游标推进、同一时间戳下不重不漏，以及 QML 列表不因整体重建而跳动。

`test_history_controller` 为这条行为增加了分页游标推进和无重复记录用例。这里的经验是：分页排序方向、数据库返回顺序和 UI 展示顺序必须一起设计，不能只看单次 SQL 是否正确。

### 50.3 删除语义必须区分“历史”和“真实文件”

阶段 E 新增了删除单条消息、删除会话、删除传输记录、清空全部聊天记录和清空全部传输历史。删除聊天会话通过外键级联移除消息；清空聊天删除会话表，保留 `peer_devices`；清空传输历史只删除 `transfer_history`。传输记录没有保存文件路径，因此仓储层也没有删除文件的能力。

这种限制是有意设计：历史管理按钮不应意外删除接收文件或发送源文件。传输历史界面和确认对话框明确写为“仅删除本地历史记录”，对应测试分别验证删除目标性，以及清空聊天/传输后设备目录仍存在。

### 50.4 保留期限是配置与后台任务的组合

`ConfigManager` 增加 `retentionDays`，`0` 表示永久保留，设置页提供 7、30、90 天选项。修改后写入 `QSettings`，下次启动仍可恢复。`HistoryController` 以当前 UTC 时间减去配置天数作为严格过期边界，异步调用消息和传输仓储的过期清理；应用启动时先执行一次，随后每小时执行一次。

清理只影响过期聊天消息和传输历史，既不删除设备目录，也不影响在线 P2P 链路。测试覆盖过期记录被删除、较新记录保留，以及 `retentionDays` 跨重启持久化。

### 50.5 测试基础设施的误判：Worker 不拥有线程

新增 `test_history_controller` 时，第一版测试错误假设 `DatabaseWorker` 自己提供 `start()` 和 `stop()`。实际实现中，Worker 只负责将任务投递到其所属线程，线程生命周期由外部 `QThread` 管理：创建 Worker 后调用 `moveToThread()`，测试结束时退出并等待线程。

这不是给 Worker 补两个便利方法的问题。若让 Worker 同时管理自身线程，会混淆 QObject 所属线程、析构时机和任务队列的责任。修复后测试按生产代码相同的 `QThread + moveToThread()` 方式建立隔离环境，能够覆盖异步回投而不会制造第二套生命周期模型。

### 50.6 链接错误说明测试 target 也需要完整依赖图

`test_history_controller` 第一次链接时出现 `ApplicationPaths`、`HistoryController`、`TransferSessionManager` 等未定义符号。根因不是实现缺失，而是 CMake 的测试 target 只加入了测试源文件，没有把其实际使用的应用层、网络辅助和路径实现一并加入。

修复时补齐 `history_controller.cpp`、`application_paths.cpp`、`transfer_session_manager.cpp`、`file_sender_worker.cpp` 等必要源文件和目标依赖。这个过程再次说明：单测并不自动获得应用 target 的链接闭包；每个测试 target 都应显式声明其需要的生产源文件和库。

### 50.7 阶段验收结果

阶段 E 最终构建通过，`ctest` 共执行 15 个测试目标，全部通过；其中 `test_history_controller` 覆盖 12 项场景，包括聊天分页、传输设备/状态筛选、定点删除、清空后保留设备目录、过期清理和配置持久化。`git diff --check` 无输出，版本号在 README、顶层 CMake 与应用入口统一为 `v6.4.0`。阶段提交为 `601e0a4`（`接入本地历史视图和保留清理设置`）。

## 51. Stage 6 阶段 F：托盘、通知、后台运行与历史降级体验

**日期**：2026-06-25

阶段 F 是 Stage 6 的体验收口阶段。前面几个阶段已经把本地历史的表结构、仓储、异步任务、历史视图和保留策略接好；这一阶段要解决的是“用户真的把程序当桌面应用使用时会遇到什么”：关窗后是否还能后台收发、收到消息或传输请求时是否能提醒、数据库不可用时是否会误伤 P2P 主链路、退出时是否会丢掉刚提交的历史写入。

这一阶段没有把重点放在新增大功能，而是把系统边界补完整：托盘属于桌面壳层，通知属于 UI 体验层，本地历史失败属于降级路径，异步存储退出属于生命周期管理。它们都不能反向污染网络协议、仓储接口或 QML 与 SQL 的分层边界。

### 51.1 托盘设计：关窗不是退出，退出必须是显式动作

桌面文件传输工具的一个常见预期是：用户点窗口关闭按钮时，程序可以继续在后台接收请求。阶段 F 因此将主窗口关闭行为改为“托盘可用时隐藏主窗口”，真正退出交给托盘菜单中的“退出”。

实现上选择 QML 侧的 `Qt.labs.platform SystemTrayIcon`，而不是在 C++ 层引入 `QSystemTrayIcon` 和 `QtWidgets`。这样可以保持项目当前 Qt Quick 应用结构，不把 Widgets 依赖带进客户端目标。托盘菜单只暴露三个清晰动作：显示主窗口、隐藏到托盘、退出。托盘图标单击或双击恢复主窗口，关闭窗口时提示“应用仍在后台运行”。

这里的设计取舍是：托盘是平台能力，必须允许平台不可用。代码在关闭窗口时先判断 `trayIcon.available`，不可用时保持原有退出路径，避免在不支持托盘的桌面环境中把窗口隐藏后用户找不回来。

### 51.2 通知设计：提醒事件，不泄露敏感路径

通知覆盖三类事件：收到聊天消息、收到传输请求、传输完成。它们的共同原则是只提醒用户发生了什么，不把本地文件路径、完整文件名或过长聊天内容直接暴露到系统通知中。

聊天通知由 `ChatManager` 发出 `incomingMessageReceived(deviceId, senderName, preview)`。这个信号放在消息归档成功之后发出，并复用已有的 messageId 去重逻辑：只有 `appendMessage()` 真正插入新消息时才通知，因此重复帧不会触发重复提醒。预览文本使用简化和截断，避免换行、多空格或长文本破坏托盘通知显示。

传输请求通知只显示发送方和文件数量，不展示完整文件列表。传输完成通知使用通用文案“已完成一项文件传输”，不暴露接收路径。完整文件名和打开所在位置仍保留在应用内完成弹窗中，由用户主动查看。

这条边界很重要：系统通知不是应用内部详情页，它可能出现在锁屏、共享屏幕或系统通知中心。对文件传输应用来说，路径和文件名通常比“发生了一次传输”更敏感，默认通知应保守。

### 51.3 本地历史不可用不能影响 P2P 主链路

Stage 6 的本地历史是增强能力，不是文件传输和聊天的前置条件。阶段 F 因此补上 `AppController.localHistoryAvailable`，把 SQLite 初始化结果暴露给 QML。设置页在历史不可用时显示状态提示，让用户知道聊天和传输仍可正常使用，但本地记录可能缺失。

存储任务失败时，`DatabaseWorker::taskFinished(false, error)` 不会向上传播成致命错误，而是由 `AppController` 发出 `localHistoryOperationFailed()`。QML 收到后显示非阻塞提示，并可通过托盘通知提醒后台状态。这样即使磁盘权限、数据库文件损坏或临时写入失败，在线收发链路也不会被打断。

这个设计延续了前面阶段的原则：Repository 和 Worker 可以报告失败，应用层负责降级策略，UI 负责展示状态；任何一层都不应该因为历史写入失败而关闭网络连接或阻塞用户操作。

### 51.4 退出前排空异步任务：生命周期比“调用 quit”更复杂

阶段 C-E 已经把历史写入放到 `DatabaseWorker` 所在线程串行执行。阶段 F 暴露出一个新的生命周期问题：如果用户点托盘“退出”时，主线程直接 `QCoreApplication::quit()`，已经投递但尚未执行的历史任务可能来不及落库。

修复思路不是在退出时强行同步写库，而是让 Worker 支持一个队尾标记：`beginShutdown()` 通过 `QueuedConnection` 投递到存储线程。按照 Qt 事件队列的 FIFO 语义，当这个调用执行时，它之前提交的数据库任务已经处理完成。此时 Worker 停止接收新任务并发出 `drained()`，应用再真正退出。

这里需要注意两个边界：

1. `beginShutdown()` 必须排在 Worker 线程事件队列中，不能直接跨线程调用，否则无法证明它之前的任务都已执行。
2. 退出开始后要拒绝新任务，避免队列排空边界不断后移，造成退出卡住或行为不确定。

这类问题很容易在功能测试中漏掉，因为单次发送和单次关闭通常看起来正常；但从架构上看，只要存在异步写入，就必须定义退出时的队列收口语义。

### 51.5 验收中确认的历史遗留问题：MouseArea 与 test_file_transfer 偶发崩溃

阶段 F 验收时检查了 QML 规范项，确认本阶段没有新增 `MouseArea` 或 `var` 违规。检索命中的 `MouseArea` 属于历史遗留代码，不是阶段 F 引入。这个结论很关键：阶段验收要区分“本次变更引入的问题”和“仓库既有技术债”，否则容易把小阶段收口演变成无边界重构。

全量测试中 `test_file_transfer` 出现过一次偶发 SegFault，但重跑 3 次均通过，判断为已知多线程竞态，没有归入 Stage F 新问题。这里仍应记录风险：偶发崩溃即使不阻塞本阶段提交，也不应被遗忘。后续如果进入传输稳定性专项，应优先梳理该测试的线程停止、socket 生命周期和 worker 析构顺序。

### 51.6 阶段验收结果

## 52. 托盘退出 Bug：关窗语义、后台进程与异步存储收口

**日期**：2026-06-25

阶段 F 验收通过后，又暴露出一个典型的桌面体验 Bug：用户点击窗口关闭按钮时，程序直接隐藏到后台，没有询问用户是要最小化到托盘还是退出程序；同时，程序已经隐藏到后台后，托盘菜单中的“退出”不能可靠关闭进程。

这个问题表面上是 UI 交互缺一个确认框，实际牵涉三层状态：QML 窗口关闭事件、系统托盘菜单动作、C++ 应用退出和数据库 Worker 排空。只改其中一层，都可能形成新的问题。

### 52.1 现象与用户感知

第一版托盘逻辑把 `ApplicationWindow.onClosing` 改成了“托盘可用时直接 `hide()`”。这符合“关闭窗口后后台运行”的预期，但没有给用户明确选择。对于桌面应用来说，窗口右上角关闭按钮存在两种常见语义：退出程序，或者最小化到托盘。GridYard 又是文件传输工具，后台继续监听会影响端口占用、托盘常驻和系统资源，因此不能静默决定。

第二个问题更严重：应用隐藏到托盘后，如果托盘菜单“退出”不能结束进程，用户就失去了关闭后台服务的入口。这个 Bug 在视觉上不明显，因为窗口已经消失；但进程仍在、P2P 端口仍被占用，下一次启动或测试时会出现端口冲突、重复实例或“看不到窗口但程序还活着”的问题。

### 52.2 排查难点：退出动作会再次撞上 onClosing

这次排查的关键点是区分“用户请求关闭窗口”和“应用已经决定退出”。如果所有关闭路径都经过同一个 `onClosing`，那么托盘菜单点击“退出”时，也可能再次触发窗口关闭事件，结果又被 QML 拦截成隐藏到后台，退出动作就被吞掉。

因此，QML 层需要一个明确的状态标记：普通点击窗口 X 时拦截并弹出选择框；当用户已经选择“退出程序”或从托盘菜单退出时，设置允许关闭标记，让后续关闭流程不再被当作“隐藏到后台”处理。

最终引入 `_allowWindowClose`，并把退出入口统一为 `requestApplicationQuit()`：

- 点击窗口 X：如果 `_allowWindowClose` 为假，则 `close.accepted = false`，打开关闭选择对话框；
- 点击“隐藏到后台”：只执行 `hideToTray()`，不调用退出；
- 点击“取消”：只关闭对话框；
- 点击“退出程序”或托盘菜单“退出”：先设置 `_allowWindowClose = true`，再调用 `AppController.quit()`。

这样关闭窗口、隐藏托盘和退出程序三种动作有了明确分工，不再互相覆盖。

### 52.3 C++ 退出不能只依赖理想路径

阶段 F 已经为了避免丢失历史写入，在 `AppController::quit()` 中先向 `DatabaseWorker` 投递 `beginShutdown()`，等 Worker 发出 `drained()` 后再退出。这条路径在正常情况下是对的：退出前尽量排空已提交的历史任务，避免刚收到的消息或传输历史还没落库。

但这个设计也带来另一个风险：如果 Worker 线程事件循环异常、队列没有及时响应，或者退出时某个边界条件导致 `drained()` 没有回来，应用就会一直留在后台。用户此时看不到窗口，只能手动杀进程。

修复时没有取消“先排空”的设计，而是增加 3 秒兜底：

- 正常路径：收到 `DatabaseWorker::drained` 后退出；
- 异常路径：3 秒内没有响应，也调用 `QCoreApplication::exit(0)` 结束事件循环。

这个取舍比“立即退出”稳，也比“无限等待”可控。它承认本地历史是增强能力，不能为了等待历史写入而让用户无法关闭程序。

### 52.4 实现细节上的坑

这次还遇到一个 Qt 细节：`Qt::QueuedConnection | Qt::SingleShotConnection` 按位或后的类型不是 `Qt::ConnectionType`，直接传给 `connect()` 会导致编译失败。需要显式 `static_cast<Qt::ConnectionType>(...)`。

这个错误本身不复杂，但提醒我们：Qt 的枚举位组合虽然常见，不同 API 对类型的要求并不完全一致。尤其是在信号槽连接这种模板重载很多的接口上，一个类型不匹配会产生很长的编译错误，排查时要先看最后的“cannot convert ... to Qt::ConnectionType”，不要被前面一串候选函数干扰。

QML 侧也做了保守处理：没有依赖不确定的 `DialogButtonBox` 角色回调，而是使用显式 `Button` 的 `onClicked` 分别处理“隐藏到后台”“退出程序”和“取消”。这样代码更直接，也避免不同 Qt 版本或控件角色信号差异造成运行期问题。

### 52.5 验收结果与限制

该修复提交为 `39625e9`（`修复托盘后台退出和关窗确认`）。验收结果如下：

- 构建通过；
- 全量 `ctest` 15/15 通过；
- `git diff --check` 通过；
- 未新增 `MouseArea`；
- 未新增 `var`；
- 未引入 `QtWidgets` 或 `QSystemTrayIcon`；
- QML/UI 层无 SQL 泄漏；
- 代码审查确认 `closeChoiceDialog` 包含三个选择，`_allowWindowClose` 防止退出动作被再次拦截，`AppController::quit()` 有 3 秒兜底退出。

验收环境是 headless 服务器，没有真实桌面显示器，因此窗口关闭弹窗、隐藏到后台、托盘菜单恢复、托盘菜单退出和退出后无残留进程仍需要在有桌面的 Linux 环境补做手工确认。自动化测试能证明代码未破坏现有 15 个测试目标，但不能替代托盘交互的真实桌面验证。

这次 Bug 的经验是：托盘不是简单的“窗口 hide/show”。一旦应用支持后台常驻，就必须明确三件事：用户关闭窗口时是否真的退出、后台状态下用户如何找回窗口、后台状态下用户如何可靠结束进程。只要这三件事有一个没有闭环，桌面体验就会从“方便后台运行”变成“程序关不掉”。

### 52.6 聊天输入框占位提示遮挡真实输入

托盘退出 Bug 修复后，同一轮 6.6.1 补丁又处理了聊天输入框的显示问题：用户输入文字时，输入框里的“输入消息”提示没有隐藏，还会变色并遮挡已经输入的内容。

根因在于 `TextArea` 使用了内置 `placeholderText`，同时又自定义了背景和布局。Qt Quick Controls 的内置占位绘制由控件内部状态控制，在自定义背景、禁用状态和文本区域重绘组合下，表现不够可控。这里如果继续调控件内部颜色或状态，很容易只修掉“变红”，但仍然不能保证“有内容时一定隐藏”。

最终做法是禁用内置 `placeholderText`，改为在输入框容器里放一个显式 `Label`：

- `messageInput.placeholderText` 置空，避免控件内部再绘制占位文字；
- 外层 `Label` 只在 `messageInput.text.length === 0` 时显示；
- 在线时显示“输入消息”，离线时显示“设备离线，无法发送”；
- 一旦用户输入任何字符，提示 Label 立即隐藏，不再遮挡真实文本。

这个修复的经验是：输入框占位提示属于视觉状态，不一定要依赖控件内置实现。只要项目已经对控件背景和布局做了较多定制，用一个受业务状态显式控制的 Label，反而比继续调控件内部 placeholder 更稳定。

## 53. AppController 不是“挂 QML 的工具类”

**日期**：2026-06-28

Stage 6 做完以后，我们重新复盘了一次程序入口。最初 Qt Quick 模板里的写法很自然：`main.cpp` 创建 `QGuiApplication`，再创建 `QQmlApplicationEngine`，最后 `loadFromModule("...", "Main")`。这在小例子里没有问题，但放到四层架构项目里，老师指出它会让程序看起来像“先挂 UI 模块，再由 QML 反向触发应用层对象创建”。

老师原话大意是：controller 对象应该负责整个系统初始化，包括 UI 层和其他软件层初始化。如果 `main.cpp` 直接使用 `QQmlApplicationEngine` 挂 UI 模块，四层系统架构的入口关系就变了。

### 53.1 当时误解的点

我们一开始把 `AppController` 理解成“给 QML 调用的后端单例”。所以 `main.cpp` 里先加载 QML，QML 再通过 `AppController` 单例拿对象，看起来也能跑。

但从架构表达上看，这样的入口方向是不清楚的：

```text
main.cpp
  -> QQmlApplicationEngine
      -> Main.qml
          -> AppController
```

这会让表现层像是系统组装入口。对课程要求的四层架构来说，更合理的表达应该是：

```text
main.cpp
  -> QGuiApplication
  -> AppController::singleton()
      -> 初始化应用层对象
      -> 初始化数据管理层入口
      -> 初始化 QML UI 引擎
  -> app.exec()
```

### 53.2 最后的修改

我们把 `QQmlApplicationEngine` 从 `main.cpp` 移到了 `AppController` 内部，由 `AppController::initializeUi()` 创建并加载 `Main.qml`。`main.cpp` 只保留启动准备和显式创建组合根：

- 创建 `QGuiApplication`；
- 解析命令行参数；
- 初始化日志和元类型；
- 调用 `AppController::singleton()`；
- 检查 `controller->uiReady()`；
- 进入事件循环。

同时，`AppController::create(QQmlEngine *, QJSEngine *)` 只返回同一个 `singleton()`，避免 QML 单例机制和 C++ 侧各自创建两个控制器。

### 53.3 这次留下的经验

`QQmlApplicationEngine` 本身不是错，错在把它放在业务项目的入口位置后，架构表达会变成 UI 在前、控制器在后。以后再做 Qt Quick 项目，要先区分两种情况：

- 普通教学示例或小工具：`main.cpp + QQmlApplicationEngine` 可以接受；
- 明确要求四层架构的业务项目：`main.cpp` 应显式创建 controller 组合根，UI 由 controller 后续初始化。

这不是语法问题，而是依赖方向和系统入口表达问题。

## 54. Broker 不是 Proxy：数据管理层不能塞进 Controller

**日期**：2026-06-28

老师还提醒过一个更细的问题：我们代码里有一些类叫 `Proxy`，但实际上做的是 broker 的事情。比如数据库连接、Repository、任务线程、历史写入顺序都被某个对象统一代管时，这更像 **Broker（代管者）**，不是 Proxy。

### 54.1 原先的问题

Stage 6 初版里，`AppController` 直接持有了不少数据层细节：

- SQLite 数据库入口；
- 设备、消息、传输历史 Repository；
- `DatabaseWorker`；
- 存储线程；
- 多个跨 Repository 的写入 lambda。

功能能跑，但 `AppController` 逐渐变成了“系统入口 + 网络组装 + UI 初始化 + 数据库线程 + Repository 编排”的混合类。老师说“数据管理层不应该放到控制器中，不符合四层结构设计”，指的就是这个问题。

### 54.2 排查时看到的危险信号

我们排查时看了几个信号：

1. `AppController` 头文件里是否出现大量 SQLite / Repository / Worker / Thread 成员；
2. `AppController` 构造函数里是否直接写多个数据库操作 lambda；
3. 数据库类名是否还叫 `Proxy`，但实际职责是连接代管、事务代管或表数据映射；
4. QML 是否有机会越过 controller 直接碰到数据层对象。

只要这些现象同时出现，说明“组合根”和“数据管理层”已经混在一起了。

### 54.3 最后的方案

我们新增 `LocalDataBroker`，让它负责：

- 初始化 SQLite 数据库；
- 持有 `SqliteDatabaseBroker`；
- 持有各个 Repository；
- 创建和管理 `DatabaseWorker`、存储线程；
- 编排聊天消息、传输历史、设备目录之间的写入顺序；
- 提供历史查询、删除、清空、过期清理等语义接口。

同时把命名改清楚：

- 数据库连接与事务入口：`SqliteDatabaseBroker`；
- 具体表读写：`SqliteDeviceRepository`、`SqliteMessageRepository`、`SqliteTransferHistoryRepository`；
- 本地数据层代管者：`LocalDataBroker`。

这样 `AppController` 仍然负责创建 `LocalDataBroker`，但不再直接知道里面有多少 Repository、Worker 或线程。

### 54.4 这次留下的经验

类名会影响老师和队友对架构的理解。`Proxy` 不是“听起来高级的间接层”，它有明确模式语义：代理真实对象并保持相似接口。我们这些类真正做的是代管和数据映射，用 `Broker` / `Repository` 更准确。

以后如果一个类负责“持有多个底层对象并协调它们完成一组用例”，优先考虑叫 `Broker`、`Coordinator` 或 `Facade`；如果它负责某类数据的持久化读写，叫 `Repository`；不要随手叫 `Proxy`。

## 55. Getter 不一定错，但拿到底层对象就危险

**日期**：2026-06-28

做完 `LocalDataBroker` 后，我们又发现一个容易被忽略的问题：虽然 `AppController` 不再直接持有 Repository，但 `LocalDataBroker` 为了让 `HistoryController` 工作，临时暴露了几个 getter：

```cpp
DatabaseWorker *worker() const;
IMessageRepository *messageRepository() const;
ITransferHistoryRepository *transferHistoryRepository() const;
```

这看起来只是“取一下依赖”，但从封装角度看，它等于把 broker 内部最核心的东西又递出去了。`HistoryController` 拿到这些对象后，仍然可以绕过 broker 自己投递数据库任务、自己调用 Repository。这样 broker 只是换了个地方存对象，并没有真正形成边界。

### 55.1 怎么判断 getter 是否破坏封装

我们后来按下面几类区分：

- **可以接受**：返回值类型状态，比如 `bool isAvailable()`、`QString deviceName()`、`QVariantList transfers()`。这些是快照或只读状态。
- **可以接受但要谨慎**：返回 UI 门面对象，比如 `AppController::transferController()`。它暴露的是有意设计过的 QML API。
- **危险**：返回内部 worker、thread、socket、database、repository、可变容器引用。这类 getter 会让外部对象参与内部生命周期和编排。

所以 getter 不是原罪，关键是它返回的是“外部应该知道的状态”，还是“内部用来工作的零件”。

### 55.2 最后的修改

我们删除了 `LocalDataBroker` 的 worker/repository getter，改为提供业务语义方法：

- `loadMessages(...)`
- `queryTransfers(...)`
- `deleteMessage(...)`
- `deleteConversation(...)`
- `deleteTransfer(...)`
- `clearAllMessages(...)`
- `clearAllTransfers(...)`
- `deleteExpiredRecords(...)`

`HistoryController` 现在只知道自己要“加载更多历史”“删除记录”“清理过期记录”，不再知道这些动作背后是 `DatabaseWorker` 还是哪个 Repository。

### 55.3 这次留下的经验

如果一个 getter 的返回值会让调用方知道“这个类里面是怎么实现的”，就要停下来想一想。更好的办法通常是把调用方真正想做的动作写成语义方法，让拥有内部对象的类自己完成编排。

这次我们真正理解了“封装不是把成员设成 private 就结束了”。如果 private 成员可以通过 getter 原样拿出去，封装还是破的。

## 56. QML 只应该看到 ViewModel / Controller，不应该看到内部 Manager

**日期**：2026-06-28

在梳理 getter 时，我们还发现了另一个问题：QML 通过 `AppController.discovery`、`AppController.transfer`、`AppController.chat`、`AppController.history` 直接拿到了内部对象。虽然这些对象本身就是 QObject，也能绑定属性和调用方法，但从命名和职责上看，`DiscoveryService`、`TransferSessionManager`、`ChatManager` 更像内部服务或管理器，不应该直接成为 UI API。

### 56.1 问题在哪里

直接暴露内部 Manager 有两个隐患：

1. QML 能看到对象上所有 `Q_PROPERTY`、`Q_INVOKABLE` 和信号，接口面会越来越大；
2. 后续开发者看到 `Q_INVOKABLE`，容易继续把 UI 命令加到 Manager 上，导致 Manager 同时承担业务管理和表现层 API。

这和前面的 broker 问题很像：对象虽然能用，但架构边界不清楚。

### 56.2 最后的修改

我们加了三层薄门面：

- `PeerDiscoveryViewModel`：只暴露在线设备列表和刷新命令；
- `TransferController`：只暴露传输列表、接受/拒绝/取消/移除等 UI 命令；
- `ChatController`：只暴露消息模型、发送文本和清理会话等 UI 命令。

`AppController` 对 QML 暴露：

```text
AppController.peerDiscoveryViewModel
AppController.transferController
AppController.chatController
AppController.historyController
```

同时把内部类里的 QML 痕迹去掉：

- `DiscoveryService` 去掉 `QML_ANONYMOUS`、`Q_PROPERTY`、`Q_INVOKABLE`；
- `TransferSessionManager` 去掉 QML 属性和 `Q_INVOKABLE`；
- `ChatManager` 去掉 `QML_ANONYMOUS` 和 `Q_INVOKABLE`。

### 56.3 这次留下的经验

QML 能调用某个 QObject，不代表它就应该调用。我们现在更倾向于把“给 UI 用的对象”明确命名为 `Controller` 或 `ViewModel`。内部服务类可以继续继承 QObject、继续发信号，但不把它们作为 QML API 暴露。

这样有一个额外好处：看 QML 代码时，一眼就能知道自己在调用表现层门面，而不是直接操作网络服务或会话管理器。

## 57. Qt Creator 里的 CMake 分组不是小事

**日期**：2026-06-28

做完 domain 层后，我们发现 `domain/` 下两个头文件在 Qt Creator 里的显示位置不对。代码能编译，但项目树看起来像它们属于别的 target。这个问题很容易被当成“IDE 小毛病”，但对课程项目来说，老师看项目结构时，Qt Creator 里的分组就是第一印象。

### 57.1 问题原因

`gy_domain` 是头文件接口层，最初写法是：

```cmake
add_library(gy_domain INTERFACE)
target_sources(gy_domain INTERFACE
    history_records.h
    history_repositories.h
)
```

问题在于 `INTERFACE` sources 会作为 usage requirement 传播给链接它的目标。`gy_storage` 和 `appGridYard` 链接了 `gy_domain`，所以 Qt Creator 有可能把这两个 domain 头文件显示到消费目标下面，而不是稳定显示在 `client/domain` 自己的分组里。

### 57.2 最后的修改

我们保留 `gy_domain` 的 INTERFACE 属性，因为它确实是头文件接口库；但把头文件 sources 改成 `PRIVATE`，只挂到 `gy_domain` 自己的项目树：

```cmake
add_library(gy_domain INTERFACE)
target_sources(gy_domain PRIVATE
    history_records.h
    history_repositories.h
)
target_include_directories(gy_domain INTERFACE ${CMAKE_CURRENT_SOURCE_DIR})
```

同时 source group 改成基于目录树的写法：

```cmake
source_group(TREE ${CMAKE_CURRENT_SOURCE_DIR} PREFIX "client/domain"
    FILES history_records.h history_repositories.h
)
```

这样 include 路径和链接依赖仍然向上游传播，但两个头文件不会再作为 `INTERFACE_SOURCES` 跑到别的 target 展示树里。

### 57.3 对全部分组的复查

这次顺手复查了项目中的分组逻辑：

- `appGridYard`：`core/`、`network/`、`ui/`、`utils/`、`icons/` 都通过 `source_group(TREE ... PREFIX ...)` 展示；
- `gy_storage`：作为独立静态库展示在 `client/storage`，没有混入 app target；
- `gy_shared`：独立展示在 `shared`；
- `gy_domain`：修正后独立展示在 `client/domain`，但 include 路径仍传递给 storage 和 app；
- tests：测试目标按各自 executable 展示，暂时没有继续细分 source group，因为测试文件数量和结构还可控。

### 57.4 这次留下的经验

CMake 的 `target_sources` 不只是影响“哪些文件参与构建”，还会影响 IDE 项目树。特别是 `INTERFACE` target，`INTERFACE_SOURCES` 会传播到消费方。头文件接口库如果只是想让 IDE 显示自己的头文件，不应该把它们作为 `INTERFACE` sources 传播出去。

以后新增模块时，我们会同时检查两件事：

1. 构建依赖是否正确；
2. Qt Creator 里展示的 target 和 source group 是否能反映架构分层。

## 58. 把聊天和传输合成一条会话流，比删页签麻烦

**日期**：2026-06-28

v6.7.0 做了一次界面上的小重构：原来设备会话页里有“聊天”和“传输”两个页签，聊天消息在 `ChatView.qml`，传输任务在 `DeviceSessionView.qml` 里单独一个 `ListView`。从使用习惯看，这不太像即时通讯软件。用户发文件时，其实更希望看到“我在这段对话里发了一个文件”，而不是切到另一个传输列表里找进度。

所以我们把它改成了统一会话流：文本消息和传输任务按时间混排，传输任务作为一种卡片出现在聊天记录中。

### 58.1 第一版想简单了

一开始以为只是把传输 `ListView` 挪进聊天页面，然后删掉 `TabBar` 就行。但真正改时发现有几个问题：

1. 聊天消息来自 `ChatMessageModel`，传输记录来自 `TransferController.sessions`，它们不是同一个模型；
2. 聊天历史支持向上分页加载，传输任务会频繁更新进度，两个刷新节奏不一样；
3. 发送文件后原逻辑会主动切到“传输”页，删掉页签后这些调用必须一起清掉；
4. 传输卡片内部已经有取消、移除、删除本地文件、文件夹展开等操作，不能为了混排重写一份相似卡片；
5. QML delegate 里如果同时写聊天分支和传输分支，即使某个分支不可见，也可能因为绑定求值而读取到不存在的字段。

最后我们没有动 C++ 消息模型，也没有把传输记录塞进聊天表，而是新建了 `ConversationTimelineView.qml`，在 QML 层把两份数据合成一个展示数组：

```text
{ kind: "message", sortTime, ... }
{ kind: "transfer", sortTime, ... }
```

这样做的好处是改动集中在表现层。聊天收发、文件传输、数据库恢复和历史清理都继续走原来的 Controller。

### 58.2 混排模型的刷新问题

合成数组不是 Qt 原生模型，它不会自动知道底层哪一行变了。所以我们显式监听两类信号：

- `ChatController.messagesChanged(deviceId)`：当前设备聊天消息变化时重建时间线；
- `TransferController.sessionsChanged()`：传输进度或状态变化时重建时间线。

重建以后如果用户本来在底部，就自动滚到最新；如果用户正在翻历史，就不强行拉到底部。这个细节很重要，否则一个大文件传输中的进度刷新会不断把列表拖回底部，用户根本看不了前面的记录。

### 58.3 delegate 隐藏分支也会踩坑

统一时间线的 delegate 里同时有聊天气泡和传输卡片两个分支。看起来可以简单写：

```qml
visible: modelData.kind === "message"
text: modelData.content
```

但 QML 的绑定不等于“不可见就不求值”。如果当前项是传输记录，聊天分支虽然不可见，里面的 `modelData.content`、`modelData.senderName` 仍然可能被求值，结果就是控制台出现绑定警告，严重时还会影响尺寸计算。

最后我们在 delegate 顶部做了安全字段：

```qml
readonly property bool isMessage: modelData.kind === "message"
readonly property string safeContent: isMessage ? String(modelData.content || "") : ""
```

传输卡片那边也给 `sessionId`、`fileName`、`progress`、`fileList` 等字段补了默认值。这个写法啰嗦一点，但能保证混合 delegate 不会因为另一种类型缺字段而报错。

### 58.4 头像显示不是简单加一个圆

统一会话流做完后，又补了一个聊天软件里很常见的小细节：连续消息不要重复显示头像。

规则最后定成这样：

- 第一条聊天消息显示头像；
- 如果上一条也是同一个方向、同一个发送者的聊天消息，就不重复显示头像；
- 如果上一条是传输卡片，或者发送方向发生变化，就重新显示头像；
- 传输卡片会打断聊天消息分组。

这里没有单独改 `ChatMessageModel`，而是在合成时间线排序之后给消息项补一个 `showAvatar` 字段。这样头像显示只是展示层逻辑，不会污染消息数据本身。

### 58.5 关闭确认框也有焦点问题

托盘功能做完后，关闭窗口时会弹出“关闭 GridYard”确认框，让用户选择隐藏到后台还是退出程序。后来发现一个体验问题：如果窗口已经被别的窗口挡住，或者系统准备关闭窗口时焦点不在 GridYard 上，确认框可能弹了但用户不容易注意到。

解决办法很简单：在 `onClosing` 里弹框前先调用已有的窗口恢复函数：

```qml
mainWindow.showMainWindow()
closeChoiceDialog.open()
```

`showMainWindow()` 内部会执行 `show()`、`raise()` 和 `requestActivate()`。这样关闭确认框出现时，主窗口会尽量回到前台并请求焦点。

### 58.6 这次留下的经验

界面合并不能只看“视觉上少了一个页签”。如果背后是两个不同数据源，真正要处理的是模型合成、排序、刷新、滚动策略和 delegate 安全绑定。

这次我们比较庆幸没有为了统一会话流去重写传输卡片，也没有改 C++ 数据结构。`TransferTaskCard` 继续负责传输卡片自己的操作，`ConversationTimelineView` 只负责“把什么东西放在什么位置”。这个边界清楚以后，后面修头像显示和关闭弹窗焦点时，改动范围都比较小。
