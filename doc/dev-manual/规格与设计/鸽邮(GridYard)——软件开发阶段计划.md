## 0. 文档使用说明

### 0.1 写给团队成员

- 这份文档是你**找事做**的入口。不分工，**任务公示在群里，谁感兴趣谁认领**。
- 每个阶段分 **必要任务** 与 **加分任务**：
  - **必要任务**：阶段进入下一阶段之前必须完成的；做不完整个团队就卡在这个阶段。
  - **加分任务**：时间宽裕、能力允许时做；提升项目质量，但不做不影响下个阶段开始。
- 不要跳阶段。下一阶段的任务依赖上一阶段的成果，提前抢做会因接口不稳返工。
- 选择任务的原则：
  1. **能做的优先做**（量力而行，不要选超出当前能力 2 个量级的）
  2. **没人接手的兜底**（如果某项必要任务 24 小时无人认领，Tech Lead 会派活）
  3. **加分任务凭兴趣**（喜欢 UI 的去打磨视觉，喜欢底层的去抠性能）

### 0.2 写给 Tech Lead

- 每阶段开始前，把该阶段的必要任务清单贴进群公告，召集认领。
- 每阶段结束前，按"验收标准"逐项确认；不达标不允许进入下一阶段。
- 加分任务可以滚动到后续阶段，不必强求当阶段完成。
- 阶段切换时打 git tag：`stage-0-done` / `stage-1-done` ... 便于事后回顾节奏。

**核心交付定义**：

- **MVP（最小可行产品）= Stage 0 + 1 + 2 + 3** — 两机能互相看见、能传一个文件
- **V1.0 完整版 = MVP + Stage 4** — 文件夹、SHA-256、异常处理与协议防护
- **V1.5 局域协同版 = V1.0 + Stage 5** — 在线设备之间可直接发文本聊天（纯 P2P）
- **V1.6 本地数据版 = V1.5 + Stage 6** — SQLite 本地聊天记录与传输历史、托盘、体验打磨
- **V2.0 校园网增强版 = V1.6 + Stage 7** — 跨 AP 发现、直连探测、协调节点与中继兜底

**最低交付底线**：必须达到 **V1.6 本地数据版**（Stage 0–6）。这一档既覆盖老师要求的四层架构（数据管理层落地），又包含可演示的文件直传与局域网在线聊天。Stage 7 校园网可达性增强按子阶段独立决定是否启动。

**关键演进决策**：

- 保留当前 TLV/P2P 文件传输架构，不整体改写为 LocalSend REST 或 IPMSG；借鉴 LocalSend 的版本、能力、token、部分接受、限流与发现兜底设计。
- **在线聊天优先用 P2P 实现**：在线设备之间的文本消息走现有 UDP 发现 + TCP + FrameCodec 通道直发，不依赖账号登录。这是项目 P2P 内核的自然延伸。
- 本地数据层统一承载聊天记录与传输历史，不要求登录；QML 只能通过 Controller/Repository 使用数据。
- **Stage 7 优先解决校园网 AC+AP 可达性**：UDP 广播被 AP 或网关隔离时，先通过手动地址、历史端点、定向 Hello、协调节点和连通性探测尽量恢复直连；只有确认直连不可达时才使用中继兜底。
- **中继不是文件云盘**：中继只转发在线传输流量，不保存文件内容、不做账号漫游、不替代本地历史。大文件优先直连，直连失败才允许用户显式切换到中继。
- 登录、对话历史漫游和离线消息暂存整体后移为后续加分项，不作为当前下一阶段默认目标。

### 风险点

- **接收侧后台化的 socket 线程归属**：socket 由 `P2pServer` 在主线程 `nextPendingConnection()` 取得，移线程时须连同 socket 一起 `moveToThread`，且接管前不要在主线程读它的数据。
- **SHA-256 同步计算阻塞**：大文件 hash 必须随写盘在后台线程增量计算，不能回到主线程一次性算。

## Stage 5 — 局域网在线聊天

### 目标

> 在已发现的在线设备之间直接收发文本消息：在 A 的聊天窗口输入文字，在线的 B 立即收到并显示。**纯 P2P，不依赖服务端、不依赖登录、本阶段消息只存内存。** 离线消息暂存后移为更后续加分项，当前 Stage 7 优先解决校园网可达性。

### 入口条件

- Stage 4 完成（协议防护与接收侧后台化达标，FrameCodec 路由稳定）

### 设计要点

- **协议**：在 V1.0 低位段新增文本 Type 码，不触碰为服务端预留的 `0x1000` 段。
  - `0x0501 kTypeChatText` — P2P 在线文本消息（JSON 载荷）
  - `0x0502 kTypeChatAck` — 文本消息送达回执（加分项使用）
  - 文本消息 JSON 字段建议：`message_id`、`from_device_id`、`from_name`、`content`、`sent_at`。
- **连接策略**：聊天是双向、随时、短载荷，与文件传输"单向一次性大流量"形态不同。建议为每个对端维护一条轻量 TCP 长连接（在线期间复用），断线后按需重连；`P2pServer` 收到入站连接后按首帧 Type 区分这是文件传输还是聊天会话，分别交给接收 Worker 或聊天会话处理。
- **职责边界**：网络与连接管理在 C++（`ChatManager` / 聊天会话对象）；QML 只负责气泡渲染与输入，经 Controller 发送意图、绑定消息模型。文本内容的格式化（时间、换行、链接识别）属于 JavaScript/QML 展示层。

- ✅ 相关单测通过（协议码、消息编解码、连接分流）

### 风险点

- **同端口多用途的帧路由**：`P2pServer` 必须可靠区分"文件传输连接"和"聊天连接"，否则会把聊天帧喂给接收 Worker。建议以首帧 Type 判定连接用途。
- **长连接生命周期**：聊天连接的建立、复用、断线重连要与设备在线状态联动，避免对离线设备反复重连。
- **不要为聊天改动文件传输主链路**：聊天是新增旁路，FileSenderWorker / FileReceiverWorker 的传输逻辑保持不动。

### 与设计文档对应

- 实现规格说明书 P2P 子系统中"P2P 局域网在线文本聊天"需求
- 落实 QML / JavaScript / C++ 职责边界（聊天的网络在 C++，展示在 QML/JS）

## Stage 7 — 校园网可达性增强（跨 AP 与中继兜底）

### 目标

> 在 V1.6 本地数据层之上，优先解决校园网 AC+AP 环境下“同一校园网但 UDP 广播发现不到、不同 AP 下 TCP 直连不稳定、部分 SSID 开启客户端隔离”的问题。目标不是先做账号服务器，而是让用户在校园网大环境里尽量保持高速直传；只有直连失败时，才使用轻量协调节点或中继节点兜底。

现实边界必须先确认：如果 AP 隔离或网关策略彻底禁止两个无线客户端互相发起单播连接，纯客户端无法“打破”这个限制，只能通过一个双方都能访问的节点转发。Stage 7 的正确路线是“先探测、能直连就直连、不能直连再中继”，而不是盲目把文件传输全部改成中心服务端转发。

### 入口条件

- Stage 6 完成，本地 SQLite 与 Repository 边界稳定
- 已明确至少一个真实校园网测试场景：同 AP、不同 AP、不同楼栋或不同 SSID
- 已确认当前 UDP 广播、TCP 直连、手动 IP 连接在这些场景下的实际表现
- 在线聊天与文件传输无需账号登录也能继续使用
- 团队接受“中继会消耗中继节点带宽，无法保持所有场景满速”的事实

### Stage 7.0 — 网络诊断与连接策略基线

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.0.1 | 增加网络诊断面板：本机网卡、IP、子网、TCP 监听端口、发现端口、最近直连错误 | 用户能判断是发现失败、连接失败还是传输失败 | 1 天 |
| 7.0.2 | 增加对指定 IP:端口的定向 Hello 和 TCP 探测，不依赖广播 | 知道对端地址时可绕过 UDP 广播完成发现 | 1 天 |
| 7.0.3 | 扩展设备目录保存多个历史端点，并在广播失败时尝试历史端点重连 | 同一设备换 AP 后仍可通过最近端点探测 | 1 天 |
| 7.0.4 | 为发送流程加入连接候选排序：已发现端点、历史端点、手动端点 | 连接失败有明确降级路径和错误提示 | 0.5 天 |

### Stage 7.1 — 校园网发现兜底

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.1.1 | 增加“邀请连接”：复制或二维码展示 `deviceId + ip + port + name` | 不在同一广播域时仍可手动添加对端 | 1 天 |
| 7.1.2 | 支持配置固定校园网网段或白名单地址段，只对用户指定范围做轻量探测 | 不做全校园网暴力扫描，避免噪声和误报 | 1 天 |
| 7.1.3 | 增加定向 Hello 响应，收到探测后回发本机端点和协议能力 | 双方可完成互相登记，不依赖广播包穿透 | 1 天 |
| 7.1.4 | UI 区分“广播发现”“历史端点”“手动添加”“探测在线”四种来源 | 用户能理解设备为什么出现、是否可信 | 0.5 天 |

### Stage 7.2 — 轻量协调节点

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.2.1 | 新增可独立运行的 `rendezvous` 小节点，只保存短期在线端点和能力，不保存文件与聊天内容 | 不同 AP 下客户端可通过节点互相看到候选端点 | 2 天 |
| 7.2.2 | 客户端增加协调节点配置、心跳注册、候选端点拉取和过期剔除 | 协调节点离线时客户端回退到 Stage 7.1 | 1.5 天 |
| 7.2.3 | 增加直连打洞式探测：双方收到候选后同时尝试 TCP/UDP 探测 | 网络允许单播互通时最终走 P2P 直连 | 1.5 天 |
| 7.2.4 | 协调节点接入限流和简单访问口令，避免被无关设备刷爆 | 节点可在校园网内长期运行 | 0.5 天 |

### Stage 7.3 — 流式中继兜底

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.3.1 | 在协调节点上增加 TCP 流式中继通道，只转发在线会话字节流，不落盘 | AP 隔离导致直连失败时仍能传文件 | 2 天 |
| 7.3.2 | 客户端发送前执行直连测速和中继测速，默认优先直连，直连失败才提示中继 | 大文件不会无提示走慢速中继 | 1 天 |
| 7.3.3 | 中继链路复用现有 TLV 文件传输帧或增加最小封装，保持 FileSender/FileReceiver 主状态机不重写 | 文件夹、多文件、校验和取消能力不回归 | 2 天 |
| 7.3.4 | 中继节点增加带宽限制、最大并发、空闲超时和会话清理 | 单个异常传输不会拖垮节点 | 1 天 |

> **与 Stage 5/6 的关系**：在线单聊和本地历史仍由现有 P2P 与 SQLite 提供。Stage 7 不做账号登录、不做聊天记录漫游、不保存文件内容；只增强校园网内“发现得到、连得上、传得动”的网络可达性。

### 后续加分任务

| 编号 | 任务 | 价值 |
|:---|:---|:---|
| 7.A | TCP/UDP NAT 行为统计与可视化 | 帮助判断不同校园网策略 |
| 7.B | 端到端加密会话密钥协商 | 中继可用但看不到文件内容 |
| 7.C | 中继断点续传与多路径切换 | 长距离大文件更稳 |
| 7.D | 登录、记录漫游和离线消息 | 后续服务端能力 |

### 验收标准

- ✅ 每个子阶段均可独立演示与停止，不要求一次完成全部 Stage 7
- ✅ 同 AP、不同 AP、不同 SSID 至少三类场景有诊断结果和连接策略记录
- ✅ 广播失败但单播可达时，手动端点或协调节点可恢复 P2P 直连
- ✅ 单播被隔离时，中继可完成在线文件传输，且 UI 明确提示正在走中继
- ✅ 中继节点不保存文件内容，不要求账号登录，不影响本地历史
- ✅ V1.6 的 P2P 文件传输与在线聊天在无协调节点时仍保持可用

### 风险点

- **AP 隔离不是代码能直接破解的限制**。如果网络策略禁止客户端互通，必须使用双方都能访问的中继节点。
- 协调节点只能帮助互相找到候选端点，不能保证直连成功。
- 中继会消耗节点带宽，大文件性能取决于中继所在网络位置和出口策略。
- 不要做无边界网段扫描；校园网内主动探测必须由用户配置范围并限速。
- 时间不足时停在 7.1，仍能得到“手动连接 + 历史端点 + 定向探测”的实用增强。

### 与设计文档对应

- 实现 V2.0 设计书 §10 演进规划（在线聊天部分由 Stage 5 的 P2P 方案替代）
