## 第 1 页：封面

**主讲：高扬**

老师好，我们小组答辩的项目是 GridYard，中文名叫“鸽邮”。它面向同一局域网内的电脑，提供设备自动发现、点对点文件传输、在线聊天和本地历史记录功能。

项目使用 C++23 和 Qt6 QML 开发，构建工具是 CMake，本地数据使用 SQLite。最终版本是 v6.8.1，已经整理为可以运行、可以演示、也可以打包分发的桌面应用。接下来我会从选题原因、技术调研、开发过程、核心实现、测试发布和团队分工几个方面介绍。

## 第 2 页：项目背景与课程目标

**主讲：高扬**

GridYard 首先是课程学习大作业，不是要提出一个市场上从来没有的新需求，也不是要替代微信、QQ 或其他成熟工具。

我们选择“聊天会话 + 文件传输”这个方向，是因为这种交互已经被成熟产品验证过，用户很容易理解：选择一个联系人，进入会话，然后发送文字或文件。我们的重点是把这种熟悉的交互放到局域网 P2P 场景中，用 Qt/QML、C++ 网络编程、本地数据库和软件工程流程完整实现出来。

所以项目目标不是做一个概念界面，而是完成一个课程项目应有的工程闭环：能运行、能演示、能打包、能验证，也能解释清楚架构和实现过程。

## 第 3 页：市场调研与定位

**主讲：高扬**

开发前我们没有直接开始写一个“传文件工具”，而是先对同类工具和技术路线做了调研。调研的目的不是证明 GridYard 比成熟软件更强，而是确认哪些思想适合课程项目借鉴。

微信和 QQ 给我们的启发是，会话式交互非常成熟，聊天消息和文件记录放在同一个会话里是自然的。IPMSG 和飞鸽传书证明局域网 P2P 模型可行，设备可以不依赖账号系统和公网服务器，直接在同网段通信。LocalSend 给我们的启发是免配置发现、接收确认和跨平台分发体验。

最后 GridYard 的取舍是：借鉴 P2P 和会话式交互思想，但不照搬现成协议。我们用 Qt/QML 做桌面界面，用 UDP 发现设备，用 TCP 直连传输，用自研 TLV 协议组织业务消息，再用 SQLite 保存本地历史。

## 第 4 页：从 IPMSG 架构吸收了什么

**主讲：高扬**

IPMSG 给我们的主要价值不是某一段代码，而是局域网通信项目的基本组织方式：UDP 负责上线、发现和通知，TCP 负责可靠的数据传输，每台设备既可以发起连接，也可以监听连接。

GridYard 保留了这个架构思想，但没有照搬它的文本命令格式和线程模型。节点双角色落到 `P2pServer` 的入站监听和主动 TCP 连接上；UDP 发现落到 `DiscoveryService`；业务命令分发改成了 Type 码、首帧分流和 TLV 帧。

这样设计既符合局域网 P2P 的成熟经验，又能和 Qt 的事件循环、信号槽、Worker-Object 多线程模式、QML 界面和本地 SQLite 数据层结合起来，形成适合课程答辩解释的四层架构。

## 第 7 页：企业化工程实践

**主讲：高扬**

软件工程实践不是简单地“文档很多”，而是从选题到交付都有对应的流程。

前期我们先做可行性分析：局域网 P2P 适合课堂演示，Qt6 QML 符合课程方向，SQLite 可以支撑本地历史，AppImage 能作为最终交付形式。接着做需求分析，把范围收敛到设备发现、文件传输、在线聊天、本地历史和发布运行，没有把账号系统、服务端漫游、离线消息这些更大的功能混进当前版本。

设计阶段通过四层架构、UML、API 文档和阶段计划确定模块边界。编码阶段通过 CMake 分层、文件头版本记录、Change Log、命名规范和日志系统提高可维护性。收尾阶段再通过 CTest、双实例测试、日志和发布包验证，把课程项目从代码实现推进到可交付状态。

## 第 8 页：功能总览

**主讲：杜若贤**

最终用户看到的核心功能，是围绕“设备会话”组织起来的。

左侧是在线设备列表，来自 UDP 广播发现和心跳维护。用户选择某个设备后，进入统一会话时间线。聊天消息和文件传输记录会按时间顺序展示，文件发送、接收状态和历史记录不会被拆成两个完全割裂的工具。底部提供消息输入和文件发送入口，设置和历史功能用于修改设备名、接收路径以及查看本地记录。

统一会话是最终版本的重要变化。它借鉴了成熟聊天工具的交互方式，也把网络传输、在线聊天和 SQLite 本地历史整合成了一个完整的使用场景。

## 第 9 页：最终发布形式

**主讲：高扬**

项目没有停留在“源码能在开发机上运行”，而是整理成了更接近真实桌面应用的交付方式。

主交付物是 AppImage。选择它的原因是 Linux 下可以免安装运行，并且能把运行依赖一起打进包里，适合课堂演示和分发。portable 压缩包作为备用形式，方便解压后运行。源码构建则保留给需要重新编译和检查代码的场景。

Qt 程序发布时不能只拷贝一个可执行文件，因为它还依赖 Qt 插件、QML 模块、SQLite 驱动和 Widgets 相关库。我们的打包流程是先整理 AppDir，再补齐这些运行时依赖，最后生成 AppImage。后续继续完善时，可以补充 Windows 和 macOS 平台包，提高跨平台交付能力。

## 第 10 页：总体架构

**主讲：高扬**

总体架构分成四层，目的是把界面、业务逻辑、网络协议和本地数据分开。

最上面是 QML 表现层，负责设备列表、统一会话、聊天气泡、文件卡片和设置窗口。它只负责展示和交互，不直接处理 socket，也不直接写 SQL。第二层是应用逻辑层，负责业务状态和模块调度，包括 AppController、ChatManager、TransferSessionManager 和 HistoryController。第三层是网络与协议层，负责 UDP 发现、TCP 监听、首帧分流、文件收发和 TLV 编解码。最下面是本地数据层，负责 SQLite 数据库、设备目录、聊天历史、传输历史、迁移和仓储。

AppController 是应用组合根，负责在启动时把设备发现、P2P 服务、传输管理、聊天管理、历史控制器、配置和日志这些模块组装起来，再向 QML 提供统一入口。这样可以避免 UI、网络和数据库逻辑混写在一起。

## 第 11 页：设备发现设计

**主讲：冯春霖**

进入具体技术实现后，首先是局域网设备发现。GridYard 启动后，会通过 UDP 广播向同网段发送 Hello 消息，相当于告诉其他客户端“我在线”。其他 GridYard 客户端收到广播后，就可以更新自己的设备列表。

这个功能看起来简单，但实际开发时要处理多网卡环境。比如一台电脑可能同时连接有线网和 WiFi，如果只向默认广播地址发送，某些网段上的设备可能收不到。所以我们遍历本机网卡，过滤回环地址和不支持广播的接口，再向每个可广播的 IPv4 地址发送 Hello。

UDP 在这里只负责发现和心跳，不承载大文件。真正的文件和聊天数据会通过 TCP 直连传输。设备是否在线，则通过心跳和 `lastSeen` 时间来维护。

## 第 12 页：文件传输链路

**主讲：冯春霖**

文件传输采用 P2P TCP 直连，但不是一建立连接就直接发送文件内容。发送端会先整理元信息，包括文件名、文件数量、总大小、目录相对路径和 SHA-256 校验值，然后发送 TransferRequest。

接收端收到元信息后，先让用户确认是否接收。只有确认之后，发送端才开始正式传输文件数据。正式传输时不会一次性把大文件读进内存，而是按块发送，当前 chunk 大小调整为 8MB。接收端逐块写入本地文件，完成后再根据 SHA-256 校验文件完整性。

这样的流程可以让接收方在传输前知道自己要接收什么，也能让大文件、文件夹和多文件传输更稳定。传输状态最后会同步到统一会话时间线，并写入 SQLite 历史记录。

## 第 13 页：聊天与首帧分流

**主讲：冯春霖**

在线聊天加入以后，P2P 入站连接就不再只有文件传输一种用途。文件传输和聊天都基于 TCP，接收端收到一个连接时，必须先判断它到底是来发文件，还是来发聊天消息。

为了解决这个问题，我们约定 TCP 连接的第一帧必须携带 Type。`P2pServer` 收到连接后先读取首帧，根据 Type 做分流：如果是 TransferRequest，就交给文件接收 Worker；如果是 ChatText，就交给 ChatManager；如果是未知类型或无效帧，就关闭连接并写入日志。

这样设计的好处是，P2pServer 只负责连接入口和业务分流，不把文件接收、聊天处理和错误处理全部混在一个类里。后续如果增加新的业务类型，也可以继续通过 Type 扩展。

## 第 14 页：自研 TLV 协议的价值

**主讲：高扬**

自研 TLV 协议主要是为了解决 TCP 字节流没有消息边界的问题。TCP 只能保证数据按顺序到达，但不保证发送端一次 write 的数据，接收端就会一次 readyRead 完整收到。接收端可能遇到半包，也可能遇到多个帧粘在一起到达。

所以我们把每条业务消息封装成 Type、Length、Value 三部分。Type 表示业务类型，比如文件请求、聊天文本或错误帧；Length 表示后面载荷的长度，帮助接收端判断什么时候凑齐一帧；Value 放具体内容。

Value 并不总是 JSON。对于设备信息、文件元信息、聊天文本这类结构化数据，使用 JSON 更方便阅读、调试和扩展；真正的文件内容则按二进制块传输，避免把大文件再编码成文本造成额外开销。

## 第 15 页：本地数据层

**主讲：高扬**

本地数据层让 GridYard 不只是当前窗口里能收发消息，而是能把设备目录、聊天记录和传输历史保存下来。用户重启应用后，仍然可以看到曾经连接过的设备、聊天内容和文件传输记录。

数据层没有直接让 QML 或业务控制器去写 SQL，而是通过 Repository 做隔离。上层只关心“保存消息”“查询历史”“记录传输结果”这些业务操作，具体 SQLite 读写由 Repository 和 DatabaseWorker 处理。DatabaseWorker 在后台线程执行数据库操作，避免阻塞界面和网络传输。

另外，MigrationRunner 负责数据库结构的创建和升级。这样后续如果需要增加字段或调整表结构，也有统一的迁移入口，而不是到处手写建表逻辑。

## 第 16 页：最终路径问题与修复

**主讲：高扬**

发布包能启动还不够，运行数据放在哪里也很重要。早期如果把数据库、配置或日志写在程序目录里，用户移动或删除发布包时，就可能把历史记录一起破坏掉。

最终版本把程序包和用户数据分开。AppImage 或 portable 包只负责放程序和依赖；配置文件进入 `~/.config/CQNU-SED/GridYard/`，数据库和日志进入 `~/.local/share/CQNU-SED/GridYard/` 下的对应目录。

这样做更符合 Linux 桌面应用的习惯。用户删除或移动发布包，不会影响已有配置和历史数据；开发和验收时，也能通过日志目录快速定位设备发现、传输、数据库迁移和打包运行问题。
