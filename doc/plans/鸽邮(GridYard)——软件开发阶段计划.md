## 0. 文档使用说明

### 0.1 写给团队成员

- 这份文档是你**找事做**的入口。不分工，**任务公示在群里，谁感兴趣谁认领**。
- 每个阶段分 **必要任务** 与 **加分任务**：
  - **必要任务**：阶段进入下一阶段之前必须完成的；做不完整个团队就卡在这个阶段。
  - **加分任务**：时间宽裕、能力允许时做；提升项目质量，但不做不影响下个阶段开始。
- 不要跳阶段。下一阶段的任务依赖上一阶段的成果，提前抢做会因接口不稳返工。
- 选择任务的原则：
  1. **能做的优先做**（量力而行，不要选超出当前能力 2 个量级的）
  2. **没人接手的兜底**（如果某项必要任务 24 小时无人认领，Tech Lead 会派活）
  3. **加分任务凭兴趣**（喜欢 UI 的去打磨视觉，喜欢底层的去抠性能）

### 0.2 写给 Tech Lead

- 每阶段开始前，把该阶段的必要任务清单贴进群公告，召集认领。
- 每阶段结束前，按"验收标准"逐项确认；不达标不允许进入下一阶段。
- 加分任务可以滚动到后续阶段，不必强求当阶段完成。
- 阶段切换时打 git tag：`stage-0-done` / `stage-1-done` ... 便于事后回顾节奏。

## 1. 全局里程碑总览

```
                                  ┌───────────────────────┐
                                  │  课程答辩 / 期末交付   │
                                  └──────────▲────────────┘
                                             │
                                  ┌──────────┴────────────┐
                                  │  V1.0 最小可交付      │  ← 必须达到
                                  └──────────▲────────────┘
                                             │
   ┌─────────┬─────────┬─────────┬───────────┴────┬─────────┬─────────────┐
   │ Stage 0 │ Stage 1 │ Stage 2 │   Stage 3      │ Stage 4 │  Stage 5    │
   │ 工程奠基 │ 通信基石 │ 设备发现 │   文件传输    │ 健壮性  │  体验打磨   │
   │ ~3 天   │ ~3 天   │ ~5 天   │   ~7 天        │ ~5 天   │  ~3 天      │
   └─────────┴─────────┴─────────┴────────────────┴─────────┴──────┬──────┘
                                                                    │
                                                       ┌────────────┴──┐
                                                       │  Stage 6      │ ← 加分
                                                       │  V2.0 IM      │
                                                       │  时间够才做    │
                                                       └───────────────┘
```

**核心交付定义**：

- **MVP（最小可行产品）= Stage 0 + 1 + 2 + 3** — 两机能互相看见、能传一个文件
- **V1.0 完整版 = MVP + Stage 4** — 文件夹、SHA-256、异常处理和协议防护
- **V1.5 本地数据版 = V1.0 + Stage 5** — SQLite 传输历史、托盘和体验打磨
- **V2.0 服务版 = V1.5 + Stage 6.0~6.2** — 登录、服务端部署和传输记录漫游
- **V2.1 IM 版 = V2.0 + Stage 6.3~6.4** — 在线单聊和离线消息漫游

**最低交付底线**：必须达到 **V1.5 本地数据版**（Stage 0–5）。Stage 6 可按子阶段独立决定是否启动。

**关键演进决策**：

- 保留当前 TLV/P2P 文件传输架构，不整体改写为 LocalSend REST 或 IPMSG；借鉴 LocalSend 的版本、能力、token、部分接受、限流与发现兜底设计。
- SQLite 本地传输记录属于基础能力，不要求登录；QML 只能通过 Controller/Repository 使用数据。
- 登录与服务端属于可选增强，服务端不参与文件流量；传输记录漫游默认关闭且只同步必要元数据。
- Stage 6 先完成安全鉴权和记录漫游，再决定是否投入 IM；所有登录和同步流量必须使用 TLS。

### 风险点

- **Worker-Object 跨线程信号槽**：是 Stage 3 最容易踩坑的地方。务必：
  - 自定义参数类型用 `qRegisterMetaType<T>()` 在 `main()` 注册
  - 跨线程信号让 Qt 自动选 `Qt::AutoConnection`，**不要手动指定 DirectConnection**
- **QML 拖放事件**：QML `DropArea` 与 C++ 端拿文件路径需要 `Drag.urls`，注意类型转换。
- **TCP 半包 / 粘包**：靠 Stage 1 的 `FrameCodec` 已经搞定，但要确保所有接收侧都通过它解码，不自己手解。

### 与设计文档对应

- 实现 V1.0 设计书 §5.3 P2P 文件传输完整时序
- 实现代码规范 §3.6 Worker-Object 模式
