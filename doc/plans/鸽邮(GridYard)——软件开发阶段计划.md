## 0. 文档使用说明

### 0.1 写给团队成员

- 这份文档是你**找事做**的入口。不分工，**任务公示在群里，谁感兴趣谁认领**。
- 每个阶段分 **必要任务** 与 **加分任务**：
  - **必要任务**：阶段进入下一阶段之前必须完成的；做不完整个团队就卡在这个阶段。
  - **加分任务**：时间宽裕、能力允许时做；提升项目质量，但不做不影响下个阶段开始。
- 不要跳阶段。下一阶段的任务依赖上一阶段的成果，提前抢做会因接口不稳返工。
- 选择任务的原则：
  1. **能做的优先做**（量力而行，不要选超出当前能力 2 个量级的）
  2. **没人接手的兜底**（如果某项必要任务 24 小时无人认领，Tech Lead 会派活）
  3. **加分任务凭兴趣**（喜欢 UI 的去打磨视觉，喜欢底层的去抠性能）

### 0.2 写给 Tech Lead

- 每阶段开始前，把该阶段的必要任务清单贴进群公告，召集认领。
- 每阶段结束前，按"验收标准"逐项确认；不达标不允许进入下一阶段。
- 加分任务可以滚动到后续阶段，不必强求当阶段完成。
- 阶段切换时打 git tag：`stage-0-done` / `stage-1-done` ... 便于事后回顾节奏。

**核心交付定义**：

- **MVP（最小可行产品）= Stage 0 + 1 + 2 + 3** — 两机能互相看见、能传一个文件
- **V1.0 完整版 = MVP + Stage 4** — 文件夹、SHA-256、异常处理与协议防护
- **V1.5 局域协同版 = V1.0 + Stage 5** — 在线设备之间可直接发文本聊天（纯 P2P）
- **V1.6 本地数据版 = V1.5 + Stage 6** — SQLite 本地聊天记录与传输历史、托盘、体验打磨
- **V2.0 服务版 = V1.6 + Stage 7** — 登录、对话历史与传输记录漫游、离线消息

**最低交付底线**：必须达到 **V1.6 本地数据版**（Stage 0–6）。这一档既覆盖老师要求的四层架构（数据管理层落地），又包含可演示的文件直传与局域网在线聊天。Stage 7 服务端与漫游按子阶段独立决定是否启动。

**关键演进决策**：

- 保留当前 TLV/P2P 文件传输架构，不整体改写为 LocalSend REST 或 IPMSG；借鉴 LocalSend 的版本、能力、token、部分接受、限流与发现兜底设计。
- **在线聊天优先用 P2P 实现**：在线设备之间的文本消息走现有 UDP 发现 + TCP + FrameCodec 通道直发，不依赖服务端、不依赖登录。这是项目 P2P 内核的自然延伸。
- 本地数据层统一承载聊天记录与传输历史，不要求登录；QML 只能通过 Controller/Repository 使用数据。
- **服务端只负责 P2P 做不到的事**：身份鉴权、对话历史与传输记录漫游、以及接收方离线时的消息暂存兜底。服务端不参与文件流量，也不替代在线 P2P 直发。
- Stage 7 先完成安全鉴权与漫游，再决定是否投入离线消息；所有登录与同步流量必须使用 TLS。

## Stage 5 — 局域网在线聊天

### 目标

> 在已发现的在线设备之间直接收发文本消息：在 A 的聊天窗口输入文字，在线的 B 立即收到并显示。**纯 P2P，不依赖服务端、不依赖登录、本阶段消息只存内存。** 给离线设备发消息是 Stage 7 服务端的事。

### 入口条件

- Stage 4 完成（协议防护与接收侧后台化达标，FrameCodec 路由稳定）

### 设计要点

- **协议**：在 V1.0 低位段新增文本 Type 码，不触碰为服务端预留的 `0x1000` 段。
  - `0x0501 kTypeChatText` — P2P 在线文本消息（JSON 载荷）
  - `0x0502 kTypeChatAck` — 文本消息送达回执（加分项使用）
  - 文本消息 JSON 字段建议：`message_id`、`from_device_id`、`from_name`、`content`、`sent_at`。
- **连接策略**：聊天是双向、随时、短载荷，与文件传输"单向一次性大流量"形态不同。建议为每个对端维护一条轻量 TCP 长连接（在线期间复用），断线后按需重连；`P2pServer` 收到入站连接后按首帧 Type 区分这是文件传输还是聊天会话，分别交给接收 Worker 或聊天会话处理。
- **职责边界**：网络与连接管理在 C++（`ChatManager` / 聊天会话对象）；QML 只负责气泡渲染与输入，经 Controller 发送意图、绑定消息模型。文本内容的格式化（时间、换行、链接识别）属于 JavaScript/QML 展示层。

### 验收标准

- ✅ 两台在线设备可双向实时收发文本，延迟无明显卡顿
- ✅ 对端离线时不可发送且有清晰提示
- ✅ 气泡区分发件方与收件方，时间显示正确
- ✅ 聊天会话与文件传输共用端口但互不干扰
- ✅ 聊天相关异常不影响设备发现与文件传输主链路
- ✅ 相关单测通过（协议码、消息编解码、连接分流）

### 风险点

- **同端口多用途的帧路由**：`P2pServer` 必须可靠区分"文件传输连接"和"聊天连接"，否则会把聊天帧喂给接收 Worker。建议以首帧 Type 判定连接用途。
- **长连接生命周期**：聊天连接的建立、复用、断线重连要与设备在线状态联动，避免对离线设备反复重连。
- **不要为聊天改动文件传输主链路**：聊天是新增旁路，FileSenderWorker / FileReceiverWorker 的传输逻辑保持不动。

### 与设计文档对应

- 落实 QML / JavaScript / C++ 职责边界（聊天的网络在 C++，展示在 QML/JS）

## Stage 7 — 服务端、登录与漫游（分步加分阶段）

### 目标

> 在 V1.6 本地数据层之上平滑叠加 C/S 服务端。服务端只做 P2P 做不到的三件事：**身份鉴权、对话历史与传输记录的跨设备漫游、接收方离线时的消息暂存兜底**。在线聊天与文件直传仍走 P2P，不经服务端。

### 入口条件

- Stage 6 完成，本地 SQLite 与 Repository 边界稳定
- 已明确服务端部署位置、证书与数据库备份方式
- 在线聊天与文件传输无需登录也能继续使用
- 团队接受服务端、数据库与安全运维成本

### Stage 7.0 — 服务端骨架与数据基线

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.0.1 | 建立 `server/` target、配置加载、日志、健康检查与优雅退出 | 服务端可独立部署并稳定运行 | 1.5 天 |
| 7.0.2 | PostgreSQL migration：`users`、`auth_sessions`、`transfer_records`、`messages` | 空库自动升级，重复执行不破坏数据 | 1.5 天 |
| 7.0.3 | 定义 V2 Type、请求 ID、错误码与协议版本；设置帧长与频率限制 | 客户端与服务端共享协议测试通过 | 1 天 |
| 7.0.4 | 配置 TLS；密码采用 Argon2id/bcrypt，不使用普通 SHA-256 | 抓包看不到明文密码与 token | 1 天 |

### Stage 7.1 — 登录与会话鉴权

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.1.1 | 服务端实现注册、登录、token 刷新、登出与会话失效 | 非法 token 无法访问受保护接口 | 2 天 |
| 7.1.2 | 客户端实现 `ServerLink`、`AuthManager` 与登录/注册 QML | 登录状态由 C++ 属性驱动，断线可恢复 | 2 天 |
| 7.1.3 | 未登录模式与登录模式并存，登录失败不影响 P2P 文件传输与在线聊天 | 无服务端时 V1.6 功能全部可用 | 0.5 天 |

### Stage 7.2 — 对话历史与传输记录漫游

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.2.1 | 本地聊天记录与传输记录使用全局 UUID 与同步状态；实现上传、拉取、游标与幂等去重 | 重复同步不产生重复记录 | 2 天 |
| 7.2.2 | 只同步必要元数据，不上传文件内容与敏感路径；漫游默认关闭由用户开启 | 服务端记录字段通过隐私检查 | 0.5 天 |
| 7.2.3 | UI 增加漫游开关、同步状态与删除服务端记录入口 | 用户可控制同步与删除 | 1 天 |

### Stage 7.3 — 离线消息漫游

| 编号 | 任务 | 验收方式 | 估时 |
|:---|:---|:---|:---|
| 7.3.1 | 接收方离线时，发送方经服务端暂存消息；收到 delivered ACK 后标记投递 | 接收方离线时消息不丢失 | 2 天 |
| 7.3.2 | 客户端登录后按稳定游标拉取离线消息并写入本地 SQLite | 重复拉取不产生重复消息 | 1 天 |

> **与 Stage 5 的关系**：在线单聊已在 Stage 5 用 P2P 实现，Stage 7 不再重复造在线聊天。服务端聊天能力只补两点——把聊天历史漫游到云端（7.2），以及在对端离线、P2P 发不出去时经服务端兜底投递（7.3）。

### 后续加分任务

| 编号 | 任务 | 价值 |
|:---|:---|:---|
| 7.A | 局域网聊天大厅与群聊 | 群体协作 |
| 7.B | 已读状态、撤回与搜索 | IM 体验 |
| 7.C | 可信设备管理与多设备同步 | 完整账号体验 |
| 7.D | LocalSend REST 兼容适配层或浏览器下载入口 | 跨应用兼容 |

### 验收标准

- ✅ 每个子阶段均可独立演示与停止，不要求一次完成全部 Stage 7
- ✅ 登录与漫游通道使用 TLS，密码与 token 不明文传输
- ✅ 本地聊天与历史不登录也可用；开启漫游后跨设备记录不重复
- ✅ A 给离线的 B 发消息，B 上线后能可靠拉取且不重复
- ✅ V1.6 的 P2P 文件传输与在线聊天始终不受服务端状态影响

### 风险点

- **登录不是一个对话框，而是身份、token、TLS、数据库与失效策略的组合**。
- 漫游只同步元数据；服务端保存文件内容会破坏 P2P 职责边界与隐私承诺。
- 不要在没有幂等键、ACK 与 migration 前开始漫游或离线消息。
- 时间不足时停在 7.2，仍能形成"本地历史 + 登录 + 对话/记录漫游"的完整增量。

### 与设计文档对应

- 实现 V2.0 设计书 §10 演进规划（在线聊天部分由 Stage 5 的 P2P 方案替代）
