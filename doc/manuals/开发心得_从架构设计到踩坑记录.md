## 1. 初始架构设计：为什么这么分层？

在项目启动之初（2026-04-23），我们面临一个核心挑战：如何在一个开发周期内，既实现高性能的 P2P 文件直传，又为未来的即时通讯（IM）和离线漫游预留空间？

### 1.1 模块化设计的初衷
我们在 `src/` 目录下进行了极其详细的分类，这并非为了增加复杂度，而是为了实现**物理隔离**：

*   **`shared/` (核心基石)**：存放 TLV 协议定义、共用数据类型和帧编解码器。它是 client 和 server 的“共同语言”。将其独立出来，可以确保双端协议实现的高度一致性。
*   **`client/` (桌面端)**：基于 Qt Widgets/Quick 的客户端。它只负责 UI 展示和 P2P 逻辑。
*   **`server/` (未来演进)**：预留给 V2.0 的“邮局”服务端。它不参与文件传输，仅负责用户鉴权和离线消息。
*   **`tests/` (质量保证)**：独立于业务代码，确保协议解析等核心逻辑的健壮性。

### 1.2 这么分类的好处
1.  **平滑演进**：V1.0 实现纯 P2P 传输时，`server/` 可以保持空壳。到了 V2.0 引入服务端时，我们只需要在 `server/` 下写代码，并让它链接 `shared/` 库即可，**完全不需要改动 client 的核心逻辑**。
2.  **职责清晰**：网络层、业务层、UI 层边界明确。比如 `FrameCodec` 只管字节流拆包，不管里面是文件还是聊天记录。
3.  **构建提速**：CMake 可以针对改动的模块进行增量编译，而不需要重新扫描整个项目。

## 2. CMake 层级构建逻辑

我们采用了典型的“总-分”式 CMake 结构：

1.  **顶层 `src/CMakeLists.txt`**：作为指挥官，负责环境检测（如 Qt6 查找）、编译器配置，并通过 `add_subdirectory()` 串联各个子模块。
2.  **子模块 `shared/CMakeLists.txt`**：被构建为一个静态库 `gy_shared`。它声明了自己的包含路径（include directories）和编译特性（C++23）。
3.  **应用端 `client/CMakeLists.txt`**：最终的可执行文件 target。它链接 `gy_shared` 以及 Qt 库。

这种层级设计的精妙之处在于**依赖传递**：只要 client 链接了 `gy_shared`，它就会自动继承 `shared` 目录的头文件搜索路径，代码中直接 `#include "protocol.h"` 即可，无需写复杂的相对路径。

## 3. 踩坑记录：C++23 模块与中文路径

**日期**：2026-05-26

### 问题现象
在环境搭建完成后，第一次编译遇到了诡异的错误。CMake 配置通过了，但在编译生成依赖阶段，连最基本的 `#include "frame_codec.h"` 都报了解析错误：
```text
error: 无法确定 .../frame_codec.h 的 ‘#include’ 转换：
malformed string 'ERROR 'unrecognized \'INCLUDE-TRANSLATE \'/.../frame_codec.h\'\'''
```

### 真正的原因
最终确认是 **GCC 16 的一个编译器 Bug**：
我们在 CMake 中开启了 C++23 模块的实验性支持。当 GCC 尝试扫描代码依赖时，它的 `g++-mapper-server` 无法正确处理我们项目路径中的中文字符（`Qt6软件开发资料`）。中文路径导致它的内部指令格式损坏，引发崩溃。

此外，也发现了一些配置上的小疏忽：
1. `main.cpp` 用了 `QQuickStyle`，但 CMake 里忘了链接 `QuickControls2`。
2. 自动生成的 C++ 注册代码找不到 `app_controller.h`，需要把 `core/` 目录加入包含路径。

### 解决办法
为了兼顾中文路径下的开发体验，我们采取了以下措施：
1.  **关闭扫描**：在 `src/CMakeLists.txt` 中设置 `set(CMAKE_CXX_SCAN_FOR_MODULES OFF)`，绕过编译器 Bug。
2.  **补全配置**：在 CMake 中显式引入 `QuickControls2` 组件，并将 `client/core` 加入包含路径。

### 避坑建议

在玩 C++23 模块化等前沿特性时，尽量保持**项目全路径为英文**。如果遇到诡异的编译器报错，先换个英文路径试试，这往往是解决“灵异事件”的最快方式。

## 4. CMake 模板多模块拆分艺术：从单体到三层架构

**最后更新**：2026-05-26

为了让后续新加入团队的同学理清 CMake 构建体系，我们在 `doc/templates/CMakeLists.qml.template` 中对经典单体 Quick 模板进行了“三段式”的功能区域划分，并总结了多模块拆分的深层思考。

### 4.1 原单体 CMake 模板的模块划分与职责
在一个标准的 Qt Quick 单体工程中，CMake 文件主要集成了以下四大职责板块：
1. **全局编译器环境定义**（第 19-21 行）：声明最低 CMake 版本，并启用实验性 C++23 模块。
2. **Qt 环境发现与基础工程化配置**（第 25-26 行）：通过 `find_package` 拉取所需的 Qt 二进制包，并调用 `qt_standard_project_setup` 规范化资源加载路径。
3. **QML 模块注册与源文件声明**（第 28-38 行）：采用 `qt_add_qml_module` 将 C++ 源码与 QML 界面资产进行一站式注册与资源编译。
4. **依赖注入与部署发布**（第 39-48 行）：声明 `cxx_std_23` 标准，链接 Qt 组件库，并注入 `/opt/${PROJECT_NAME}` 的标准安装目录。

### 4.2 为什么要进行“三层拆分”？
如果死板地套用上述单体模板，当 GridYard 项目随着阶段演进时，会立刻遭遇架构“大熔炉”的困境：
* **如果协议库不隔离**：客户端（Client）和服务端（Server）都要共用 TLV 协议，如果不拆分，服务端在编译时就不得不链接 QtQuick 等沉重的 UI 动态库，背负无意义的运行时包大小。
* **如果测试用例不独立**：核心的网络粘包状态机（FrameCodec）极其依赖自动化单测。在单体结构下，运行 `ctest` 必须连带启动整个客户端 UI 系统，导致单测效率低下。

因此，我们以 **“物理隔离、高内聚”** 为原则，将单体模板打碎重构为三层：
* **顶层 `src/CMakeLists.txt`**：只保留**全局编译器环境定义**与 **Qt 包统一拉取**，作为整个项目的“总参谋部”，使用 `add_subdirectory` 挂载子模块。
* **逻辑层 `src/shared/CMakeLists.txt`**：剥离所有 UI 动作，将其重塑为一个**纯 C++ 静态库 `gy_shared`**，专门负责协议常量与帧状态编解码。
* **应用层 `src/client/CMakeLists.txt`**：专门处理**客户端 QML 注册**与 UI 依赖，最终静态链接 `gy_shared`。

### 4.3 三层拆分的核心工程学好处
1. **极致的模块化与高内聚**：
   通过分层，项目结构呈现出极高的系统秩序。`shared` 协议库只和字节流、网络报文打交道，没有任何 QML 的杂质，这保证了底层业务逻辑的纯洁性。开发 IM 服务端和桌面客户端的同学可以完全并行开发，互不干扰。
2. **依赖传递与“零包含路径”痛苦**：
   在 `shared/CMakeLists.txt` 中，我们巧妙使用了 `PUBLIC` 关键字：
   ```cmake
   target_include_directories(gy_shared PUBLIC .)
   ```
   这使得任何链接了 `gy_shared` 的上层模块（如 client）都会**自动向上冒泡继承**公共包含路径。在客户端 C++ 源码中，我们可以优雅直接地编写：
   ```cpp
   #include "protocol.h"  // 极其干净，无需写 "../shared/protocol.h"
   ```
3. **极速的增量编译**：
   当美术或前端同学仅仅修改了 `Main.qml` 的布局时，CMake 只会增量重新打包 client 的 QML 资源系统，底层的 `gy_shared` 静态库以及未来的 `server` 进程完全不需要重新编译，这为大型项目的日常研发协同节省了海量的等待时间。

## 5. 踩坑记录：Git 全局忽略规则“误杀”子目录与排除规则的优雅艺术

**日期**：2026-05-28

### 5.1 问题现象
在 Stage 0 阶段，本地客户端编译、运行均正常，但当将代码推送到远程，其他团队成员拉取后，却发生了由于缺少 `src/client/core/app_controller.h` 和 `app_controller.cpp` 导致的诡异编译报错。然而，在执行 `git status` 时，本地工作区显示完全干净，未跟踪文件列表空无一物，给排查带来了极大的隐蔽性。

### 5.2 真正的原因
这是一起由于 **过宽的 Git 全局忽略规则** 导致的“源文件误杀事件”。
原本的 `.gitignore` 规则中写入了：
```text
core
core.*
```
本意是为了全局忽略在项目开发和调试过程中由系统（Linux）生成的各种核心转储文件（core dump 文件，如 `core` 或 `core.<pid>` 格式）。

然而，由于没有加前缀路径符号 `/`，这两条规则被 Git 视作**全局模式**，不仅会忽略根目录下的匹配文件，还会默默地忽略**任何子目录下名为 `core` 的整个文件夹**！

巧合的是，根据我们的“四层架构设计”，客户端的核心控制器业务逻辑刚好存放在 `src/client/core/` 目录中。因为文件夹名字恰好为 `core`，它里面的所有 C++ 源文件在创建之初就被 Git 默不作声地忽略了，根本没有被加入版本跟踪，自然也就没能推送到远程仓库，导致别人拉取下来后编译直接报错。

### 5.3 解决办法
之前有同学通过把 `.gitignore` 的规则改写为 `/core` 和 `/core.*` 来临时规避，但这留下了新的隐患——核心转储文件不再能被全局忽略，在子目录下运行程序崩溃时产生的文件会继续污染 `git status` 工作区。

为了彻底、优雅地解决此问题，我们采用了 **全局忽略匹配 + 精准子目录排除（Exclusion）** 的组合拳：
```text
core
core.*
!**/core/
```
*   **`core` 和 `core.*`**：继续发挥其全局忽略 core dump 文件的安全屏障作用，防止垃圾文件污染。
*   **`!**/core/`**：通过使用排除语法 `!`，显式地声明**任何子目录下名为 `core/` 的文件夹绝不能被忽略**。这赋予了 Git 忽略引擎极高的精确性，在隔离调试垃圾文件的同时，确保了业务源码的绝对安全。

### 5.4 避坑建议
1.  **警惕全局字样冲突**：在 `.gitignore` 中编写普通名词（如 `core`、`build`、`lib` 等）作为忽略项时，若不希望其递归应用于子目录，请前置 `/` 限制范围；或者极其小心，因为它可能会悄无声息地在子目录里“杀掉”你宝贵的业务源文件。
2.  **善用排除白名单**：当需要在全局忽略某种格式的文件或特定缩写，但又确信某些特定子目录下可能会用到同名目录时，请善用 `!**/<目录名>/` 的排除语法，这比直接割裂全局规则要健壮、清晰得多。
3.  **开发自检习惯**：在多人协作时，将新模块或新文件加入项目后，建议在提交前主动使用 `git status --ignored` 审查一次被忽略的文件列表，以防关键业务源码被误杀漏提。

## 6. Stage 1 心得：TLV 帧编解码器与粘包状态机

**日期**：2026-06-02

### 6.0 什么是"粘包状态机"？

**粘包**（TCP Sticky Packet）是 TCP 网络编程中的经典问题。TCP 是**流式协议**，它不保证每次 `send()` 的数据会被对方以相同的次数 `recv()` 收到。发送端连续发送两个数据包，在接收端可能：
- 两次分别收到（正常）
- 合并成一次收到（粘包）
- 第一个包收到一半，剩下部分和第二个包合并到达（半包 + 粘包）

**状态机**是一种编程模式：程序处于某个"状态"，收到新数据后根据当前状态决定如何处理，然后转移到下一个状态。

**粘包状态机**就是用状态机模式来解决 TCP 粘包/半包问题的方案。在我们的实现中，程序在两个状态之间循环：
1. **WaitingHeader**：等待凑齐 8 字节帧头（Type + Length）
2. **WaitingPayload**：等待凑齐 Length 字节载荷

每当新数据到达，状态机就尝试推进：如果当前状态所需的数据够了，就解析、转移状态；如果不够，就继续等待下一次数据到达。这样无论数据怎么"粘"、怎么"拆"，都能正确还原出完整的帧。

### 6.1 最难的部分：粘包状态机

Stage 1 的核心任务是实现 `FrameCodec`——TLV 帧的编解码器。其中最难的部分是 **`feed()` 方法的粘包/半包状态机**。

#### 为什么需要状态机？

TCP 是流式协议，没有消息边界。发送端调用两次 `socket.write()`，接收端可能收到：
- **粘包**：两次发送的数据合并成一次到达
- **半包**：一次发送的数据分多次到达

如果直接在 `readyRead` 信号里解析字节流，代码会变成一团乱麻。所以我们用一个两状态的状态机来优雅处理：

```
WaitingHeader (等待帧头)
    ↓ 收到 8 字节
WaitingPayload (等待载荷)
    ↓ 收到 length 字节
    ↓ emit frameReady
WaitingHeader (循环)
```

#### 实现细节与踩坑

1. **大端序处理**：网络协议统一使用大端序（Big-Endian），但 x86 机器是小端序。必须用 `QDataStream::setByteOrder(QDataStream::BigEndian)` 显式设置，否则解析出的 Type 和 Length 会是乱码。

2. **循环处理粘包**：一次 `feed()` 调用可能包含多个完整帧，所以必须用 `while(true)` 循环，直到数据不足才退出。初版实现漏掉了这个循环，导致粘包时只解析第一个帧，后续帧被丢弃。

3. **状态重置**：每解析完一个完整帧，必须重置状态为 `WaitingHeader`，并清零 `_pendingType` 和 `_pendingLength`。忘记重置会导致下一个帧的帧头被当作载荷读取。

4. **边界条件**：空 payload（如 `kTypeTransferDone`）的帧，Length 为 0，状态机应直接从 `WaitingHeader` 跳到 `emit frameReady`，不进入 `WaitingPayload` 等待。

### 6.2 单测的价值

写单测时发现了一个隐藏 bug：测试"半包"用例时，先喂 4 字节（半个帧头），再喂剩余部分。初版实现在 `WaitingHeader` 状态下没有检查缓冲区大小，直接用 `QDataStream` 读取，导致读取越界。

修复后，5 个测试用例全部通过：
- 单帧编解码
- 粘包（多个帧合并）
- 半包（帧分多次到达）
- 空 payload
- 超大 payload（1MB）

### 6.3 设计决策记录

**为什么用 `enum class State` 而不是 `bool`？**

初版用 `bool _waitingHeader` 来表示状态。但考虑到未来可能扩展（如增加"等待校验和"状态），改用 `enum class State` 更具可扩展性，也更符合 SOLID 的开闭原则。

**为什么 `encode()` 是静态方法？**

编码过程无状态，只需要输入 type + payload，输出字节流。静态方法避免了不必要的实例化，也方便在没有 FrameCodec 实例的地方直接调用（如 `FrameCodec::encode(kTypeHello, json)`）。

### 6.4 经验总结

1. **TCP 编程第一课**：粘包/半包是网络编程的基础，理解了这个，后面的文件传输、心跳包都是顺理成章。
2. **状态机是利器**：遇到"分阶段处理字节流"的场景，第一反应应该是状态机，而不是一堆 if-else。
3. **先写单测再写实现**：单测能帮你发现边角 case，比肉眼看代码靠谱得多。

## 7. Stage 2 心得：UDP 广播与设备发现

**日期**：2026-06-02

### 7.1 最难的部分：多网卡广播

Stage 2 的核心是实现 `DiscoveryService`——局域网设备发现服务。其中最难的部分是 **多网卡环境下的 UDP 广播精确发送**。

#### 为什么需要多网卡处理？

在同时连接有线局域网和 WiFi 的主机上，如果直接使用 `QHostAddress::Broadcast`，Qt 底层可能仅向默认网卡发送，导致其他网段的设备收不到广播。

**解决方案**：遍历所有激活的网络接口，向每个网卡的广播地址单独发送：

```cpp
const auto interfaces = QNetworkInterface::allInterfaces();
for (const QNetworkInterface &iface : interfaces) {
    // 过滤：必须是激活中的、非回环的、支持广播的物理网卡
    if (!(iface.flags() & QNetworkInterface::IsUp))       continue;
    if (!(iface.flags() & QNetworkInterface::CanBroadcast)) continue;
    if (  iface.flags() & QNetworkInterface::IsLoopBack)  continue;

    for (const QNetworkAddressEntry &entry : iface.addressEntries()) {
        if (entry.ip().protocol() != QAbstractSocket::IPv4Protocol) continue;
        _socket->writeDatagram(data, entry.broadcast(), kDiscoveryPort);
    }
}
```

**设计决策**：为什么不直接用 `QHostAddress::Broadcast`？

因为 Qt 的广播行为依赖系统路由表，在双网卡场景下可能只向一个网卡发包。精确遍历网卡虽然代码复杂，但能确保所有网段的设备都能收到广播。

### 7.2 节点表维护：UDP 的"连接"语义

UDP 是无连接协议，没有"断开连接"的通知。所以我们必须自己维护在线状态：

1. **心跳机制**：每 5 秒广播一次 Hello 包，包含设备 ID、名称、IP、端口
2. **超时剔除**：每 3 秒扫描节点表，超过 15 秒未更新的标记为离线
3. **本机过滤**：忽略自己发出的广播（用 device_id 去重）

**设计决策**：为什么用 `QHash<QString, PeerInfo>` 而不是 `QList<PeerInfo>`？

- 查找效率：O(1) vs O(n)
- 更新方便：直接用 device_id 作为 key 插入/更新
- 去重简单：同一设备多次广播只保留最新状态

### 7.3 ConfigManager 的单例模式

配置管理器使用 `QML_SINGLETON` 模式，确保全局唯一实例。这样：
- 任何组件都能通过 `ConfigManager.deviceName` 访问配置
- 配置变更自动通知所有监听者（通过信号）
- 配置持久化到 `QSettings`，重启后自动恢复

**设计决策**：为什么不用静态方法？

虽然配置管理可以用静态方法实现，但单例模式更符合 Qt 的信号槽机制，也更方便 QML 绑定。

### 7.4 QML 组件设计：required property

`DeviceCard.qml` 使用 `required property` 声明所有属性：

```qml
required property string deviceId
required property string deviceName
required property string ipAddress
required property bool   isOnline
```

**为什么用 required property？**

当组件作为 ListView 的 delegate 使用时，QML 引擎会根据名字自动从 model 项里填值。这样就不需要手动写 `model.deviceId` 绑定，代码更简洁，也更不容易出错。

### 7.5 经验总结

1. **UDP 编程要注意网卡**：双网卡场景下，必须精确遍历所有网卡发送广播
2. **无连接协议要自己维护状态**：UDP 没有断开通知，必须用心跳+超时机制
3. **QML_SINGLETON 是利器**：需要全局共享的组件，优先考虑单例模式
4. **required property 简化 delegate**：ListView delegate 优先用 required property

## 八、Stage 3 心得：P2P 文件传输

### 8.1 Worker-Object 模式与跨线程信号

文件收发涉及大量磁盘 I/O 和网络传输，不能阻塞主线程。采用 Worker-Object 模式（继承 QObject + `moveToThread`）而非继承 QThread 重写 `run()`，原因：

- Worker-Object 的事件循环天然支持信号槽连接
- `moveToThread` 后，该对象的槽函数自动在目标线程执行，不需要手动管理线程同步
- 更容易与主线程通信：跨线程信号自动走队列连接

**踩坑**：`TransferSessionManager` 管理多个 Worker 的生命周期，构造函数中 UDP socket 初始化和信号连接的顺序很重要——先绑定 socket 再连接信号，否则早期数据报会丢失。

### 8.2 本机回环测试：双实例调试

P2P 传输需要至少两个设备，开发阶段没有多台机器，解决办法是同一台机器启动两个实例，通过命令行参数隔离：

```bash
./appGridYard --port 35100 --name "接收端" &
./appGridYard --port 35101 --name "发送端" &
```

`--port` 不仅指定 TCP 监听端口，还自动让 `QSettings` 使用不同的配置文件（通过 `GRIDYARD_CONFIG` 环境变量），避免两个实例共享同一个 deviceId。

### 8.3 QML_ANONYMOUS 与类型注册

`DiscoveryService` 作为 `QML_ANONYMOUS` 注册而非 `QML_ELEMENT`，原因是它不作为独立 QML 类型实例化，而是通过 `AppController.discovery` 属性暴露给 QML。如果用 `QML_ELEMENT`，QML 引擎会尝试独立创建实例，导致与 C++ 端持有的实例不一致。

**规则**：被其他对象持有的子对象（不独立使用），用 `QML_ANONYMOUS`；需要在 QML 中直接创建的类型，用 `QML_ELEMENT`。

### 8.4 Dialog contentItem 与布局冲突

`SettingsDialog` 使用 `Dialog` + `standardButtons` 时，如果把 `ScrollView` 赋值给 `contentItem`，会替换 Dialog 的整个内容区域，导致标题栏和按钮栏的布局计算失效，ScrollView 无法正确获取可用高度，内容溢出且滚动条不出现。

**解决**：不要用 `contentItem:` 前缀，让 ScrollView 作为 Dialog 的普通子项，由 Dialog 内部布局统一管理标题、内容和按钮区域。

### 8.5 经验总结

1. **后台操作用 Worker-Object**：需要事件循环的后台任务，优先 QObject + moveToThread
2. **命令行参数隔离多实例**：本地回环测试时，端口+配置文件隔离是关键
3. **QML 类型注册要分清场景**：被持有的子对象用 QML_ANONYMOUS，独立使用的用 QML_ELEMENT
4. **Dialog contentItem 谨慎替换**：需要滚动内容时，ScrollView 作为普通子项而非 contentItem

## 九、Stage 3 进阶心得：连接体验与传输完善

### 9.1 QML Dialog 的 contentItem 陷阱

`Dialog` 的 `contentItem` 属性会**替换**整个内容区域，而非向其中添加子项。当 `standardButtons` 存在时，Dialog 内部有自己的布局管理器（标题栏 + 内容区 + 按钮栏）。如果把 `ScrollView` 赋值给 `contentItem`，Dialog 的布局管理器不再控制该区域，导致：

- ScrollView 无法获取正确的 `availableHeight`
- 内容溢出但滚动条不出现
- 标题栏和按钮栏的布局也被破坏

**解决**：去掉 `contentItem:` 前缀，让 ScrollView 作为 Dialog 的普通子项，由 Dialog 内部布局统一管理。

**规则**：Dialog 中需要滚动内容时，永远不要用 `contentItem:` 包裹 ScrollView。

### 9.2 接收路径的传递链路

文件接收路径的配置涉及多个组件，需要理清传递链路：

```
ConfigManager (QSettings 持久化)
    ↓ _config->receivePath()
TransferSessionManager (init 时持有 _config)
    ↓ worker->setReceivePath(path)
FileReceiverWorker (acceptTransfer 时使用 _receivePath)
    ↓ _file.setFileName(_receivePath + "/" + _fileName)
```

**踩坑**：最初 `FileReceiverWorker::acceptTransfer()` 硬编码了 `QDir::homePath() + "/GridYard"`，没有使用 `ConfigManager` 的配置。原因是 Worker 在独立线程运行，不能直接访问 ConfigManager。解决办法是通过 `setReceivePath()` 方法在创建会话时由 `TransferSessionManager` 注入路径。

### 9.3 传输完成信号的接收端处理

发送端的 `transferFinished` 信号在 `createSendSession` 中已连接，但接收端的 `transferFinished` 信号最初没有连接。原因是接收会话的 Worker 由 `P2pServer` 创建，通过 `onTransferRequestReceived` 回调传入 `TransferSessionManager`，需要在该回调中连接信号。

**设计**：接收完成后发射 `transferCompleted(sessionId, fileName, filePath)` 信号，QML 端弹出对话框询问是否打开文件夹。通过 `QDesktopServices::openUrl()` 打开系统文件管理器。

### 9.4 本机 IP 获取与刷新

`QNetworkInterface::allAddresses()` 返回所有网络接口地址，包括回环地址和 IPv6 地址。获取本机 IPv4 地址需要过滤：

```cpp
for (const QHostAddress &addr : QNetworkInterface::allAddresses()) {
    if (addr.protocol() == QAbstractSocket::IPv4Protocol
        && !addr.isLoopback()) {
        return addr.toString();
    }
}
```

**注意**：多网卡环境下可能返回不同的 IP，`refreshLocalIp()` 方法允许在运行时重新获取。

### 9.5 经验总结

1. **Dialog contentItem 是替换不是追加**：需要滚动内容时，ScrollView 作为普通子项
2. **跨线程配置传递要用 setter**：Worker 在独立线程，不能直接访问单例，通过方法注入
3. **接收端信号别忘接**：发送端和接收端的 Worker 生命周期不同，信号连接时机也不同
4. **QDesktopServices 打开文件夹**：`openUrl(QUrl::fromLocalFile(path))` 跨平台打开文件管理器
5. **QNetworkInterface 过滤要严格**：回环地址、IPv6 地址都需要排除

## 十、Stage 4 心得：多文件传输与 SHA-256 校验

**日期**：2026-06-04

### 10.1 DirSerializer 设计决策

`DirSerializer` 是一个纯静态工具类，不继承 QObject，不需要暴露给 QML。设计为 `gy` 命名空间下的独立类：

- **为什么用结构体 `FileItem` 而不是已有的 `FileEntry`？**

  `FileEntry` 是 Q_GADGET，设计用于 QML 属性反射，带 Q_OBJECT 开销。`FileItem` 是纯 C++ 结构体，仅在 C++ 层使用，不需要元对象系统。遵循 YAGNI 原则，不为不需要的功能增加复杂度。

- **SHA-256 计算时机**

  在 `serialize()` 遍历目录时同步计算。虽然大文件会阻塞，但 `DirSerializer` 在 Worker 线程中调用，不会卡 UI。如果未来需要异步计算，可以单独抽成后台任务。

### 10.2 多文件传输的协议复用

Stage 3 的 chunk 元数据格式（20 字节：fileIndex + chunkOffset + chunkSize + isLastChunk）已经预留了 `fileIndex` 字段。Stage 4 只需：

1. 发送端：按 `_fileList` 顺序逐个文件发送，每个文件的 chunk 用相同的 `fileIndex`
2. 接收端：收到 `isLastChunk=1` 后，发送 `kTypeChunkAck` 并切换到下一个文件
3. 发送端：收到 `kTypeChunkAck` 后，校验通过则打开下一个文件继续发送

**关键点**：`kTypeTransferDone` 帧（0x0302）在 Stage 1 已定义但未使用，Stage 4 用它标记所有文件传输完成。

### 10.3 目录结构还原

接收端按 `relative_path` 中的路径分隔符创建子目录：

```cpp
QString dirPath = _receivePath + "/" + QFileInfo(relativePath).path();
QDir().mkpath(dirPath);
```

**踩坑**：`QFileInfo("subdir/file.txt").path()` 返回 `"subdir"`，但 `QFileInfo("file.txt").path()` 返回 `"."`。需要先检查 `relativePath` 是否包含目录分隔符。

### 10.4 SHA-256 校验流程

1. **发送端**：`DirSerializer::computeSha256()` 在序列化时计算，结果存入 `FileItem.sha256`
2. **握手请求**：`kTypeTransferReq` 的 JSON 中每个文件携带 `sha256` 字段
3. **接收端**：文件写入完成后，用 `QCryptographicHash::Sha256` 重新计算，与发送方的 hash 对比
4. **确认帧**：`kTypeChunkAck` 携带 `verified` 字段，校验失败时携带 `error_msg`

**注意**：SHA-256 计算必须在文件关闭前完成，否则读取不完整。

### 10.5 经验总结

1. **纯工具类不需要 QObject**：不需要信号槽、不需要 QML 暴露的类，用普通 C++ 类即可
2. **协议设计要预留扩展**：Stage 3 的 chunk 格式已预留 fileIndex，Stage 4 直接复用
3. **目录创建要处理相对路径**：`QFileInfo::path()` 对单文件返回 `"."`，需要判断
4. **SHA-256 计算要在 Worker 线程**：大文件计算会阻塞，不能在主线程执行

## 十一、Stage 4.4 心得：异常断网处理

**日期**：2026-06-04

### 11.1 难点分析

**难点 1：如何检测对端崩溃？**

TCP 的 `disconnected` 信号只能检测到正常断开（调用 `disconnectFromHost()`）。如果对端进程崩溃（`kill -9`），TCP 连接不会立即断开，而是保持半开状态（Half-Open）。此时：
- 发送数据不会报错（数据在内核缓冲区）
- 不会触发 `disconnected` 信号
- 只有等到 TCP keepalive 超时（默认 2 小时）才会断开

**解决方案**：应用层超时检测。每次收到数据时重置定时器，如果 30 秒没有收到任何数据，认为连接已死。

**难点 2：不完整文件的清理**

传输中断时，接收端可能已经写入了部分文件数据。如果不清理，下次传输同名文件会出现：
- 文件大小不一致
- SHA-256 校验失败
- 用户困惑

**解决方案**：在 `cleanup()` 方法中，关闭文件后立即删除不完整文件。

### 11.2 设计决策

**为什么用 QTimer 而不是 TCP keepalive？**

1. **TCP keepalive 默认超时太长**（2 小时），需要修改系统参数
2. **应用层超时更灵活**：可以根据业务需求调整超时时间
3. **QTimer 跨平台**：不需要关心不同操作系统的 TCP keepalive 实现

**为什么超时时间选择 30 秒？**

1. **太短（< 10s）**：网络抖动会误判
2. **太长（> 60s）**：用户体验差，长时间无响应
3. **30 秒**：平衡了可靠性和用户体验，符合验收标准"30s 内检测到"

**为什么在 cleanup() 中删除文件而不是保留？**

1. **不完整文件没有价值**：SHA-256 校验会失败，无法使用
2. **避免磁盘空间浪费**：大文件传输中断会留下 GB 级垃圾
3. **用户期望**：要么完整接收，要么不要留下半成品

### 11.3 实现细节

**超时定时器的生命周期**：
```
构造 -> acceptTransfer() 启动 -> 每次 onReadyRead() 重置 -> 超时/完成/取消 时停止
```

**资源清理的时机**：
1. 超时触发 -> cleanup() -> emit transferFinished(false, "传输超时")
2. 连接断开 -> cleanup() -> emit transferFinished(false, "连接断开")
3. 用户取消 -> rejectTransfer() -> _socket->disconnectFromHost() -> 触发 onDisconnected() -> cleanup()

### 11.4 经验总结

1. **TCP 断开检测不可靠**：必须在应用层实现超时检测
2. **资源清理要彻底**：文件、定时器、socket 都要清理
3. **cleanup() 要幂等**：多次调用不会崩溃
4. **析构函数调用 cleanup()**：确保任何路径都能清理资源

## 十二、Stage 4.5 心得：大文件吞吐量优化

**日期**：2026-06-04

### 12.1 难点分析

**难点 1：如何找到性能瓶颈？**

大文件传输涉及多个环节：
- 发送端：文件读取 -> 内存缓冲 -> TCP 发送
- 接收端：TCP 接收 -> 内存缓冲 -> 文件写入
- 中间：TLV 编解码、信号槽、UI 更新

**瓶颈可能在**：
1. 磁盘 I/O（读写速度）
2. 网络带宽（千兆 = 125 MB/s）
3. CPU（编解码、SHA-256 计算）
4. Qt 事件循环（信号槽开销）

**难点 2：chunk 大小的选择**

- **太小（< 1MB）**：信号槽开销大，TCP 包头占比高
- **太大（> 16MB）**：内存占用高，单次写入可能阻塞
- **8MB**：平衡了内存占用和吞吐量

### 12.2 设计决策

**为什么调整 chunk 大小为 8MB？**

1. **减少系统调用次数**：8MB chunk 意味着 5GB 文件只需 640 次 read/write
2. **匹配 TCP 窗口**：现代 TCP 窗口大小通常 4-16MB，8MB 是合理选择
3. **内存占用可控**：每个 Worker 最多占用 8MB 缓冲区，不会 OOM

**为什么调大 socket buffer 到 4MB？**

1. **减少 TCP 窗口收缩**：默认 buffer（通常 128KB）在高带宽下会成为瓶颈
2. **匹配 chunk 大小**：4MB buffer 可以缓冲半个 chunk，减少等待
3. **操作系统限制**：Linux 默认最大 buffer 通常 208KB，需要显式调大

**为什么减少进度信号发射频率？**

1. **信号槽有开销**：每次发射需要 Qt 事件循环处理
2. **UI 更新不需要太频繁**：每 32MB 更新一次（约 0.25 秒）足够
3. **减少 CPU 占用**：5GB 文件从 640 次信号减少到 160 次

### 12.3 实现细节

**chunk 大小的定义位置**：
```cpp
// file_sender_worker.h
static constexpr qint64 kChunkSize = 8 * 1024 * 1024;  // 8MB
```

**socket buffer 设置时机**：
```cpp
// 连接成功后设置
_socket->setSocketOption(QAbstractSocket::SendBufferSizeSocketOption, 4 * 1024 * 1024);
_socket->setSocketOption(QAbstractSocket::ReceiveBufferSizeSocketOption, 4 * 1024 * 1024);
```

**进度信号发射逻辑**：
```cpp
// 每 4 个 chunk 发射一次（约 32MB）
static int chunkCount = 0;
if (++chunkCount % 4 == 0 || isLastChunk == 1) {
    emit progressChanged(_bytesSent, _totalBytes);
}
```

### 12.4 性能预期

| 文件大小 | chunk 数量 | 信号发射次数 | 预期耗时（千兆） |
|----------|-----------|-------------|-----------------|
| 100 MB   | 13        | 4           | ~1 秒           |
| 1 GB     | 128       | 33          | ~8 秒           |
| 5 GB     | 640       | 161         | ~40 秒          |

**理论吞吐量**：千兆网络 125 MB/s，实际受限于磁盘 I/O 和 CPU，预期 80-100 MB/s。

### 12.5 经验总结

1. **chunk 大小要匹配网络环境**：千兆网络用 8MB，万兆可以考虑 16MB
2. **socket buffer 要显式设置**：操作系统默认值太小
3. **信号发射要节制**：高频信号会拖慢整个应用
4. **性能优化要量化**：先测量，再优化，最后验证

## 十三、AppImage 打包踩坑记录

**日期**：2026-06-04

### 13.1 背景

Stage 4 完成后，尝试将 GridYard 打包为 Linux AppImage 格式，实现单文件分发、免安装运行。

### 13.2 难点分析

**难点 1：linuxdeploy strip 报错**

**现象**：linuxdeploy 在收集依赖库时，调用 strip 命令失败：
```
ERROR: Strip call failed: unknown type [0x13] section '.relr.dyn'
```

**原因**：linuxdeploy 内置的 strip 工具版本过旧，无法识别新版 glibc（2.38+）引入的 `.relr.dyn` 段。这是 GNU binutils 的一个已知兼容性问题。

**影响**：strip 失败不影响库的功能，只影响符号表大小。可以安全忽略。

**解决**：忽略 strip 错误，继续打包流程。最终 AppImage 可以正常运行。

**难点 2：Qt6 插件和 QML 模块缺失**

**现象**：AppImage 打包成功，但启动时崩溃（核心转储）。

**原因**：linuxdeploy 只收集共享库（`.so` 文件），不会自动收集 Qt6 插件和 QML 模块。GridYard 使用 QML 架构，需要：
- `/usr/lib/qt6/plugins/platforms/` — 平台插件（xcb/wayland）
- `/usr/lib/qt6/plugins/imageformats/` — 图片格式插件
- `/usr/lib/qt6/qml/QtQuick/` — QML 运行时模块
- `/usr/lib/qt6/qml/QtQuick.Controls/` — QML 控件库

**解决**：手动复制整个 `/usr/lib/qt6/plugins` 和 `/usr/lib/qt6/qml` 目录到 AppDir。

**难点 3：appimagetool 的 desktop 文件位置要求**

**现象**：`Desktop file not found, aborting`

**原因**：appimagetool 要求 desktop 文件在 AppDir 根目录，而不是 `usr/share/applications/`。

**解决**：将 desktop 文件复制到 AppDir 根目录（保留 `usr/share/applications/` 中的副本）。

**难点 4：appimagetool 架构检测失败**

**现象**：`More than one architectures were found`

**原因**：appimagetool 无法自动检测目标架构，可能因为 AppDir 中混合了不同架构的库。

**解决**：显式设置环境变量 `ARCH=x86_64`。

**难点 5：图标文件查找路径**

**现象**：`gridyard{.png,.svg,.xpm} defined in desktop file but not found`

**原因**：appimagetool 在 AppDir 根目录查找 desktop 文件中定义的图标，而不是 `usr/share/icons/`。

**解决**：将图标文件复制到 AppDir 根目录。

### 13.3 最终打包方案

经过多次尝试，确定了以下打包流程：

1. **构建项目**：Release 模式编译
2. **准备 AppDir**：创建目录结构，复制可执行文件和资源
3. **linuxdeploy 收集依赖**：自动收集系统共享库（忽略 strip 错误）
4. **手动补充 Qt6 组件**：复制 plugins 和 qml 目录
5. **创建 AppRun 脚本**：设置环境变量，启动应用
6. **appimagetool 打包**：生成最终 AppImage

**最终产物**：`GridYard-x86_64.AppImage`（92MB）

### 13.4 AppRun 脚本设计

AppRun 是 AppImage 的入口脚本，负责设置运行时环境：

```bash
#!/bin/bash
SELF=$(readlink -f "$0")
HERE=${SELF%/*}
export PATH="${HERE}/usr/bin/:${PATH:+:$PATH}"
export LD_LIBRARY_PATH="${HERE}/usr/lib/:${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export QT_PLUGIN_PATH="${HERE}/usr/lib/qt6/plugins/${QT_PLUGIN_PATH:+:$QT_PLUGIN_PATH}"
export QML2_IMPORT_PATH="${HERE}/usr/lib/qt6/qml/${QML2_IMPORT_PATH:+:$QML2_IMPORT_PATH}"
exec "${HERE}/usr/bin/appGridYard" "$@"
```

**关键环境变量**：
- `LD_LIBRARY_PATH`：让应用优先加载 AppDir 内的共享库
- `QT_PLUGIN_PATH`：告诉 Qt 去哪里找平台插件
- `QML2_IMPORT_PATH`：告诉 QML 引擎去哪里找 QML 模块

### 13.5 经验总结

1. **linuxdeploy 不万能**：只能收集共享库，Qt 插件和 QML 模块需要手动补充
2. **strip 错误可以忽略**：新版 glibc 的兼容性问题，不影响功能
3. **appimagetool 要求严格**：desktop 文件和图标必须在根目录
4. **ARCH 环境变量必须设置**：否则 appimagetool 无法确定目标架构
5. **AppRun 脚本是关键**：正确设置环境变量才能让应用找到 Qt 组件

## 十四、单机多实例测试与设备发现 Bug 修复

**日期**：2026-06-05

### 14.1 问题背景

GridYard 是局域网 P2P 文件传输软件，需要多台设备测试。开发阶段通常只有一台电脑，需要在同一台机器上启动多个实例进行测试。

**测试命令**：
```bash

./build/client/appGridYard --port 35100 --name "接收端"

# 终端 2 - 发送端
./build/client/appGridYard --port 35101 --name "发送端"
```

### 14.2 Bug 现象

两个实例启动后，界面一直显示"正在搜索设备..."，无法发现对方。

**日志输出**：
```
DiscoveryService: 发送广播，deviceId: "0f5bb927-..." name: "接收端"
DiscoveryService: 发送广播，deviceId: "0f5bb927-..." name: "发送端"
DiscoveryService: 忽略自己的广播，deviceId: "0f5bb927-..."
```

**关键发现**：两个实例的 **deviceId 完全相同**！

### 14.3 根本原因

**问题链条**：
1. `main.cpp` 中指定了 `--port` 参数时，会设置 `GRIDYARD_CONFIG` 环境变量指向不同的配置文件
2. 但 `ConfigManager` 构造函数中，`QSettings` 的初始化方式有误
3. 导致两个实例读取了同一个配置文件，生成了相同的 `deviceId`

**问题代码**（修复前）：
```cpp
QSettings settings(configPath.isEmpty() ? QSettings::IniFormat : QSettings::IniFormat,
                   configPath.isEmpty() ? QSettings::UserScope : QSettings::SystemScope,
                   configPath.isEmpty() ? QString() : configPath);
```

当 `configPath` 不为空时，`QSettings::SystemScope` + `configPath` 的组合并不会按预期使用指定文件，而是使用系统级配置目录。

### 14.4 解决方案

**修复 1：统一 QSettings 创建方式**

在 `ConfigManager` 中，所有使用 `QSettings` 的地方都改为检查 `GRIDYARD_CONFIG` 环境变量：

```cpp
QString configPath = qEnvironmentVariable("GRIDYARD_CONFIG");
QSettings settings(configPath.isEmpty() ? QSettings() : QSettings(configPath, QSettings::IniFormat));
```

**修复 2：添加调试日志**

在关键位置添加日志，方便排查问题：

```cpp
// ConfigManager::ensureDeviceId()
if (_deviceId.isEmpty()) {
    _deviceId = QUuid::createUuid().toString(QUuid::WithoutBraces);
    settings.setValue("device/id", _deviceId);
    qDebug() << "ConfigManager: 生成新的 deviceId:" << _deviceId;
} else {
    qDebug() << "ConfigManager: 使用已有的 deviceId:" << _deviceId;
}

// DiscoveryService::handleHelloPacket()
if (deviceId == _config->deviceId()) {
    qDebug() << "DiscoveryService: 忽略自己的广播，deviceId:" << deviceId;
    return;
}
qDebug() << "DiscoveryService: 收到设备广播，deviceId:" << deviceId
         << "name:" << deviceName << "ip:" << sender.toString();
```

**修复 3：UDP 端口绑定优化**

当默认端口 45678 绑定失败时，尝试绑定到备用端口，并同时向两个端口发送广播：

```cpp
// 绑定失败时尝试备用端口
if (!bound) {
    bound = _socket->bind(QHostAddress::AnyIPv4, 0,
                          QUdpSocket::ShareAddress | QUdpSocket::ReuseAddressHint);
}

// 发送广播时，同时发送到默认端口和本地端口
_socket->writeDatagram(data, entry.broadcast(), gy::protocol::kDefaultDiscoveryPort);
if (_socket->localPort() != gy::protocol::kDefaultDiscoveryPort) {
    _socket->writeDatagram(data, entry.broadcast(), _socket->localPort());
}
```

1. **QSettings 构造要谨慎**：`QSettings::SystemScope` + 自定义路径的行为可能不符合预期，直接用文件路径构造更可靠

## 十五、拖拽文件崩溃与 QML_SINGLETON 陷阱

**日期**：2026-06-05

### 15.1 问题现象

修复设备发现 bug 后，用户测试拖拽文件到设备卡片功能，程序立即崩溃（段错误）。

**日志**：
```
[TransferSession] 创建发送会话
[TransferSession] 目标设备ID: "da6de09d-..."
[TransferSession] 文件路径: "/root/GridYard/GridYard/README.md"
segmentation fault (core dumped)
```

### 15.2 根本原因

`TransferSessionManager` 声明为 `QML_SINGLETON`，QML 引擎会自动创建一个独立实例。但这个实例没有调用 `init()` 方法，导致 `_discovery`、`_config`、`_p2pServer` 都是空指针。

**问题链条**：
1. `AppController` 构造函数中创建了 `TransferSessionManager` 并调用 `init()`
2. QML 引擎又创建了一个新的 `TransferSessionManager` 单例（未调用 `init()`）
3. QML 中使用 `TransferSessionManager.createSendSession()` 调用的是未初始化的实例
4. 访问空指针 `_discovery->peerInfo()` 导致段错误

### 15.3 解决方案

**方案**：移除 `TransferSessionManager` 的 `QML_SINGLETON`，改为通过 `AppController` 暴露给 QML。

**修改内容**：

1. `transfer_session_manager.h`：移除 `QML_ELEMENT`、`QML_SINGLETON` 和 `create()` 静态方法
2. `app_controller.h`：添加 `transfer` 属性和 getter 方法
3. `Main.qml`：将所有 `TransferSessionManager.xxx` 改为 `AppController.transfer.xxx`

**代码变更**：
```cpp
// app_controller.h - 添加 transfer 属性
Q_PROPERTY(TransferSessionManager* transfer READ transfer CONSTANT)
TransferSessionManager *transfer() const;

// transfer_session_manager.h - 移除 QML_SINGLETON
class TransferSessionManager : public QObject {
    Q_OBJECT
    // 移除 QML_ELEMENT 和 QML_SINGLETON
    ...
};
```

```qml
// Main.qml - 使用 AppController.transfer
Connections {
    target: AppController.transfer  // 而不是 TransferSessionManager
    ...
}

onFileDropped: function(deviceId, filePath) {
    AppController.transfer.createSendSession(deviceId, filePath)
    // 而不是 TransferSessionManager.createSendSession(...)
}
```

### 15.4 经验总结

1. **QML_SINGLETON 的陷阱**：使用 `QML_SINGLETON` 时，QML 引擎会自动创建实例，但不会调用自定义的初始化方法。如果需要初始化，应该通过其他方式暴露。

2. **单例初始化顺序**：如果一个单例依赖其他组件，应该在所有依赖都准备好之后再暴露给 QML，而不是让 QML 引擎自动创建。

3. **空指针检查**：在访问可能为空的指针时，应该添加检查。但更重要的是从架构上避免这种情况。

4. **段错误调试**：段错误通常发生在访问空指针或已释放内存时。通过日志定位最后执行的操作，然后检查该操作涉及的指针。

5. **QML 类型注册选择**：
   - `QML_SINGLETON`：QML 引擎自动创建实例，适合无状态或全局唯一的组件
   - `QML_ELEMENT` + 手动暴露：适合需要初始化或依赖注入的组件
   - `QML_ANONYMOUS`：不作为独立类型暴露，适合被其他对象持有的子对象
