## 1. 初始架构设计：为什么这么分层？

在项目启动之初（2026-04-23），我们面临一个核心挑战：如何在一个开发周期内，既实现高性能的 P2P 文件直传，又为未来的即时通讯（IM）和离线漫游预留空间？

### 1.1 模块化设计的初衷
我们在 `src/` 目录下进行了极其详细的分类，这并非为了增加复杂度，而是为了实现**物理隔离**：

*   **`shared/` (核心基石)**：存放 TLV 协议定义、共用数据类型和帧编解码器。它是 client 和 server 的“共同语言”。将其独立出来，可以确保双端协议实现的高度一致性。
*   **`client/` (桌面端)**：基于 Qt Widgets/Quick 的客户端。它只负责 UI 展示和 P2P 逻辑。
*   **`server/` (未来演进)**：预留给 V2.0 的“邮局”服务端。它不参与文件传输，仅负责用户鉴权和离线消息。
*   **`tests/` (质量保证)**：独立于业务代码，确保协议解析等核心逻辑的健壮性。

### 1.2 这么分类的好处
1.  **平滑演进**：V1.0 实现纯 P2P 传输时，`server/` 可以保持空壳。到了 V2.0 引入服务端时，我们只需要在 `server/` 下写代码，并让它链接 `shared/` 库即可，**完全不需要改动 client 的核心逻辑**。
2.  **职责清晰**：网络层、业务层、UI 层边界明确。比如 `FrameCodec` 只管字节流拆包，不管里面是文件还是聊天记录。
3.  **构建提速**：CMake 可以针对改动的模块进行增量编译，而不需要重新扫描整个项目。

## 2. CMake 层级构建逻辑

我们采用了典型的“总-分”式 CMake 结构：

1.  **顶层 `src/CMakeLists.txt`**：作为指挥官，负责环境检测（如 Qt6 查找）、编译器配置，并通过 `add_subdirectory()` 串联各个子模块。
2.  **子模块 `shared/CMakeLists.txt`**：被构建为一个静态库 `gy_shared`。它声明了自己的包含路径（include directories）和编译特性（C++23）。
3.  **应用端 `client/CMakeLists.txt`**：最终的可执行文件 target。它链接 `gy_shared` 以及 Qt 库。

这种层级设计的精妙之处在于**依赖传递**：只要 client 链接了 `gy_shared`，它就会自动继承 `shared` 目录的头文件搜索路径，代码中直接 `#include "protocol.h"` 即可，无需写复杂的相对路径。

## 3. 踩坑记录：C++23 模块与中文路径

**日期**：2026-05-26

### 问题现象
在环境搭建完成后，第一次编译遇到了诡异的错误。CMake 配置通过了，但在编译生成依赖阶段，连最基本的 `#include "frame_codec.h"` 都报了解析错误：
```text
error: 无法确定 .../frame_codec.h 的 ‘#include’ 转换：
malformed string 'ERROR 'unrecognized \'INCLUDE-TRANSLATE \'/.../frame_codec.h\'\'''
```

### 真正的原因
最终确认是 **GCC 16 的一个编译器 Bug**：
我们在 CMake 中开启了 C++23 模块的实验性支持。当 GCC 尝试扫描代码依赖时，它的 `g++-mapper-server` 无法正确处理我们项目路径中的中文字符（`Qt6软件开发资料`）。中文路径导致它的内部指令格式损坏，引发崩溃。

此外，也发现了一些配置上的小疏忽：
1. `main.cpp` 用了 `QQuickStyle`，但 CMake 里忘了链接 `QuickControls2`。
2. 自动生成的 C++ 注册代码找不到 `app_controller.h`，需要把 `core/` 目录加入包含路径。

### 解决办法
为了兼顾中文路径下的开发体验，我们采取了以下措施：
1.  **关闭扫描**：在 `src/CMakeLists.txt` 中设置 `set(CMAKE_CXX_SCAN_FOR_MODULES OFF)`，绕过编译器 Bug。
2.  **补全配置**：在 CMake 中显式引入 `QuickControls2` 组件，并将 `client/core` 加入包含路径。

### 避坑建议

在玩 C++23 模块化等前沿特性时，尽量保持**项目全路径为英文**。如果遇到诡异的编译器报错，先换个英文路径试试，这往往是解决“灵异事件”的最快方式。

## 4. CMake 模板多模块拆分艺术：从单体到三层架构

**最后更新**：2026-05-26

为了让后续新加入团队的同学理清 CMake 构建体系，我们在 `doc/templates/CMakeLists.qml.template` 中对经典单体 Quick 模板进行了“三段式”的功能区域划分，并总结了多模块拆分的深层思考。

### 4.1 原单体 CMake 模板的模块划分与职责
在一个标准的 Qt Quick 单体工程中，CMake 文件主要集成了以下四大职责板块：
1. **全局编译器环境定义**（第 19-21 行）：声明最低 CMake 版本，并启用实验性 C++23 模块。
2. **Qt 环境发现与基础工程化配置**（第 25-26 行）：通过 `find_package` 拉取所需的 Qt 二进制包，并调用 `qt_standard_project_setup` 规范化资源加载路径。
3. **QML 模块注册与源文件声明**（第 28-38 行）：采用 `qt_add_qml_module` 将 C++ 源码与 QML 界面资产进行一站式注册与资源编译。
4. **依赖注入与部署发布**（第 39-48 行）：声明 `cxx_std_23` 标准，链接 Qt 组件库，并注入 `/opt/${PROJECT_NAME}` 的标准安装目录。

### 4.2 为什么要进行“三层拆分”？
如果死板地套用上述单体模板，当 GridYard 项目随着阶段演进时，会立刻遭遇架构“大熔炉”的困境：
* **如果协议库不隔离**：客户端（Client）和服务端（Server）都要共用 TLV 协议，如果不拆分，服务端在编译时就不得不链接 QtQuick 等沉重的 UI 动态库，背负无意义的运行时包大小。
* **如果测试用例不独立**：核心的网络粘包状态机（FrameCodec）极其依赖自动化单测。在单体结构下，运行 `ctest` 必须连带启动整个客户端 UI 系统，导致单测效率低下。

因此，我们以 **“物理隔离、高内聚”** 为原则，将单体模板打碎重构为三层：
* **顶层 `src/CMakeLists.txt`**：只保留**全局编译器环境定义**与 **Qt 包统一拉取**，作为整个项目的“总参谋部”，使用 `add_subdirectory` 挂载子模块。
* **逻辑层 `src/shared/CMakeLists.txt`**：剥离所有 UI 动作，将其重塑为一个**纯 C++ 静态库 `gy_shared`**，专门负责协议常量与帧状态编解码。
* **应用层 `src/client/CMakeLists.txt`**：专门处理**客户端 QML 注册**与 UI 依赖，最终静态链接 `gy_shared`。

### 4.3 三层拆分的核心工程学好处
1. **极致的模块化与高内聚**：
   通过分层，项目结构呈现出极高的系统秩序。`shared` 协议库只和字节流、网络报文打交道，没有任何 QML 的杂质，这保证了底层业务逻辑的纯洁性。开发 IM 服务端和桌面客户端的同学可以完全并行开发，互不干扰。
2. **依赖传递与“零包含路径”痛苦**：
   在 `shared/CMakeLists.txt` 中，我们巧妙使用了 `PUBLIC` 关键字：
   ```cmake
   target_include_directories(gy_shared PUBLIC .)
   ```
   这使得任何链接了 `gy_shared` 的上层模块（如 client）都会**自动向上冒泡继承**公共包含路径。在客户端 C++ 源码中，我们可以优雅直接地编写：
   ```cpp
   #include "protocol.h"  // 极其干净，无需写 "../shared/protocol.h"
   ```
3. **极速的增量编译**：
   当美术或前端同学仅仅修改了 `Main.qml` 的布局时，CMake 只会增量重新打包 client 的 QML 资源系统，底层的 `gy_shared` 静态库以及未来的 `server` 进程完全不需要重新编译，这为大型项目的日常研发协同节省了海量的等待时间。
